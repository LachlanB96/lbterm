# The code map

Where LBTerm's code lives and what runs when, for whoever is about to change it. The design docs beside this file say why each feature works the way it does; this says where it is, and FLOWS.md says step by step what runs for each event that matters. Read both before searching the code.

Keep it true as you go, and make it more detailed every time you learn something it doesn't say: where a thing happens, what calls it, on which thread, how often it runs, what it holds while it does, and the processes and threads LBTerm runs. A search this map should have answered is a gap you fill in the same commit as the work that needed it; the next reader should never have to search for what you found. A file renamed, split or moved gets its line fixed in the same commit too. Function names are given rather than line numbers, which move.

The sizes below are rough line counts. The big files are for searching, not reading whole: `rg -n 'fn name' <file>`, then read the part you need.

## The crates

How the split goes: LBTerm's logic goes in an `lbterm-*` crate where a test can reach it without a window; `wezterm-gui` holds the drawing and the GUI-thread glue; an upstream file gets as small a change as can be, a call into LBTerm's code with a comment starting `// LBTerm:`. `rg -n '// LBTerm' <upstream file>` finds every hook LBTerm has in it.

## The paths

### A key press

1. `window/src/os/windows/window.rs`, `key()`: `WM_KEYDOWN`, `WM_CHAR` and the rest become a `WindowEvent::RawKeyEvent` and then a `WindowEvent::KeyEvent`, the modifiers read from the GUI thread's own keyboard state (`GetKeyboardState`), which a key a test posts doesn't change but the real keyboard's does: a modifier Lachlan holds reaches a test window's posted keys (2026-11-01, a posted A arriving as a capital while he held Shift in a game), so the harness's `Send-Key` waits one out (`Wait-ModifiersUp`) and notes it. IME composition is `ime_composition()` beside it. The tasks queued for the GUI thread run between messages: the message loop (`connection.rs`) drains them with `window/src/spawn.rs`'s `run_until_message()`, which stops for a key, the pointer or a posted message waiting.
2. `wezterm-gui/src/termwindow/mod.rs`, `dispatch_window_event()`, hands them to `termwindow/keyevent.rs`: `raw_key_event_impl()` and `key_event_impl()`. LBTerm notes the key's arrival (`lbterm_extras::arrival`), stops the scroll strip scrolling a program, and notes the modifiers held (`termwindow/held.rs`), then `process_key()` (while a menu is open, its raw passes act on no binding and its cooked pass gives the key to the menu ahead of the leader and the bindings: render/menu_fade.rs `lbterm_menu_takes_keys` and `lbterm_menus_key`, Lachlan's 7b; but both first ask `lbterm_menus_binding`, the raw pass by each of its three key forms, for the bindings an open menu acts on, a + menu row's shortcut and a paste into the picker's box, render/new_tab.rs `lbterm_new_tab_binding`, his 5a and 11a; FLOWS.md, "A key while a menu is open") either runs a key assignment (`inputmap.rs` finds it, `perform_key_assignment()` in `mod.rs` and `commands.rs` run it) or sends the key to the pane with `pane.key_down()`. A binding's `SendString` (Lachlan's Shift+Enter and Alt+Enter), a key in win32-input or kitty mode, an IME's or the char selector's text, the scroll strip's keys, a voice draft and Lua's `pane:send_text` write to the pane instead (`pane.writer()`): on a mux domain that's `clientpane.rs`'s `PaneWriter`, which sends `WriteToPane` from a task as a key is sent, behind any key still waiting to go, and doesn't wait for the answer. The task hears it (`Client::lbterm_write_to_pane`, `lbterm_link::Failure::of`), and a write the server refused or that was lost with the connection is logged and handed to `mux::lbterm_writes::failed` with the window's own pane id; while the connection is down a write waits in the client's channel with the keys round it and fails only if the client gives up (`lbterm_link::GaveUp`, PITFALLS 178). The GUI's hook (`render/scroll_strip.rs`'s `start()`, set in `main.rs` after `counters::start()`) hops to the main thread, finds the window holding the pane (`Mux::resolve_pane_id`, `GuiFrontEnd::gui_window_for_mux_window`) and has it run `lbterm_scroll_write_failed`: a seek in that pane ended (`SeekCtl::gone`), the pane's tab resolved again (`Mux::resolve_pane_id`; a pane the mux no longer holds is only logged) and the strip's note kept with it (`lbterm_extras::scroll_note::Note::tab`), shown while that tab is the window's active one (`lbterm_scroll_shown_note`). The strip's seek asks `ClientPane::lbterm_link_down` before each burst (`seek`'s `Step::Press`, `link_down`) and with the link down ends as `Sought::Down`, which notes "Not sent" through the same `lbterm_scroll_write_failed`. A write lost with the connection is headed "May not have arrived" (`Failure::reached`, `mux::lbterm_writes::Reached`). A voice draft's send doesn't go through `PaneWriter`: `termwindow/control.rs`'s `type_keys` waits for each key's answer (`ClientPane::lbterm_write_answered`) and on a failure puts the draft back (`lbterm_draft_failed`, `lbterm_extras::drafts::put_back`), noting through the same `lbterm_scroll_write_failed`. lbterm/SCROLL-STRIP.md, "Notes"; MUX.md, "A write to a pane". A key sent to a pane asks for no frame of its own unless that frame draws something LBTerm draws itself (`termwindow/echo.rs`, `lbterm_extras::echo`): the echo's output asks for the frame that shows it. A dead key or an IME composing comes as `WindowEvent::AdviseDeadKeyStatus` (from `key()` and `ime_composition()` in `window.rs`), handled in `dispatch_window_event()`; its end waits for the composed key's echo to paint it the same way (`lbterm_composition_frame` in `termwindow/echo.rs`).
3. A pane of the GUI's own: `mux/src/localpane.rs`, `key_down()`, encodes it into the pty through the terminal's writer thread (term's `terminalstate/mod.rs`, `ThreadedWriter`: a channel and a thread a pane, which a paste and the terminal's replies to queries take too). A pane's `writer()` (a binding's SendString, a mux client's WriteToPane, Lua's `send_text`) writes through the same thread since perf/mux-client (`TerminalState::lbterm_writer`), so it reaches the program behind the keys typed before it: it wrote to the pty itself, on the caller's thread, and could overtake them (PITFALLS 137).
4. A pane on a mux domain (every tab, with `MUX = true`): `wezterm-client/src/pane/clientpane.rs`, `key_down()`, predicts the echo (`renderable.rs`, `predict_from_key_event()`) and sends `SendKeyDown` from a spawned task. The server's `wezterm-mux-server-impl/src/sessionhandler.rs` takes it in its `Pdu::SendKeyDown` arm: it notes the pane as the connection's input pane, so `lbterm_flow` pushes that pane first, runs `pane.key_down()` on the server's main thread, and sends the pane's changes back at once (`compute_changes()`).
5. The echo comes back as pane output, below. `termwindow/budget.rs` times a key from its arrival to the frame that shows its echo.

### Pane output

1. `mux/src/lib.rs`: `read_from_pane_pty()` reads each pane's pty on a thread of its own, and `parse_buffered_data()` is the parser thread. It holds output back for `mux_output_parser_coalesce_delay_ms` on a high-resolution timer (`lbterm_wait.rs`), applies it to the terminal (`term`: the parser hands a run of printable ASCII over whole, `wezterm-escape-parser`'s `Parser::lbterm_print_runs` and `vtparse`'s `VTActor::print_ascii`, and `terminalstate/performer.rs`'s `flush_print` writes it to its line at once, `lbterm_print_ascii` and `Line::set_cells_ascii`, which `Terminal::lbterm_print_as_upstream` turns off for a test's reference; a cell's 24-bit colours and link are `wezterm-cell`'s `fat`, an `Arc` shared by the cells a pen wrote), then queues one `PaneOutput` notification at a time (`lbterm_output.rs`, `OutputNotice`) and the batch's alerts together (`HeldAlerts`). On Windows, before and around the parser (FLOWS.md's pane-output flow, rows 1 to 18, has each step's cost):
   - The pty: portable-pty's `ConPtySystem::openpty` (`pty/src/win/conpty.rs`) makes two anonymous pipes with CreatePipe (the default size, synchronous), and `PseudoCon::new` (`pty/src/win/pseudocon.rs`) calls CreatePseudoConsole with `PSEUDOCONSOLE_INHERIT_CURSOR`, `RESIZE_QUIRK` and `WIN32_INPUT_MODE` (`PASSTHROUGH_MODE` is defined and unused). `load_conpty` takes `conpty.dll` from beside the exe (the bundled ConPTY 1.25 in `assets/windows/conhost`, with its `OpenConsole.exe`; wezterm-gui's `build.rs` copies both next to the exes) and falls back to kernel32's inbox ConPTY without a word (PITFALLS 106). Each pane's `OpenConsole.exe` is a child of the process that made the pane: on a mux domain, `lbterm-mux-server`. `LocalDomain::spawn_pane` (`mux/src/domain.rs`) runs `openpty` and `spawn_command` on a `smol::unblock` thread unless the mux is empty.
   - The pane's terminal is made in `LocalDomain::spawn_pane` with `TermConfig::new()` (no config, so each lookup goes to `config::configuration()`), `enable_conpty_quirks`, and a `WriterWrapper` (a Mutex round the pty's input pipe) through which the parser thread writes replies to queries, under the terminal lock (PITFALLS 85).
   - Four unnamed threads a pane: `split_child`'s waiter (`mux/src/localpane.rs`), the terminal's writer (term's `ThreadedWriter`, made with the terminal: the program's input, written to the pty's pipe in the order it's given, the key press's step 3), the reader (`Mux::add_pane` → `read_from_pane_pty`, a 128 KB buffer, `LBTERM_READ_BUFSIZE`) and the parser (`parse_buffered_data`, started by the reader). The reader hands each read to the parser over filedescriptor's Windows socketpair, a loopback TCP connection (`filedescriptor/src/windows.rs`, `socketpair_impl`; 1 MB buffers from `allocate_socketpair` in `lib.rs`), so that the parser can ask it with WSAPoll(0) (filedescriptor's `poll_impl`) between sleeps on `lbterm_wait`'s high-resolution timer (`Coalesce::wait`, which sleeps its whole time: PITFALLS 82). Each ConPTY write is one read and one send (PITFALLS 94).
   - Synchronized output (DECSET and DECRST 2026, DECSTR) is held in `parse_buffered_data`'s callback, not in `term`: the performer ignores the mode, and `term/src/terminalstate/mod.rs` answers DECRQM 2026 with status 2. The hold has no time or size bound (PITFALLS 83 and 84), and the flush at a DECSET performs the DECSET itself as a batch of its own (PITFALLS 125). ConPTY 1.25 passes all three on as written, and real Claude Code brackets every frame (FLOWS.md rows 1, 2 and 9, run 5).
   - A pane's pty reads can be recorded: with `LBTERM_PTY_RECORD=<folder>` in the process's environment (a test window's, which the mux server it starts inherits; a GUI records its own local panes too), `read_from_pane_pty` writes every read, with the time it returned and its bytes, and the pane's size to `pane-<pid>-<pane id>.ptyrec` there (`mux/src/lbterm_ptyrec.rs`, `Recorder`: one unbuffered write a record), and `LocalPane::resize` notes each resize (`lbterm_ptyrec::resized`, through the open recorders by pane id). Off, the reader holds `None`. `mux/tests/lbterm_pty_frames.rs` reads a recording back through the terminal model as the parser does it, and `perf/claude-output.ps1` makes one of real Claude Code.
   - `LocalPane::perform_actions` wraps the batch in `procs.printed()` and `procs.shows()` (`lbterm_proclist`). Alerts raised while performing go `LocalPaneNotifHandler` (`localpane.rs`) → `HeldAlerts` → `deliver_held`, all inside the terminal lock.
   - The server's main-thread queue is promise's `SimpleExecutor` (`promise/src/spawn.rs`): one unbounded flume FIFO that normal and low-priority spawns share, drained by `loop { executor.tick() }` in `wezterm-mux-server/src/main.rs`. `spawn_into_main_thread` takes two process-wide std mutexes (SCOPED_EXECUTOR, ON_MAIN_THREAD) and allocates twice, and `schedule_runnable` holds ON_MAIN_THREAD across the scheduler's Box, its flume send and the main thread's unpark, so every spawner in the process serializes on that mutex across a syscall (PITFALLS 108).
   - The mux server installs no metrics recorder (`stats::Stats::init` is commented out in its `main.rs`), so the `histogram!` calls in `mux/src/lib.rs` record nothing there, and its logger's level is Info (`env-bootstrap/src/ringlog.rs`) (PITFALLS 99).
2. `Mux::notify()` reaches each subscriber on the main thread. In the GUI that's `termwindow/mod.rs`, `subscribe_to_pane_updates()`, where a mux pane's output out of the open tab stops as news for the budget, with no task (`termwindow/budget.rs`, `lbterm_hidden_output()`), noted for the scan of its screen once it's been quiet 250 ms (`termwindow/hidden_scan.rs`, `lbterm_extras::hidden_scan`), and `mux_pane_output_event_callback()` drops what the window has no use for, repaints for the layout changes upstream didn't paint for (`mux/src/lbterm_repaint.rs`) and hands the rest to the window as `TermWindowNotif::MuxNotification`.
3. `dispatch_notif()` then runs `mux_pane_output_event()`, which invalidates the window when the pane is visible (not while the Conductor's view covers the panes), and its `Alert` arms take titles (`termwindow/titles.rs`), user vars (`claude_status`, `claude_quiet`, `claude_session`: the tab panel and the strip; `claude_quiet`, a reply gone quiet or stuck, is read in `render/tab_panel.rs`'s `panel_tab` and judged in `lbterm-panel`'s `claude::row`), progress (`termwindow/taskbar.rs`), bells and notifications.
4. In the mux server, the same notifications feed each connection: a mux push, next.

### A tab switch

1. A key (`ActivateTabRelative`, `ActivateTab`: `inputmap.rs`, then `perform_key_assignment()`), a click on a pad on the rail (`render/tab_panel.rs`, `tab_panel_mouse`) or the side buttons (the `LbtermTab` action his lbterm.lua binds them to, `termwindow/hop.rs`; FLOWS.md, "A side button's hop, from the press to the tab switch") reach `termwindow/mod.rs`'s `activate_tab()` or `activate_tab_relative()`. The budget's `tab` action begins there (`lbterm_budget_tab`, timed to the frame that shows the other tab).
2. `mux/src/window.rs`, `remember_and_set_active_tab_idx()` then `set_active_tab_idx_without_saving()`: the old tab's active pane told `focus_changed(false)`, the index set, and `invalidate()`, which sends `MuxNotification::WindowInvalidated` to every subscriber.
   The `invalidate()`'s WindowInvalidated reaches the client domain's subscriber (`wezterm-client/src/domain.rs`, `mux_notify_client_domain`), which since perf/hidden-output queues one GUI-thread task (`lbterm_mark_shown` → `lbterm_say_shown`) that sends the server the panes the windows now show (`SetShownPanes`, `wezterm-client/src/lbterm_shown.rs`), so a server of that build pushes the new tab's held pane first (lbterm/MUX.md, "Tabs out of view: output held at the server").
3. Back in `activate_tab()`: the new tab's pane told `focus_changed(true)`, which on a mux domain (`wezterm-client/src/pane/clientpane.rs`) clears its unseen-output mark and, when it isn't the connection's focused pane already, sends `SetFocusedPane` to the server from a spawned task (`advise_focus`); then `update_title()` and `update_scrollbar()`.
4. The frame: since perf/hidden-output, each paint first asks, at `paint_impl`'s start, `TermWindow::lbterm_frame_panes` (`termwindow/frame_wait.rs`, the rules `lbterm_extras::frame_wait`) whose panes it draws: for a new view with a pane its server holds (`ClientPane::lbterm_is_held`), the frame is painted as it would be, the rail's glide, the strip's swap and every fade starting, but in the panes' room it draws the tab drawn last's panes as they were (`FrameTab::Kept`; Lachlan's 2b of 2026-11-08), which the panes and their splits (render/paint.rs), the question colours and voice drafts over them, the scroll strip beside them and the state file's `panes` read through `lbterm_panes_to_paint`, `lbterm_pane_to_paint` and `lbterm_splits_to_paint`, until the pane's push invalidates the window or `config::lbterm::SWITCH_WAIT` (50 ms after the first try, one wake armed at the wait's first frame) has passed; then the new tab's panes are drawn, and the compositor (`termwindow/compositor.rs`, `switch_flight`) keeps the old tab's pane visuals with their last frame, moves them over the new tab's and fades them on `tab_switch` (200 ms, DESIGN.md); tabs still fading each go by their share of the screen (`lbterm_motion::flight`), the window's outline by `switch_outline`, the strips down the right through `render/sides.rs` (`SideLayers`) and the strip's words through `render/strip_swap.rs`. Pane surfaces come from a pool, reassigned and resized, kept to the most panes the window has shown at once (`spare_panes`, in the state file). COMPOSITOR.md, "Motion", has the rules; PERF.md's actions table, `tab-by-key` and `tab-by-click`, what it costs.

### A window's resize

FLOWS.md's "A window's resize on a mux domain" has each step with its cost and whether it needs to run.

1. `window/src/os/windows/window.rs`: WM_WINDOWPOSCHANGED goes to `wm_windowposchanged` → `wm_size` → `check_and_call_resize_if_needed` (GetClientRect against the last size) → `WindowEvent::Resized`, its `live_resizing` the window's `in_size_move`: true between WM_ENTERSIZEMOVE and WM_EXITSIZEMOVE, Windows' sizing loop for a drag of the frame, which runs on the GUI thread and in which `wm_size` paints and runs every queued task (`SPAWN_QUEUE.run()`). `wm_enter_exit_size_move` sets it; at WM_EXITSIZEMOVE, when the size changed inside the loop (`lbterm_sized_in_move`, set by the check), `lbterm_size_move_ended` has the next check dispatch a Resized even at the drag's last size, which said nothing before perf/mux-client, and asks no paint for it (`wm_size` paints only for a size that changed); a move by the title bar, which changes no size, dispatches nothing, as upstream's didn't.
2. `wezterm-gui/src/termwindow/resize.rs`: `TermWindow::resize` (from `dispatch_window_event`, and from `mod.rs`'s `lbterm_follow_window_size`, the paint's own look at the client rect, which passes on whether a drag is under way: PITFALLS 139) → `apply_dimensions` (or `scaling_changed` → `apply_scale_change` → `apply_dimensions`) → `Tab::resize` for each tab of the window. During a drag only the tab in view takes each size and the rest the size it ends at (`lbterm_extras::resize::Behind`, the window's `lbterm_resize`; `lbterm_resize_behind` at the drag's end). `lbterm::resize` at debug says each size, how many tabs took it, each pane's size and whether it was sent.
3. `mux/src/tab.rs`: `TabInner::resize` → `resize_panes` → `apply_sizes_from_splits` → each pane's `resize`, and TabResized in the GUI's own mux when the layout key moved (`layout_key`, `notify_resized_if_changed`). A mux pane's is `wezterm-client/src/pane/clientpane.rs`'s `ClientPane::resize`: the size taken, no held line made stale (since perf/mux-client's close-pane stage; it made every one stale before), and a Resize PDU from a spawned task that, once the server answers it, asks for the pane's changes (`renderable.rs`'s `ask_changes`, a GetPaneRenderChanges): the push that answers names the rows the rewrap changed, which `apply_changes_to_surface` takes through `rows_named`. A size given inside `pane/lbterm_sizes.rs`'s `from_server` (a resync's) isn't sent, and asks at once unless a Resize of the window's own is out. A zoom (`set_zoomed`) sends SetPaneZoomed and makes nothing stale; its size comes through `resize` (FLOWS.md's resize flow, rows 4, 13 and 14).
4. Server: `sessionhandler.rs`'s Resize arm → `lbterm_resize.rs`'s `Resizes::ask`: the newest size asked for the pane and the request's answer noted; a pane not being resized is resized on a thread of its own (`lbterm-resize`: `LocalPane::resize`, which is ResizePseudoConsole under the pty's lock, `lbterm_ptyrec::resized` and `Terminal::resize` under the terminal's lock), the thread's work wrapped in `guarded` (`catch_unwind`), so a panic is an error the book hears like any other (PITFALLS 161); then on the main thread `Resizes::done` starts the newest size asked meanwhile, or, the pane's resizes over, rebuilds the split sizes of each tab none of whose panes is being resized any more (`rebuild_splits_sizes_from_contained_panes`, which reads every pane of the tab under its terminal's lock; TabResized when the layout moved, to every connection but the one whose Resizes alone it applied: `rebuilding_as` marks the rebuild with the tab and that connection's `Conn`, a number each `SessionHandler` takes as it's made, and `dispatch.rs`'s subscriber asks `is_own` as the notification reaches it), answers every request waiting, runs the pane's requests that waited, and, with no pane being resized at all, the requests that waited for every resize. The pane's input and reads (`sessionhandler.rs`'s WriteToPane, SendPaste, SendKeyDown, SendMouseEvent, GetPaneRenderChanges, GetLines and GetPaneRenderableDimensions arms) go through `Resizes::after`, which runs them at once or, while the pane is being resized, after its resizes in the order they came (PITFALLS 145); what lists every pane's size or resizes panes on the main thread (the ListPanes, SplitPane, KillPane, SetPaneZoomed, MovePaneToNewTab and AdjustPaneSize arms) goes through `Resizes::after_all`, which runs it once no pane is being resized (PITFALLS 160). The book is one for the server (`resizes()`), whichever connection asked. Until perf/mux-client every Resize was a task on the main thread, applied in order.
5. The terminal: `TerminalState::resize` → `TerminalScreens::resize` → each `Screen::resize` (`term/src/screen.rs`): trailing blank rows pruned, and for the primary screen a new width `rewrap_lines`, which joins a wrapped run (`Line::append_line`) and cuts a line longer than the width (`Line::wrap`); a clustered line a run at a time (`wezterm-surface/src/line/clusterline.rs`'s `lbterm_append_line`, `lbterm_wrap`, `lbterm_last_wrapped`; the cell-at-a-time ways kept for a vector of cells and for lines of `u16::MAX` cells or more); a line that keeps its row and cells keeps its sequence number. The screen's `lbterm_changes` is forgotten, so the next `get_changed_stable_rows` reads every line (`term/src/lbterm_changes.rs`).
6. Back in the GUI: each TabResized → `client.rs`'s arm → a task → `ClientDomain::resync` (`domain.rs`; one at a time, `coalesce.rs`) → ListPanes → `process_pane_list` → each tab `sync_with_pane_tree` at the server's sizes inside `from_server`, then, for a tab it had already one of whose panes has a Resize the server hasn't answered (`lbterm_sizes.rs`'s `Unanswered`, `tab_unanswered`; the listing was asked before the server had it), the size its window gave it put back, inside `from_server` too, so nothing is sent from a resync; with none out the server's size is the tab's (`keeps_its_own`). Each pane's first push after its resize brings its dirty rows; those above the viewport only leave the cache (`renderable.rs`'s `drop_rows_above`).

### A mux push, from the server to a window

1. Server: a connection's mux subscriber fills its `lbterm_flow::Pending` (which panes are owed a push, the alerts they raised, the window's latest title). `dispatch.rs`'s loop works out pushes only while the connection's `Outbox` has room, the input pane's first: `sessionhandler.rs`, `lbterm_push()`, then `PerPane::compute_changes()`, which copies only the lines that go (`lbterm_push::lines_to_send()`) into a `GetPaneRenderChangesResponse`. In the server, as FLOWS.md traced it (rows 19 to 41):
   - A connection is one task on the server's main thread. `LocalListener::run` (`local.rs`), on the listener thread `spawn_listener` starts, accepts it, sets SO_SNDBUF to 4 KB (`lbterm_flow::set_send_buffer`) and `spawn_into_main_thread(dispatch::process)`. Every task's wake from any thread is an async_task schedule → `schedule_runnable` (the global ON_MAIN_THREAD mutex, held through what follows: PITFALLS 108) → a Box → a flume send, unparking the main thread (WaitOnAddress) if it waits. In daily use there's one connection a GUI process (a ClientDomain has one Client for all its windows) and one an `lbterm cli` call.
   - Socket readiness comes from async-io's own reactor thread (`async-io`, polling 3.11's IOCP and AFD polls); reads and writes are tried directly on the main thread (uds_windows' recv and send on a non-blocking AF_UNIX socket).
   - Each connection's mux subscriber (`process_async`'s closure in `dispatch.rs`) runs inside `Mux::notify` on the main thread, under the subscribers' write lock: it fills `Pending` and sends `Item::Owed` once a wait. It's registered as the connection starts and dropped at the first notification after it ends.
   - A push's order: `fill` → `read_now` (one recv a pane pushed, and one more) → `Pending::take_next` → `SessionHandler::lbterm_push` (`gets_changes`) → `push_pane_changes` → `PerPane::compute_changes`: `Pane::lbterm_read_for_push(since)` (`mux/src/lbterm_push_read.rs`; since perf/mux-client's flood build), which for a `LocalPane` locks the tmux domain once and then the terminal once for everything (`from_terminal`: dimensions, cursor, mouse grab, alternate screen, the terminal's own title and OSC 7 cwd, the seqno and `terminal_get_dirty_lines` from `lbterm_rows_to_read`), and after the lock makes a default title the foreground's name (`title_or_process_name`) and a missing cwd the listed one (`lbterm_listed_cwd`); any other pane answers through the getters one by one (`by_getters`, the trait's default); then `lbterm_push::lines_to_send` (a clone and `compress_for_scrollback` a line), `SerializedLines::from`. Then `push_pane_changes` turns the notifications into PDUs (SetProgramStatus, SetPalette, NotifyAlert), and `Outbox::add` → `Pdu::encode` → `serialize_with` (varbincode) → `KeptZstd::compress` (over 32 B) → `encode_raw_as_vec` → `write_all` into the outbox; `Outbox::write_now` sends once a round. That's two terminal locks a push that sends, the read and the lines' copy (nine until the flood build, PITFALLS 86). Which owes are pushed with their changes is `lbterm_flow::Owed`'s `changes`: output, or an alert `mux::lbterm_output::reads_the_push` names (a title, the cwd); an owe of other alerts alone goes to `push_pane_changes(.., changes: false)`, which sends only their PDUs and the first push's state.

   - Pushes outside Pending, each sent through `PduSender` as `Item::WritePdu` and encoded at the next round's drain, outside the outbox's room check: SendKeyDown's (forced, with the input serial), the GUI's poll (GetPaneRenderChanges → `maybe_push_pane_changes` and a LivenessResponse), and WriteToPane's, SendPaste's, KillPane's and SetPalette's for a connection that gets the pane. SendMouseEvent's went too until perf/mux-client: a mouse event only writes the program a report (term's `terminalstate/mouse.rs`), so the arm now answers with no push, and what the program draws comes back as output the connection is owed a push for, the pane first as input's.
   - A cwd read inside a push, until the flood build: `get_current_working_dir(AllowStale)` for a pane whose terminal has no OSC 7 cwd goes to `ProcShared::list`, which asked the pane's job (`QueryInformationJobObject`, `ProcShared::count`) on every ask and, once the pane had printed since the last read, read the foreground's cwd on the main thread itself (`Refresh::ReadCwd`: OpenProcess, ReadProcessMemory), or on the pane's first ask walked every process there and then (`Refresh::Now`), all with the pane's terminal lock held: the getter is one expression, `self.terminal.lock().get_current_dir().cloned().or_else(...)`, whose guard lives through `or_else` (PITFALLS 85). Since the flood build a push asks `ProcShared::list(.., Ask::Listed)` after its read has let the terminal go: the cwd as listed, a stale one read by the `lbterm-procs` thread (`refresh_in_background` → `refresh` → `Next::ReadCwd`, paced by `lbterm_procs::wait`), whose change `tell` raises as CurrentWorkingDirectoryChanged; the count is asked only for `Ask::List` or a walk. Every other caller of `get_current_working_dir` is `Ask::Cwd`, as before, the getter's expression and all; a first ask still walks there and then. A title still 'wezterm' asks the list too, without the lock (`get_title` binds the title in a `let` first), and clones the foreground's `LocalProcessInfo`.
   - The server pushes every pane alike, in view or not, to a client that hasn't said what it shows: only the pane the connection last typed into (`lbterm_input_pane`) goes first, the rest in the order owed. It knows each mux window's active tab (SetFocusedPane → `remember_and_set_active_tab_idx`) but doesn't use it for pushes (PITFALLS 88). A window of perf/hidden-output's build says what it shows, and the server holds the rest (MUX.md, "Tabs out of view: output held at the server"): a window says the panes it shows with `SetShownPanes` (codec, PDU 7505; `ShownPane` each), which `process_one` notes in the connection's `Pending` (`set_shown`, `shows`, `says_shown`; the handler holds the `Pending` dispatch.rs uses, `SessionHandler::lbterm_pending`), and the server tells a window that knows it of a pane whose lines it holds with `PaneHeld` (7506). Its stage 2 built the server's side, all in `lbterm_flow.rs`'s `Pending` and `sessionhandler.rs`: a pane out of the set that a push has carried has its output held (`Pending::output_at` into `held`, no owe, no wake after the first), its alerts owed as before, a title or folder alert owing a push of them alone (`Owed::names`), and the hold's first output owing the word of it (`Owed::held`); `lbterm_push_pane` sends those through `PerPane::lbterm_out_of_view` (PaneHeld at the last push's seqno, only when the held output changed what a push carries, read with `lbterm_read_for_push` and no line copied, else the hold ends silently, PITFALLS 197; the names push from `Pane::lbterm_read_names`, the rest as last sent, or a real push, `OutOfView::Push`, when the read's size isn't the last push's, by `lbterm_same_size`, the size alone: PITFALLS 242). PaneRemoved drops all of it (`Pending::removed`). The window's side (stage 3) is in wezterm-client's `lbterm_shown.rs` and `domain.rs` (the client domain's mux subscriber marks, `lbterm_say_shown` sends the set; a reconnect's `reattach` asks each held pane's push again, `ClientPane::lbterm_reconnected`, PITFALLS 201), the client pane's hold (`renderable.rs`'s `lbterm_hold_from`, `lbterm_hold_ends`, `lbterm_hold_reconnected`) and the switch's wait for a held pane's push, which only the panes' room waits on (wezterm-gui's `termwindow/frame_wait.rs`, `lbterm_extras::frame_wait`): the client part below and "A tab switch". A shown pane's pace (What could go 12; MUX.md, "A shown pane's pace"; the second round's stage 4): a window that says which push of each shown pane its frames read (`PanesDrawn`, 7507, a notice at serial 0, answered with nothing, sent only where SetShownPanes was answered: PITFALLS 227) has `process_one`'s arm note it (`SessionHandler::lbterm_drawn` → `Pending::drawn`), and from then a round's push of a shown pane's changes leaves the pane waiting for the word (`lbterm_push_pane` → `Pending::pushed_changes`, `unread`), which `take_next` passes over (`passes_over`) and `owes` and the ring leave out (PITFALLS 228); alerts alone go, every push outside Pending goes, and input (`SessionHandler::lbterm_input` → `Pending::input`) lets the pane's round pushes go until a frame has read the first made since (its seqno kept in `input`, noted by `pushed_changes`: PITFALLS 235). The push log counts each push that waited and for how long (`lbterm_pushstats`' `waited`, `waited_us`). The window's side (the second round's stage 5): `RenderableInner::apply_changes_to_surface` notes each push applied in the pane's `Drawn` (wezterm-client's `lbterm_drawn.rs`, two atomics shared with `ClientPane`); `paint_pass` calls `TermWindow::lbterm_frame_read` for each pane it draws, before `paint_pane` (`ClientPane::lbterm_frame_read`: the flag, then the gate and the seqno), noting it in the window's `lbterm_read`, and `paint_impl`'s end `lbterm_say_read`, one PanesDrawn a server (`ClientPane::lbterm_say_drawn` → `Client::lbterm_panes_drawn` → `ReaderMessage::Drawn`, encoded at serial 0 by `client_thread_async`); `mux_pane_output_event` says a push of a pane it shows that no frame will draw soon at once (`lbterm_pane_shows`, upstream's `is_pane_visible` with a pane under an overlay told apart, and `lbterm_output_unpainted`: the Conductor's view, an overlay, `lbterm_unseen`), and the renderable a push with no PaneOutput (`RenderableInner::lbterm_say_drawn`); the client thread's `GateWatch` opens the gate at SetShownPanes' UnitResponse on its connection and shuts it at each connection's start (PITFALLS 227, 234).

   - The GUI runs a `LocalListener` on its own `gui-sock-<pid>` (`wezterm-gui/src/main.rs`): its connections run this same `dispatch.rs` and `sessionhandler.rs` on the GUI's main thread, each with a subscriber to the GUI's mux while it's open.
2. Client: `wezterm-client/src/client.rs`'s client thread reads each PDU and puts the unilateral ones (pushes, alerts, titles) into `lbterm_backlog.rs`'s queue, merging a pane's pushes into one. Past its `LIMIT` it stops reading the socket until the GUI thread has caught up, except while input waits on its echo or an answer. As FLOWS.md traced it (rows 42 to 52):
   - The client thread is unnamed (`Client::new`'s `thread::spawn`, so `metrics` lists it blank) and runs `smol::block_on(client_thread_async)`. It shares async-io's reactor with async-io 2.6's own `async-io` thread, and which holds it isn't known: the client thread lets it go whenever `react` returns with nothing for itself after holding it over 500 µs (every GUI timer's `Reactor::notify` after a wait), and the `async-io` thread takes it by itself (`driver.rs`'s `main_loop`: a `try_lock` when the reactor's tick hasn't moved since its last backoff wake, a blocking `lock()` after about 20 ms of quiet). While the `async-io` thread holds it, a socket event reaches the client thread as GetQueuedCompletionStatusEx there and an unpark, and the GUI thread's async-io timers fire there (PITFALLS 107; FLOWS.md row 43). Readiness is polling 3.11's IOCP backend: an IOCTL_AFD_POLL re-armed each wait, then GetQueuedCompletionStatusEx; each wait boxes its future (`wait_for_readable` is an `#[async_trait]` method on a `Box<dyn AsyncReadAndWrite>`). The GAP wait is an `async_io::Timer`, not wrapped in `counters::timer`.

Lines a remote pane hasn't fetched yet come through `renderable.rs`'s `poll()` and `schedule_fetch_lines()`; when `poll()` asks the server (GetPaneRenderChanges) is `pane/lbterm_poll.rs`'s `PollPace`: on a unix domain on its backoff alone, a resize or a zoom bringing it back, over TLS and ssh as upstream. As FLOWS.md traced it on main before perf/mux-client (rows 53 to 67), with what the branch changed said in each:

### A frame

1. Whatever changes what a window shows calls `window.invalidate()` (`window/src/os/windows/window.rs`, `invalidate()`). It's `#[track_caller]`, and `lbterm_extras::counters` credits each frame to the lines that asked for it, but only through a direct call: one made through `&dyn WindowOps` is credited to `invalidate()` itself.
2. `wm_paint()` may hold the frame back (`window/src/os/windows/pace.rs`, `lbterm_extras::pace`); the message loop (`connection.rs`) ends the holds on a high-resolution timer, and the window gets `WindowEvent::NeedRepaint`. ### Files and processes, off the GUI thread

Every thread a GUI starts and what wakes it at rest is AT-REST.md's table ("The threads and timers"), and what still wakes and whose is its "What still wakes, and whose". Every folder watch goes through `deps/notify/`, LBTerm's copy of notify 5.2.0 (`deps/notify/LBTERM.md`): its Windows watcher's thread waits with no timeout where the published one woke every 100 ms, a read that ends without its changes says so, and a watched folder's own name is watched in its parent.

Nothing on the GUI thread reads a file, walks processes or starts one: typing would arrive in bursts. A feature that shows what a file holds gets a thread of its own that watches it through `lbterm_extras::watch` (Windows' `ReadDirectoryChangesW`), reads it when it changes, keeps what it read behind a lock, and repaints the windows (`state_files::repaint_windows()`, or only the windows that show it). The paint reads memory. That's `inbox.rs` (the InMail folders), `state_files.rs` (the Conductor's state file, the tab links' file and the agenda's), `summaries.rs` (a change to a session's `usage.json` alone repaints only the windows showing its cost: the context pill's session, or a row of the open panel), `conversations.rs` (the scroll strip's transcripts, and the context pill's while its list is open, each window's readers kept apart by `Reader`), `thumbnails.rs`, `restart.rs` (the installed version) and `lbterm_extras::tasks` (subagents' transcripts). Each watch holds a handle on its folder and its folder's parent, which stops Windows renaming or removing any folder they're in; `let_go.rs`'s thread reads requests to let go of a folder, and `lbterm_extras::watch::let_go` has every watch in the process step out of it until it's taken back (LET-GO.md). A pane's working folder and foreground process come from the last walk of its process tree (`CachePolicy::AllowStale`; `mux/src/lbterm_proclist.rs`, `ProcShared::list`), walked again on an `lbterm-procs` thread only when the pane's job says a process started or ended that changes what it shows (`ProcShared::moved`, `lbterm_procs::walks_for`): each pane's program is put in a job of its own as the pane is made, and one `lbterm-jobs` thread a process waits on every job's completion port (`mux/src/lbterm_procs.rs`, `Watch`). A shell that doesn't say its folder (OSC 7) has its foreground's cwd read alone after it prints, in the ask. `lbterm::procs` at debug says every message, walk and read (perf/proc-title.ps1 and at-rest.ps1 count them).

The Conductor's hub and seat talk over named pipes on threads of their own: `conductor_hub.rs`, `seat_client.rs`. The control pipe is `control.rs` (the pipe) and `termwindow/control.rs` (what it asks of a window).

- What the perf scripts' tabs do sets what a run measures. `perf/mux-load.ps1`'s Claude-like tabs draw about 16 frames a second (`Thread.Sleep(50)` on Windows' 15.6 ms tick) in about 2.5 .NET console writes of up to 256 characters each, its burst tab about 65 strings a second in about 10 writes each, so ConPTY's writes and the server's reads come at 2.5 and 10 times the frame rate; its stand-ins say no cwd and some no title (PITFALLS 94). `perf/paint-cost.ps1`'s open tab prints a coloured line every -IntervalMs, each scrolling the screen, the case where main's line quad cache missed every row (PITFALLS 103); `perf/line-quads.ps1` scrolls a Claude Code-like region, a shell's screen and one line among blank rows a line at a time and holds that only the lines a scroll brings are laid out, that every line shows at its row, that the cursor, a selection and the link under the pointer on moved rows are laid out again, and that the screens match the same text drawn by another build (the installed one unless `-Reference` names one); its lone mode is the one that fails without the row folded into the hashes (PITFALLS 131). Real Claude Code draws neither way (PITFALLS 127): `perf/claude-output.ps1` runs it on a mux domain against a stand-in API and records its pane's reads, and `bench/pty-frames.ps1` says what each frame did. What `perf/sample.ps1`'s numbers and names mean: PITFALLS 95 to 98.

## Hot paths

What runs per key, per batch of output, per frame and per PDU, where anything added costs Lachlan something he can feel:

- Per pointer move over a pane: `termwindow/mouseevent.rs`'s `mouse_event_terminal()` (the link under the pointer, the cursor's shape) and `pane.mouse_event()`; on a mux domain `clientpane.rs`'s `mouse_event()`, which sends a move only to a program that has the mouse (`lbterm_mouse.rs`), through `mousestate.rs` (one `SendMouseEvent` in flight, the moves meanwhile merged) to the server's `SendMouseEvent` arm, a task on its main thread each: the terminal's `mouse_event` under its lock and a UnitResponse, with no push of the pane's changes after it (since perf/mux-client, which measured that at about 0.1 ms of the server's main thread a move).
- Per key: `keyevent.rs` up to `pane.key_down()`; on a mux domain, `clientpane.rs`'s `key_down()`, the server's `SendKeyDown` arm and its `compute_changes()`. A frame asked for before the echo, however it arrives (a key, a binding's text, a composition's end), holds the echo's frame a pacing period (PERF.md, finding 35).
- Per batch of output: the parser thread (`mux/src/lib.rs`), `lbterm_output.rs`, the GUI's `mux_pane_output_event_callback()` and `dispatch_notif()`; on a mux domain also `lbterm_flow.rs`, `lbterm_push.rs`, `lbterm_backlog.rs` and `renderable.rs`. On Windows each ConPTY write is a read: the reader's ReadFile and its loopback TCP send to the parser, the parser's recv, its WSAPolls and coalescing timer (`lbterm_wait.rs`), the model under the pane's terminal lock, and `spawn_into_main_thread`'s two process-wide mutexes and two allocations, the wake's syscall made inside ON_MAIN_THREAD (PITFALLS 94 and 108; FLOWS.md rows 1 to 18).
- Per push, on the server's main thread: the subscriber and its ring, the round's `read_now` recv a pane, `compute_changes`' terminal locks (which the parser contends with: nine until perf/mux-client's flood build, two since, and none for an owe of alerts alone that don't read the push), `lines_to_send`'s clones, `SerializedLines::from`'s rebuild of every cell, and the encode's three Vecs and zstd. In the GUI, per PDU on the client thread: the decode (every line built from cells, the cwd's Url parsed) and the backlog's hand and merge; per push on the GUI thread: applying its lines (`put_line`, which scanned every line it carried for links until perf/mux-client, which scans a line as it's drawn), and for a pane in the open tab `Mux::notify` and the notice's two task hops a window (a pane out of it stops at `lbterm_hidden_output`, no task) (FLOWS.md rows 19 to 67).
- Per frame: `paint_impl()` and everything `paint_pass()` calls, `composited.rs`, `compositor.rs`'s `prepare()`, and the budget's and state file's per-frame hooks. Work on a pane's rows stays out of its `with_lines_mut`, which holds its terminal against its parser: copy what's needed (`render/pane_lines.rs`) or read what's cheap (PERF.md, findings 37 and 69). On a mux pane: its rows lent where the client holds them and copied only when changed, each row's shape key kept on its line (before perf/mux-client, three copies of each visible row and its shape hash every frame), the whole layer uploaded when anything in the pane moved, and a poll only on its backoff (FLOWS.md rows 68 to 105). Every visible row's quads are copied into its layer every frame, as one block a line moved to its row (`HeapQuadAllocator::lbterm_apply_moved`); a line is laid out again only when what it shows changes, not when it moves (since perf/line-quads-by-content, which took a scroll's layout of every row, a Box a quad and an eviction a row out). Anything a line's layout reads from its row must be in the line quad cache's key or drawn apart (PITFALLS 128).
- Per size a window takes: each pane of each tab that takes it resized (only the tab in view during a drag of the frame), and on the server each pane's whole scrollback fitted to the new width, about 25 ms a pane of 50,000 lines since perf/mux-client (72 before), on a `lbterm-resize` thread of its own; a pane of the window's own is still rewrapped on the GUI thread (FLOWS.md, "A window's resize on a mux domain").
- At rest: nothing. A thread named `lbterm-*` that wakes at rest fails `lbterm/perf/at-rest.ps1`.

Something new on one of these paths is measured before and after with the same script (the counters and the budget runner), with no lock, allocation, file read or process walk added per event in the daily build. PITFALLS.md has the traps reviews found there.
