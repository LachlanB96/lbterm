# Tabs that outlive the GUI (the mux domain)

With the mux domain on, LBTerm's tabs don't live in the window's process. They live in `lbterm-mux-server`, and the GUI attaches to them over a socket, as `wezterm connect` does. When the GUI dies (a crash, a GPU driver update taking the window, the process killed, `lbterm.ps1 restart` after an install), every tab keeps running, Claude Code included, and the next LBTerm attaches to them where they were.

Closing a window, or quitting, still ends its tabs. That's LBTerm's own choice: WezTerm detaches instead, leaving everything running in the background. A reboot ends the server and its tabs; crash restore (`RESTORE.md`) offers them again then.

## Turning it on

It's in the config, not the build. Lachlan's `Terminal\lbterm\lbterm.lua` has `MUX = true`, which comes to:

```lua
config.unix_domains = { { name = 'unix' } }
config.default_gui_startup_args = { 'connect', 'unix' }
```

The GUI then starts by connecting to the `unix` domain, starting `lbterm-mux-server --daemonize` beside its own exe at once when nothing answers on the socket and no server holds it (Starting the server, below). The server reads the same config and listens on the domain's default socket, `~\.local\share\lbterm\sock`, which `lbterm.ps1 install` and `restart` assume. Changing it takes an LBTerm restart, and that ends the tabs it had.

## What LBTerm changes to make it work

Upstream WezTerm has the mux. These are the gaps that mattered for LBTerm's setup:

- **Closing ends the tabs.** `Mux::remove_window_internal` no longer detaches the window's domains, so each of its panes is killed, and `ClientPane::kill` sends the kill to the server. It holds an `Activity` until the server has it (at most 3 s), because the GUI exits once the mux is empty and no Activity is held. Quit (`frontend::quit_application`, from QuitApplication with or without its prompt) closes every window first, then ends the message loop when those kills are done. `DetachDomain` still detaches.
- **A GUI that attaches opens its windows where they were** (2026-10-25, after a restart came up on another screen at another size and went unresponsive). Upstream sizes a new window for its tabs and lets Windows place it; on a screen too small for it Windows cut it down, and every tab's program, nine Claude sessions, redrew at the new size, then again when Lachlan put the window back. Each window's Windows placement is kept by its server window id (`window-<id>.txt` in `~\.local\share\lbterm\placement`, `lbterm-extras/src/placement.rs`, `wezterm-gui/src/placement.rs`), and the new window is made on that screen and shown at that place (`Window::lbterm_keep_placement`), so the tabs keep their size.
- **The server ends with its last tab.** `lbterm-mux-server` exits a second after its last pane has gone, so a closed LBTerm leaves nothing running, and the next one starts the server from the build installed now.
- **A GUI that attaches gets what the panes already have.** The server only sends changes, so a reattached pane used to have no user vars (claudehook's `claude_status` and `claude_session`), no OSC 9;4 progress and no OSC 7501 records until each next changed. The first time a client looks at a pane (`sent_initial_state` in `wezterm-mux-server-impl/src/sessionhandler.rs`), the server sends its user vars, progress and records ahead of anything else.
- **A shell's prompt rows cross the socket, not its scrollback.** The scroll strip marks each prompt in a pane's scrollback (lbterm/SCROLL-STRIP.md, "A shell's marks"), and the GUI holds only the lines it has drawn. It asks the server which rows hold a prompt (`GetPromptRows`, PDU 7503; `GetPromptRowsResponse`, 7504, the rows alone), where until 2026-10-31 it fetched every line of the scrollback for them. Additive like the rest: a server of an older build answers ErrorResponse naming the PDU it doesn't know, which the GUI says once in its log, and marks only what it has drawn; any other error is asked again a second on.
- **OSC 7501 crosses the socket.** `Alert::ProgramStatus` only says the records changed, and only a local pane can read them. The server now sends the records themselves in `SetProgramStatus` (`codec/src/lib.rs`, PDU 7501, numbered well clear of upstream's), and `ClientPane` keeps them for `get_program_status()`, so the tab panel and Lua see them. The protocol change is additive, so `CODEC_VERSION` stays upstream's: a peer that doesn't know the PDU decodes it as `Pdu::Invalid`. Which ends the connection when the peer is a window: wezterm-client's `process_unilateral` bails on a unilateral PDU with no pane it knows how to hand on, so a window of a build before 7501 would have ended its connection at the first status record (read from the code, 2026-11-08: no window that old is left to try). A server answers a request it doesn't know with ErrorResponse and goes on (PITFALLS 188).
- **Parked tabs** (Lachlan's 8a, 2026-11-09; NEW-TAB.md, "Landing 4"). A tab's parked flag (`Tab::lbterm_parked`, an atomic beside its title in upstream's `mux/src/tab.rs`) is kept where the tab's panes are: in the server for Lachlan's tabs, so every window and a GUI started again see it, and it ends with the tab. Three PDUs carry it, from 7508 (codec): `GetParkedTabs`, answered with `ParkedTabs { tabs }` (every parked tab of the server's), and `TabParked { tab_id, parked }`. A window's client domain asks `GetParkedTabs` after each listing of the panes (attach, reconnect, resync: the end of `process_pane_list`, `ClientInner::lbterm_ask_parked`) and sets its local tabs from the answer (`lbterm_parked_tabs`, the tab map copied out before any flag is set, since a set notifies); the server notes that the connection asked (`lbterm_flow::Pending::asked_parked`) and from then pushes it every `LbtermTabParked` as a `TabParked` (dispatch.rs, `notification_pdu`), which the window's client thread hands on by its kind (`process_unilateral`) and applies on the GUI thread (`ClientDomain::lbterm_remote_tab_parked`). A window parks a tab of the server's by sending `TabParked` (`ClientDomain::lbterm_park`, from wezterm-gui's `park.rs`) and never sets its own copy: the server's push back sets it, as it sets every other window's. Set locally as well, a park and an unpark in quick succession would each come back after the window had moved on and set it again, and each set sends again, a loop with no end (PITFALLS 159, 250). A domain whose server answers `GetParkedTabs` with an error naming 7508 (`codec::lacks_parked_tabs`: a build from before 8a) can't park (`ClientDomain::lbterm_can_park` false), so its tabs' menus have no Park tab and the action logs and does nothing; an older window never asks, so it's never pushed a `TabParked`, which would end its connection (PITFALLS 188). Beside its socket the process holding the tabs publishes `<socket>.parked.json`, `{"pid":N,"panes":[...]}`, its ids of every pane in a parked tab, for Terminal's statusline (mux's `lbterm_parked.rs`; claudehook's `statusline` verb, which serves the last line while nothing it reads has changed, has the file's modified time in what it compares, so a park shows in the box at the next run; FLOWS.md, "A park", step 11): the server writes it empty as it starts serving (so a crashed server's file never names the next one's panes) and again whenever the list changes; a GUI writes `gui-sock-<pid>.parked.json` only once one of its own tabs (not a mux domain's) has been parked. Its mux subscriber only notes that the list may have changed (a park or unpark, and while the file names a pane, a pane added or gone, a tab added, resized or a window gone) and queues one task on the main thread, which works the list out and hands it, when it differs from the last, to a thread of its own (`lbterm-parked`, idle on a channel; AT-REST.md) that writes it through a rename, retried for 250 ms while a reader holds the file (a write that still fails leaves the next look to write its list whatever it is; PITFALLS 256). A GUI's file goes with its socket: upstream's sweep of RUNTIME_DIR (every GUI's update checker, 10 s after it starts and daily) counts only `gui-sock-<pid>` as a socket and takes a `gui-sock-<pid>.<more>` beside one once the socket's gone (wezterm-client's discovery.rs; until the review's fix-up it deleted the live GUI's own file, PITFALLS 254). A split in a parked tab, a pane closed in one and a parked tab closed all change the file. Crash restore keeps it: the GUI's note records each tab's `parked`, and a tab it reopens from a parked note is parked again once it's open, asked of its server as any park is (NEW-TAB.md, Landing 4's 8a; RESTORE.md). The side buttons' hops read the flag at the press, on the GUI thread, from each window's mirror of it (`LbtermTab`, NEW-TAB.md's 9a), and Terminal's statusline.ts reads the published file (its `parkedHere`).
- **A window the server hangs up on reconnects.** Upstream never reconnects a unix domain: its connection only ends when the server dies, so it detaches, every pane leaves the window and the GUI exits. LBTerm's server can drop a GUI it still has tabs for: on 2026-10-23 the PC hit its commit limit four times in 25 minutes, the daily server (a build from before the zstd fallback in `codec`) failed a PDU encode each time and hung up, and the window closed with all 22 tabs while the server and the tabs ran on. Now the GUI's client thread (`after_disconnect` in `wezterm-client/src/client.rs`) tries again after any error, EOF included, without the connection window upstream shows (it would come up in front): a second's wait, doubling to 10 s, up to 8 tries, about a minute in all. Its log says `Reconnected!`, `ClientDomain::reattach` says who it is again (SetClientId, or `list-clients` would leave it out) and which pane has focus, and lists the panes. The tabs stay in the window throughout, input waits in the queue. Only when no server has answered 8 times does it give up, detach and close, as before. A cli connection never reconnects. The fix is the GUI's: it holds for a server of any build, the running one included.
- **A tab's environment** (2026-11-09). A pane's environment is the environment of whichever process built its command, sent whole in the spawn request (`pty::CommandBuilder` reads its process's environment as it's made, and the server spawns with the builder's entries as they came): `lbterm cli spawn -- <program>` gives the tab the cli's (so its caller's), a GUI spawn with a program, a folder or variables (`SpawnCommand` with `args`, `cwd` or `set_environment_variables`: the new-tab pad, crash restore, Lua's `spawn_tab`) gives it the GUI's, and only a spawn with none of those (`cli spawn` with no program, a plain new tab) leaves it to the server, which builds the default program from its own. So a variable taken out of the server alone (`mux_env_remove`, applied once at its start) misses most tabs. What no tab should inherit is taken out by each of the three as it starts, in `env_bootstrap::bootstrap` (`config/src/lbterm.rs`, `DROPPED_ENV`): Windows' `__COMPAT_LAYER`, which the Program Compatibility Assistant gives a GUI it has flagged when Explorer starts it, and which headless Edge relaunches itself on, its output lost. A running server took the list in at its own start, so it goes on giving its plain new tabs what it had until it restarts.
- **The server's pane ids, in Lua.** A pane's `WEZTERM_PANE`, and the ids `lbterm cli` inside it uses, are the server's. `pane:pane_id()` in the GUI is the GUI's own number for the pane, and differs. `pane:get_metadata().remote_pane_id` is the server's (nil for a local pane). Terminal's summary pane names its files by it.

- **The server keeps its socket** (2026-10-30, after a test's mux server took the daily one). Upstream binds a server's socket by removing whatever file is at its path first, so a second server started on a live one's path takes it: at 23:57 on 2026-10-29 a test's server whose config failed to load fell back to the default domain, took `~\.local\share\lbterm\sock` from Lachlan's daily server and then ended with its test, leaving a dead file there, so nothing new (the cli, the Conductor, a new window) could reach his tabs until the server restarted. Now a server never binds a path another server answers on (it says so and exits), and the server watches its socket's file every 3 s by its file index (not its creation time, which NTFS gives back to a file made again under the same name within 15 s): a file that's gone or another one is bound over again, with a listener of its own, so an older build's server that takes the path cuts the daily one off for seconds at most (`wezterm-mux-server-impl/src/local.rs`, `keep_socket`). And a server told which config to run (`--config-file`, as every test's is) won't start when that config fails to load, rather than carry on with the defaults, whose domain is the daily one; the daily server, started without it, still falls back as upstream does, so a broken `lbterm.lua` can't keep LBTerm from starting (`wezterm-mux-server/src/main.rs`). The test harness fails a test during which the daily socket's file is made again (`Invoke-Test`, `Get-SocketStamp`).
- **Starting the server** (2026-10-31, finding 25 in `PERF.md`). Upstream's client tried the socket ten times, 50 to 450 ms apart, before it started the server, in case one was on its way up, so LBTerm opened from nothing (after a login, or once the last window had closed) waited 2.25 s for a socket nobody was going to answer: its tab came 2.75 to 2.8 s after its process started, against about 1 s for a window with tabs of its own. On Windows a connect can't say a server is on its way: no file and a file nothing listens on are both refused at once, and a live listener takes every connect, its backlog full or not. So two named mutexes of the socket's path say who is there (`mux/src/lbterm_serve.rs`, named by a hash of the path in `config/src/lbterm.rs`, `mux_socket_lock`):
  - **`serving`**, the server's: claimed just before it binds the socket and held as long as it runs (`spawn_listener`, on its main thread; a process that ends lets go of it). A second server for the same socket refuses to start (`another mux server is starting or running at <path> ...: not taking its socket`), even when both are starting before either has bound, where two would each take the socket back from the other every 3 s (`keep_socket`). The server holding it also says its process id in a named section of its own beside it (`Local\lbterm-mux-pid-<hash>`, `config::lbterm::mux_server_pid`), held as long as the claim and gone with the process, so nothing can outlive it and name another: a mutex can't say who owns it, and a refusal names the pid that serves (since 2026-11-01, the review of perf/key-latency).
  - **`starting`**, a client's: held by a first connect that may start the server (a GUI attaching, a `cli` call without `--no-auto-start`) until it has connected, so two windows opened together start one server and the second waits for the first, then finds it up (`lbterm::serve` says how long it waited).

  The client tries the socket once (`wezterm-client/src/lbterm_start.rs`). Refused while no server holds `serving`, none can be listening, so it starts one at once, and tries the new server's socket every 10 ms (upstream waited 200 ms and then 50 to 450 ms between tries) for up to 2.45 s, what upstream's tries after a start came to. Refused while a server holds it (its file removed or taken, which it binds again at its next look), it waits for that server, every 50 ms for up to 7 s, and never starts a second over it; if the server lets go meanwhile, it starts one. One that holds it and never answers (hung on its way out, its listener gone) fails the client out loud after the 7 s, naming that server's pid and whether it still runs, for Lachlan to end (`the mux server with pid <n>, still running, holds <socket>, and hasn't answered on it in 7s ...: end that one and open LBTerm again`): only he ends a daily server. A reconnect, `--no-auto-start` and a domain with `no_serve_automatically` go as before. The names and waits are in `config/src/lbterm.rs` (`MUX_START_WAIT`, `MUX_SERVED_WAIT`, `MUX_STARTING_WAIT`). What a client can't see is a server started by hand that hasn't loaded its config yet: a GUI starting then starts its own too, and the one that claims the socket second refuses and exits, so one serves. A server from a build before this claims nothing, so a GUI of this build next to one that's alive but not answering (not seen) would start its own as before, which still won't take a socket that answers. A start's tab on a mux domain now comes 1,046 and 1,060 ms after its process starts at the median, against 2,752 to 2,761 before and 906 to 962 for a window with tabs of its own (`PERF.md`, "A cold start, after perf/key-latency").

- **Tabs out of view: output held at the server** (perf/hidden-output, from 2026-11-08; FLOWS.md's pane-output flow, What could go 2, which Lachlan decided on 2026-11-04 with his 10a and 11a). The server works out and sends a pane's lines only while a window shows it. Why: since perf/mux-client the window takes every push as it comes, so the server's main thread does 1.2 to 1.25 times the installed build's work a line under a flood with the floods out of view and 1.35 to 1.4 times with one in view (FLOWS.md, Run 10), and nearly all of a server's push work is for panes out of view: 472.7 of its 473.7 ms a second of pushes under mux-flood's flood, 113.7 of 114.9 under mux-load (Run 6). This is the design, written before any of it was built; "Built so far", at its end, says what is.
  - **What the window says.** `SetShownPanes` (codec, PDU 7505): the whole set of panes it shows, in place of the one before. For each mux window of the GUI's active workspace (the ones a GUI window draws), its active tab's panes of this domain (a zoomed tab's zoomed pane alone), as the server numbers them, each with `drawn`, which is always None: a frame's word goes in a PDU of its own ("A shown pane's pace", below). The whole set rather than what changed, so a lost, repeated or late one leaves nothing half said and the server keeps no history.
  - **When it says it.** At the switch, not at the new tab's first frame, where `advise_focus` sends SetFocusedPane (FLOWS.md row 75), which stays as it is: it moves the server's own active tab, which ListPanes reports and a reattach restores, and is the same for every client. The client domain's mux subscriber in the GUI (`mux_notify_client_domain`, wezterm-client's `domain.rs`, on the GUI thread) hears every change of what a window shows: WindowInvalidated (a tab switched, `Window::set_active_tab_idx_without_saving` → `invalidate`; a tab added, removed, moved, or pruned as it closes), TabResized (a zoom or unzoom, `Tab::set_zoomed`; a split; a pane of the tab closed), TabAddedToWindow (a new tab, a pane moved to a tab of its own), WindowCreated and WindowRemoved, PaneRemoved, and ActiveWorkspaceChanged. It works nothing out inside the notification: `Mux::notify` calls its subscribers under the subscribers' write lock, and `invalidate` runs with the window's write guard held, so a `get_window` there would wait on itself (upstream's WindowWorkspaceChanged arm defers for the same reason). It marks the domain and queues one GUI-thread task, once until it runs, which works out the set and sends it only when it differs from the last one sent on this connection. That task runs in the same turn of the GUI's loop as the switch, ahead of the paint the switch asked for, so the server hears of it while the window prepares the frame.
  - A new window says its tab's panes as it's made, a closed tab the tab that takes its place, a moved pane the window it lands in. A minimized window still shows its active tab: nothing is said at minimize or restore. Holding that tab too would save one tab's pushes among Lachlan's 8 to 18, the restore would then need the switch's wait, and the client domain would have to hear a GUI window's state, which it doesn't today. A covered window, a locked PC and screens off are the same. Kept as built: Lachlan's 4a of 2026-11-08 (perf/mux-hidden.ps1's step 7 measured it: the minimized window's busy tab pushed alone, 9.3 a second, and its first frame after the restore current with no wait).
  - After each connection: the server starts every connection at "not said", so once a connect or reconnect has mapped the server's panes to the window's (`resync`), the set is said on the new connection, whatever was said on the last.
  - It goes through the client's rpc from a detached task, which keeps the answer's receiver until the answer comes: a dropped receiver detaches the whole domain (PITFALLS 171). The answer is UnitResponse. A server that doesn't know the PDU (an older build) answers ErrorResponse naming `Invalid { ident: 7505 }` (`codec::lacks_shown_panes`), and the window says no more on that connection and no switch's panes wait for a push (below). Any other failure (the connection lost) is followed by the next set said.
  - **What the server holds.** Per connection, in `lbterm_flow::Pending`, which the connection's mux subscriber, its loop and its SessionHandler share (`SessionHandler::lbterm_pending`): `shown`, None until the window says (the cli, an older window: every pane is pushed as before, `Pending::shows`), else the set (each pane's `drawn` isn't kept: "A shown pane's pace", below). Per pane, as built (stage 2): `pushed`, the panes a push has carried to the client, which alone can be held (`Pending::current`, below); and `held`, each pane held with when it last printed (its quiet deadline, below), kept apart from `owed`, so a held pane isn't in the round's order at all and none of its output after the hold's first wakes the connection (`Pending::output_at`). ## Living with it

- **Installing.** A running GUI and server keep their files open. `lbterm.ps1 install` renames each in-use file aside (`<name>.<stamp>.old`, deleted by the next install once nothing holds it) and copies the new one in. The running GUI and server go on with the old build. `lbterm.ps1 restart` kills the GUI and opens the installed one, which attaches to the same tabs. It refuses when the GUI has tabs of its own outside the server (started without the domain), since those would end with it. Install also writes the build's version to `version.txt` and keeps the build it replaces whole in `%LOCALAPPDATA%\Programs\LBTerm-previous`; `lbterm.ps1 rollback` swaps the two and restarts the GUI into the kept one, checking first that it speaks the running server's protocol.
- **The server keeps the old build** until its last tab closes: changes to the terminal itself (escape sequences, OSC 7501, triggers' matching) reach existing tabs only then. GUI changes (drawing, the tab panel, keys) take effect at `restart`.
- **Protocol changes.** An upstream merge that bumps `CODEC_VERSION` makes the new GUI unable to talk to a running older server. `install` checks for that with the new `lbterm cli` against the running server, and refuses: close LBTerm (which ends its tabs) and install again.
- **The cli.** Inside a pane, `WEZTERM_UNIX_SOCKET` is the server's socket, so `lbterm cli` there works on the server, with the server's pane ids. A `cli` call without `--no-auto-start` from where no server is running starts one, with a tab of its own, which the next LBTerm then shows.
- **From outside a pane** (another program, a hook, Claude's shell), set `WEZTERM_UNIX_SOCKET` to the server's socket, `~\.local\share\lbterm\sock`, and run the installed cli, `%LOCALAPPDATA%\Programs\LBTerm\lbterm.exe` (where `lbterm.ps1 install` puts it), always with `--no-auto-start`: `lbterm cli --no-auto-start list --format json`. LBTerm is open when an `lbterm-gui` runs from that folder and the server answers. Never a `gui-sock-*` beside the socket: those are each GUI's own, with the GUI's pane ids, and a GUI that died leaves its file behind. `list-clients`' `focused_pane_id` is what a GUI last reported; with more than one, take the least idle. Where Lachlan is right now is the control pipe's `focus` (`CONTROL.md`), which asks the window itself.
- **Crash restore** asks once the domain has attached (never over the connection status the window shows until then), 2 s later when it found panes running in the server, and offers only the noted tabs that aren't live (matched by `claude_session`, then by folder). After a GUI-only restart that's none; after a restart that ended the server too, it's all of them (`RESTORE.md`, "When it asks").

## Checking it

`pwsh -File lbterm\perf\mux.ps1` runs all of it in test windows of their own class, on a domain and socket of their own (`target\perf\mux`), so the real server is never touched: a Claude-ish tab's user vars, OSC 7501 record and progress reach the GUI; the GUI is killed and the server keeps both tabs; a new GUI shows them with all of that again (`mux-reattached.png`) and offers no restore; WM_CLOSE ends the tabs and the server; a third GUI's QuitApplication does the same. The OSC 7501 PDU's encoding is tested in `codec` (`lbterm_program_status_round_trip`).

`pwsh -File lbterm\perf\server-start.ps1` starts the server in test windows of their own class on a socket of their own (Starting the server, above): with no socket file and with a killed server's file, the GUI starts it at once (its log's `Will try spawning the server` within 1.5 s of its process starting) and the server has its one tab; two GUIs started together start one server, the other saying it waited; a GUI opened while a live server's socket file is gone waits for that server and starts none; a server started by hand as a GUI starts its own leaves one serving and the other refusing, naming the pid of the one that serves; a server held still (its socket file removed, so it can't bind it again) has a GUI opened then give up after 7 s naming its pid, still running. The locks are tested in `mux` (`lbterm_serve`) and the client's tries in `wezterm-client` (`lbterm_start`).

`pwsh -File lbterm\perf\mux-reconnect.ps1` has the test server hang up on its GUI (`LBTERM_TEST_HANGUP` names a file; the server takes it and drops that connection, `wezterm-mux-server-impl/src/dispatch.rs`; nothing sets it for Lachlan's server): the window must stay, log `Reconnected!`, show the server's panes, be in `list-clients` again and get a tab made after it (`mux-reconnected.png`); then, the server killed, give up within about a minute and close. What reconnects and what doesn't is tested in `wezterm-client` (`client.rs`, part of the check). Its `update-status` handler sets an empty right status every time: without that the event doesn't come again on its interval, and the test once failed for that alone, on every build (lbterm/PERF.md, finding 71).

`pwsh -File lbterm\perf\mux-load.ps1` measures a busy domain: -Claude tabs drawing as a working Claude Code session does and -Burst tabs printing forty lines every 5 ms, behind a tab in view that echoes the keys posted to it, all in a test server of its own. Over -Seconds it reads the server's CPU, main thread, page faults and memory, the window's, and each key's time to the frame showing its echo; -Count does it again with `codec=debug` logs and counts the PDUs and bytes each side sent. It stops when the window or the server passes -MaxMemGB (2 GB) of private bytes or working set, read every 200 ms on a timer of its own (the harness's `Start-MemoryGuard`), as a client that can't keep up let a server grow to 29.5 GB on 2026-10-29. `-ServerBin` and `-GuiBin` (a build's folder, or `installed` for a copy of the daily LBTerm's) run another build's server or window against this one, which must still echo every key and show every tab: the e2e runner does both against the installed build. What a PDU costs is held by `codec/tests/lbterm_codec_cost.rs`, part of the check, which fails when encoding or decoding a push takes page faults (a zstd context made for it again) or when frames that came together take more than one read.

`pwsh -File lbterm\perf\mux-flood.ps1` floods a domain of its own past what its window can take: -Flood tabs (six) printing 200-line blocks and a title each without a pause (`-Kind alerts`: 200 user vars a block) behind a tab in view that echoes the keys posted to it, with 5,000 lines of scrollback (`-Scrollback`) and without the scrollbar and scroll strip (`-Marks` keeps them), every 200 ms both processes' memory and CPU, and a guard that kills both at 2 GB. Then the window's GUI thread held 3 s; six times a key into the echo and the GUI thread held 600 ms while the server switches the window to a flooding tab and straight back, where the window must end on the echo, as the server does; a flooding tab in view (frames, and the age of the newest line the window holds); every tab stopped on a state of its own the window must end with; and three times every tab, out of view, writing a screen of characters that hardly compress and a title at the same moment (one event they all wait on), which the window's rail must show within 5 s, read from the state file alone so that no request wakes the server's connection (a cli call to the window or the server would, and let a push it held go). It fails on 150 MB of the server's growth or 250 of the window's, 3 MB a second over the flood's second half, an echo over 250 ms at the 95th percentile or not shown in 5 s, a switch the window doesn't end on the echo, under 20 frames a second or lines over 500 ms old in view, a last state not reached in 30 s, or a screen written together not shown in 5 s; a build with the window's counters has them saved for the flood and the view. Its variants run the installed server and the installed window against this build with `-Compat`, two tabs for 10 s, judged on the echo, the switches, the last state and the screens written together alone. What decides it is tested in `wezterm-mux-server-impl` (`lbterm_flow.rs`: the connection's rounds as `dispatch.rs` runs them, against sockets that take everything at once or a few bytes at a time, every push owed going out with no news after it), `wezterm-client` (`lbterm_backlog.rs`: merged pushes leave a window as each in turn would, 3,000 random runs, and only the typed pane's pushes go ahead of the rest), `mux` (`lbterm_output.rs`) and `codec` (`read_now`).

`pwsh -File lbterm\perf\mux-push.ps1` measures what a push, a key's echo and a pane cost, each part in a test server of its own: `echo` (keys posted to an echoing tab, each timed to the frame showing its echo; -Local in the window's own domain; -Frames lists every frame after each key), `history` (the echo and two tabs printing a line every 10 ms, all with 50,000 lines of scrollback: the server's CPU and main thread), `memory` (ten idle tabs: the server's private bytes for each), `sendtext` (50 `cli send-text` calls: what was pushed to each before its answer, from the cli's `wezterm_client=debug` log, and the main thread's time), `spawn` (tabs spawned and killed beside the echo from a thread of the test's: the echo then, and the main thread's time for each) and `flood` (the echo beside a tab printing without a pause; -FloodColour, every word coloured). It stops a part at 2 GB in the window or the server (`Start-MemoryGuard`, every 200 ms), and fails on an echo that doesn't show, over 40 ms at the median, an idle tab over 4 MB, anything pushed to a send-text, or over 35 ms of the main thread a spawn and kill. The e2e runner runs all of it, and the echo again in the window's own domain held to 15 ms at the median (the parser's wait on Windows' tick made it 22).

`pwsh -File lbterm\perf\mux-hidden.ps1` measures what tabs out of view cost the window and what a switch to one shows ("Tabs out of view", above), in a test server of its own, the window drawn as Lachlan's with his hyperlink rules: -Busy tabs (six) out of view, each a Claude-like stand-in on the alternate screen, a line of its answer with a URL and a path every -EveryMs (100) scrolling the conversation and its status block redrawn, behind a quiet tab in view. The window's GUI thread over a quiet span and over -Seconds of the tabs working, with the pushes its counters took, so the GUI thread a push; each busy tab brought into view by a key while they all work, timed to the first frame that draws it; the GetPaneRenderChanges the window sends while the tab in view prints ten lines a second; then each busy tab stopped on a screen of its own, every line a URL and a path, and brought into view by a key in turn 2 s later: the first frame that draws it with its cursor where it was left (the state file's drawn_cursor, frame by frame from the recorder), any frame drawing it elsewhere before, the window's own time and its GUI thread's for the switch, the lines the window then holds of it against what it wrote, its URLs as links there (`cli get-text --escapes` from the window's own socket) and the lines it fetched. It fails over 400 µs of the GUI thread a push, over 12 polls (the backoff's are about six), on a stale or wrong screen, a URL that isn't a link, a fetch, a switch over 60 ms to its first right frame at the median, or a switch to a tab at work over 80 ms to its first frame. Its switches vary by tens of milliseconds from run to run, so a difference of a few is told only over many runs. What decides each part is tested in its crate: `wezterm-client`'s `lbterm_poll.rs` (a unix domain's pane printing is polled on the backoff alone, TLS's as upstream, a resize brings the poll back on either, unanswered input is late after 3 s) and `lbterm_renderable_test.rs` (a line is scanned only when its row is asked for, once until it's replaced, a line drawn while it's fetched again is scanned too), and `lbterm-extras`' `hidden_scan.rs` (a pane out of view is due once it has been quiet 250 ms, a busy one never, one timer at a time).

`pwsh -File lbterm\perf\mux-gui.ps1` measures the window's own side of a mux pane ("A frame of a pane on the mux domain", "Lines read and made stale", "The pointer over a pane", "A write to a pane"), each part in a test server of its own, the window drawn as Lachlan's: a screen of colour text and a spinner in a mux pane and in the window's own (the GUI thread a frame, `paint_pane.lines` and the rows whose shape key was kept, from metrics); pointer moves over a shell's pane, over a program with the mouse across its cells and inside one (the SendMouseEvent sent, the server's main thread, the reports the program read); SendString keys and letters into an echo with two tabs flooding behind it (what each WM_KEYDOWN held the GUI thread), and a letter and a SendString key with no gap, read back in order; a tab in view printing long lines (the GetLines sent); three tabs after 20,000 lines each and the window four columns narrower and back (what WM_WINDOWPOSCHANGED held the GUI thread). What decides each is tested in `wezterm-client`: `lbterm_lent.rs` (a frame is lent the lines held where they are, and what it leaves on one stays; reading a row leaves each entry as `get_lines` does, the same rows fetched; a line newer than the pane is fetching, so its fetch is taken), `lbterm_renderable_test.rs` (every line made stale where it is, the cache's size and order kept) and `lbterm_mouse.rs` (a move goes only to a program that has the mouse; presses, releases and the wheel always).

`pwsh -File lbterm\perf\mux-resize.ps1` resizes a window whose twelve tabs each have 50,000 lines of scrollback ("A window's resize", above): a drag of its frame through 40 sizes, then 30 columns narrower in one step and back, each timed to a key's echo and to every pane at the window's size on the server and in the window, with the server's main thread, the PDUs and the longest the window went without taking a message. `pwsh -File lbterm\perf\mux-throughput.ps1` times output at full speed in the tab in view on a mux domain, beside tabs flooding out of view with -Behind, and with -Local in the window's own tab, and how long the window went without taking a message ("Output at full speed", above).
