# Colour codes

A `#RRGGBB` colour code in a pane's text is shown with its colour: a bar in the code's own colour along the foot of the code's cells, from its `#` to its last digit, about 2 px at 96 DPI. Every character stays in its cell and stays as it is, so nothing moves, copying gives the text the program printed, and a link over a code still opens. On by default; `lbterm_hex_colours = false` turns it off.

Asked for on 2026-11-09 ("LBTerm should be able to show the hexidecimal colours when it is shown like #FFBF00"). A swatch beside the code was the first pick, from a mockup that pushed the text along to make room; a terminal's grid keeps every character in its cell, so the bar under the code (option c of the four that keep the grid) is what was built.

## What counts as a code

`#` and exactly six hex digits, either case, standing alone:

- not after a letter, digit, `#` or `&` (so `abc#FFBF00`, `##FFBF00` and the HTML entity `&#x27` aren't codes);
- not followed by a letter, digit or `_` (so `#FFBF00AA`, `#1234567` and `#FFBF00_x` aren't);
- six digits, never three: `#fff` isn't one.

So `#FFBF00,`, `(#8a8a9e)`, `color: #F2E86D;` and `#ffbf00` at a line's start or end are. A letter here is a letter of a script that puts spaces between its words, so a code glued to a word in Latin, Cyrillic, Greek, Korean and the like isn't one. A letter of a script written without spaces doesn't count (Lachlan's 7b of 2026-11-10): Han, Hiragana, Katakana (full and half width), Bopomofo, Thai, Lao, Khmer and Myanmar, by their Unicode blocks (`hex::spaceless`). There nothing but the sentence going on stands between a word and a code, so `颜色#FFBF00`, `いろ#00FF00です` and `สี#FF0000` are codes. A digit of any script is still a digit (`#FF0000๑`, a Thai digit after it, isn't a code). A character a combining mark sits on isn't a digit, and a cell holding one breaks a code.

The finding goes by cells, not by the line's text: each cell's text is looked at whole, a code is seven cells next to each other each holding exactly one of its characters, and its place is the cells it's in. So a wide character before a code (two cells, three bytes) moves the code's cells by two, as it moves the code on the screen.

`lbterm_extras::hex::find` is the rule, tested without a window (`cargo test -p lbterm-extras hex`).

## Where a code is found: in the line's layout, not its link scan

A code is found as the renderer lays a pane's row out (`render/screen_line.rs`, `render_screen_line`), from the row's own cells, and its bar is drawn there with the row's other quads. Nothing is kept on the line, its cells or the pane.

That layout runs only on a miss in the line quad cache, which keeps a row's quads by what the row shows and how it's shown (`LineQuadCacheKey`: the line's `shape_hash`, a hash of every visible cell's text and attributes, the wrapped bit included, with the config's generation, the shape and quad generations, the selection's columns on the row, the cursor on it, focus, the hovered link, and the rest; FLOWS.md rows 85 to 87); a frame copies a row's kept quads to its place without laying it out again. So:

- a still screen lays nothing out and finds nothing;
- a row that changes is laid out, and its codes found, in the frame that draws it;
- a row that only moved (a scroll, Claude Code moving its conversation up) finds its quads by what it shows and isn't laid out or looked at again;
- but the walk runs again on every miss of a row whose text didn't change: the cursor arriving on it or leaving it (the key echo's row, each key), a selection dragged across it, a link on it hovered, the pane gaining or losing focus, and a row whose quads expire (blinking text, laid out each frame while it blinks). A scan kept by the line's text, as the links' is, wouldn't run again on those.

That's the trade: found in the layout, the codes need no carrier on the line and nothing to clear when it changes (below), for a walk on every miss, each inside a layout that costs far more. What it costs: one walk of the row's cells (a cell's text compared with `#` or a digit and three attribute bits read, about a hundred cells), on the GUI thread, inside a layout that shapes and places every cluster of the row and costs tens of microseconds. The walk is the only look at the row's cells it adds: the last cell's wrapped bit is taken in it too, not asked of the line, whose `last_cell_was_wrapped` walks a screen row's cells again (PITFALLS 290). Worked out at under a microsecond a row, not measured on its own. A row with a code adds two or three quads to its kept quads (the bar, and its outline when it has one). Nothing runs per frame, nothing per push, and nothing in the mux server.

Measured once against main's build (2026-11-09, `budgets -Against`, 5 rounds a build; PERF.md, "Colour codes, by `budgets -Against`"), on the three flows a layout runs in, none printing a `#`: every metric the same on a frame with nothing new (`repaint`: 0 lines laid out in all 75 runs of each build, so the walk never ran), on a scroll (`busy-scroll`: about 5 rows laid out a second, the GUI thread 71.3 and 69.8 ms a second, +-7.72) and on pane output at full speed (`throughput`, 16 MB on a mux domain: about 200 rows laid out a run, the GUI thread 85.9 and 94 ms a run, +-23.9, 71.1 and 69.2 MB/s, +-8.56), but one: `throughput`'s screen refreshes from its first present to its settling, 16 and 17, higher by a count's floor (+-1.11) where the same span's time was the same (221 and 227 ms, +-29.7), not run again. So the walk adds nothing those flows can show; its own cost a row (under a microsecond, worked out above) wasn't measured, and the half widths bound it only far above that.

### Why not where the links are found

The first plan was to find the codes with the row's links (`ClientPane::apply_hyperlinks`, `renderable.rs`'s `scan_rows`, kept by the line's text in `pane/lbterm_links.rs`'s `KeptScans`) and carry them to the renderer. Looked at closely:

- **The scan can't reach the finder.** A mux pane's scan is in `wezterm-client`, a local pane's in `wezterm-surface`'s `Line::apply_hyperlink_rules`; neither depends on `lbterm-extras`. `wezterm-surface` shouldn't: it's upstream's line and cell model under the terminal, written to build without std (`#![cfg_attr(not(feature = "std"), no_std)]`), and `lbterm-extras` is std with the GUI's dependencies (resvg, image, notify). `wezterm-client` could, but then every change to `lbterm-extras` would build `wezterm-client` again, and what depends on it.
- **What it found would need a carrier.** The renderer draws from a row's cells. A code found in the scan would have to be put on them: the cells' own underline and its colour (fat attributes, a heap block a cell, the underline at the font's underline place and thickness rather than a 2 px bar at the foot, and a program's own underline or underline colour written over), or a bit of LBTerm's in `CellAttributes` (an upstream struct that goes over the wire), or a field on `Line` (8 bytes on every line of every pane's scrollback). Any of them is state on the line that every change to the line has to clear, as `invalidate_implicit_hyperlinks` clears implicit links (PITFALLS 24 and 55).
- **The renderer would read the cells anyway.** A mark saying which cells are a code doesn't say its colour; that's in the cells' text, which the renderer would read again to draw it.
- **It would scan only where links are scanned.** `scan_rows` and `apply_hyperlink_rules` return at once with no `hyperlink_rules`, so codes would have needed those early returns changed too.
- **It costs no less to read.** The link scan, too, reads only the rows a frame asks for (CODEMAP.md, "A mux push", step 3: `apply_hyperlinks` runs before `paint_pane` reads the rows, kept by the line's text in `KeptScans`), so output that scrolls past unseen is read by neither. Where they differ is that a scan kept by the text runs once a text, and the layout's walk again on each of the misses above.

Found in the layout, a code is a function of what the row shows, which is what the line quad cache's key is, so the bar is right by construction whenever the quads are: nothing to clear, nothing to keep in step, local and mux panes alike, copy mode and quick select (which draw their pane's rows) included. `KeptScans` is left as it is.

## How the bar is drawn

`render/hex.rs`'s `lbterm_hex_bars`, which `render_screen_line` calls once the row's backgrounds, underlines and the selection's background are in layer 0, only for a pane's row (`stable_line_idx` set: not the retro tab bar's line), with `lbterm_hex_colours` on. It walks the row's `visible_cells` once into `hex::Finder` (`find` a cell at a time: a `CellRef`'s text borrows the `CellRef`, so an iterator of them can't hand it on, and collecting them would allocate a `Vec` a layout), each cell with its text, whether it's underlined, whether it's hidden (SGR 8) and its wrapped bit, and for each code:

- The bar spans the code's seven cells (their columns through `phys`, as the underlines are placed), at the foot of the row: its height `max(1, round(2 × dpi / 96))` px, its bottom the cell's bottom. Within the row, so nothing is drawn at another row's place (PITFALLS 128).
- Its colour is the code's, `#RRGGBB` as sRGB, made linear as every colour the renderer draws is.
- Hidden text gets none. A code any of whose cells the program hid with SGR 8 (`Finder` leaves it out), or drew in its background's colour (a cluster over the code whose text colour is its background's, which `lbterm_hex_bars` checks against the row's shaped clusters), gets no bar: the glyph pass draws none of that text (`screen_line.rs` skips a cluster that's `invisible()` or whose glyph colour is its background's), and a bar would show the colour, and that a code is there, under blank cells (PITFALLS 291).
- In layer 0 after the selection's background, so a selected code shows its bar as at rest; glyphs are in layer 1, over it (no character of a code reaches the foot of its cell). A block or underline cursor is drawn after it in layer 0, so it sits over the bar on its cell as it sits over the cell's background; a bar cursor is in layer 2.

`lbterm_extras::hex::bar` gives the rectangles from the code's span, the cell's height and the DPI, tested without a window.

## A code too near its background

A bar in a colour too near the background under it can't be seen (`#121212` on LBTerm's `#121212`). When the code's colour is within 0.08 of the background in Oklab (a perceptual space: about `#252525` against `#121212`, and hue counts as well as lightness, so a red code on a green background as light is seen), the bar gets an outline in the colour of the code's text: a rectangle of the text's colour two pixels taller and wider than the bar, the bar inside it, all within the row (so an outlined bar is 4 px tall at 96 DPI, its colour the middle two). The background is the code's first cell's background as at rest (the pane's background unless the program set one), and the text's colour is that cell's, both as the layout resolves them for the glyphs. `lbterm_extras::hex::too_near` decides it, and `hex::look` which of the three ways a bar shows (a bar, outlined, none).

A program that shows a code's colour itself, painting the code's cells' background in it (Neovim's colour highlighters do, the text black or white over it), gets no bar. The background under the code's first cell, as drawn, is the program's (its `background()` isn't the default, or the cell is reversed) and each of its sRGB channels is within 1 of the code's. Otherwise every such code would be too near its background and get an outlined bar, a box at the foot of the program's own swatch. A background the program painted near the code's colour but not it (a colour scheme's `#1e1e2e` behind `#1e1e1e`) is outlined, as the pane's own is.

How a change reaches a row's kept bar: through the line quad cache's key, as everything else the layout drew does. The bar reads the row's cells (the code, its attributes, the last cell's wrapped bit: all in `shape_hash`), the DPI and the pane's columns (the bar's thickness, an RTL row's columns: `quad_generation`, moved by a DPI change or a resize, `resize.rs`), the palette (the text's and background's colours: `shape_generation`) and the config (the switch, and the colours it names: `config_generation`). A program's palette change (OSC 4, 10, 11) comes as `MuxNotification::Alert { alert: Alert::PaletteChanged }` (`termwindow/mod.rs`, the arm near line 1616), which dispatches `TermWindowNotif::InvalidateShapeCache`, whose handler moves `shape_generation` (near line 1468); `shape_generation` is in both `LineQuadCacheKey` and `LineToEleShapeCacheKey` (`render/pane.rs`), so every row is shaped and laid out again, the outline's nearness judged against the new background and drawn in the new text colour. A config save moves `config_generation` instead.

## A program's own underline, links, selection and the pointer

- **The bar yields to a program's own underline.** A code any of whose cells the program underlined (any underline style, SGR 4 or 4:n) gets no bar, and its underline is drawn as the program asked. Both would be lines under the same cells within a pixel or two of each other, and a program that underlines a code (a link in a Markdown viewer, a spelling mark) means its own line to be read.
- **Links.** The code's cells are unchanged, so a link over a code (an OSC 8 link, or a rule's match such as a URL ending `/#FFBF00`) is found, hovered and opened as before. Under the pointer the link's underline is drawn as before, and the bar with it (below). The hovered link's underline is the cell's underline sprite at the font's underline place, drawn in layer 0 before the bar; in Lachlan's font at 96 DPI (cells of 9 by 20) it's a row of pixels above the bar's two, so both show (perf/hex-swatch.ps1's hover.png). Where a font's underline sat in the bar's rows, the bar would be drawn over it on the code's cells.
- **The pointer and a selection.** The bar shows under the pointer's hover and in a selection as at rest (Lachlan's 6a of 2026-11-10: the colour still tells him something there, and the bar hides neither the selection nor the link's underline).
- **Copying** reads the cells, which are what the program printed: `#FFBF00` copies as `#FFBF00`, and `lbterm cli get-text` gives the same.

## A code a line wraps

A row is laid out on its own, so a code is found on a row only when all seven of its characters are on it: a code a wrap splits across two rows gets no bar on either part. Finding the other part would mean reading the row before or after during a layout, and the bar would then turn on a row the line quad cache's key doesn't hold (the next row printed after this one was laid out would leave its quads wrong). Links on a mux pane are found the same way, a row at a time (`scan_rows`). At the edges:

- a code ending at a wrapped row's last cell isn't counted: what follows it is on the next row and could be a digit (`#FFBF00` then `AA` on the next row is `#FFBF00AA`). The row says it wraps on its last cell's wrapped bit, which the walk reads as it hands that cell over (`hex::Cell::wraps`), so the layout knows without asking the line (`last_cell_was_wrapped`, which would walk the row again).
- a code at a row's first cell is taken as a start: the row can't tell whether the row above wrapped into it, so `abc` at the end of a wrapped row and `#FFBF00` at the next's start gets a bar. Rare, and harmless.

## The switch

`lbterm_hex_colours` (on by default; `config/src/config.rs`). Off, the layout looks for no codes. A config change moves the config's generation, which is in the line quad cache's key, so every row is laid out again with the switch as it is.

Decided in building it, which he wasn't asked and may want otherwise: the bar gives way to a program's own underline on any of the code's cells (codes-x3.png: `#FF4080` keeps its white underline and gets no bar); a code the program hid (SGR 8, or its text in its background's colour) gets none (hidden-x3.png); a block or underline cursor covers the bar on its own cell (cursor-x3.png); "too near" is 0.08 in Oklab (`#242424` on `#121212` is outlined, `#252525` isn't); and by the rule in "What counts", six-digit issue and PR numbers (`PR #102345`) and hashtags of hex letters (`#decade`, `#facade`) get bars too.

And one of how it's built: the brief put the finding with the links' (`KeptScans`), and it's in the row's layout instead, for the reasons in "Why not where the links are found" (the link scan's crates can't reach `lbterm-extras`, a carrier on the line would need clearing at every change, and the walk sits inside a layout that costs far more), at the cost of walking a row again on misses its text didn't cause.
