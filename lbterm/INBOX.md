# The InMail button

A small button on the window strip, in its first row above the tab rail, saying how many messages wait in a set of folders. Lachlan's projects send each other messages through an `InMail/` folder at the top of each project, one Markdown file per message, and a message waits there until the agent that deals with it archives it (moves it out). The button counts every project's at once. A click drops a list of them; picking one opens a new tab in that project, and in Lachlan's config that tab runs Claude Code, told to read the message and deal with it. Asked for on 2026-10-23: "Above the tab bar I want a little notification button. The notification button represents the amount of unread inmails in the project. Selecting an inmail there should open a new tab to that project and have the agent read it."

## Turning it on

```lua
rawset(config, 'lbterm_inbox', {
  folders = { [[C:\Work\Projects\One\InMail]], [[C:\Work\Projects\Two\InMail]] },
  glyph = '\u{f01f0}',   -- on the button, before the count; nf-md-email_outline by default
})

-- Picking a message fires this. Return false and LBTerm does nothing more; return anything else
-- (or have no handler) and it opens a new tab in m.dir, the folder above the message's
wezterm.on('lbterm-inbox-open', function(window, pane, m)
  -- m.file, m.name, m.folder, m.dir, m.project, m.from, m.subject, m.sent
end)
```

`rawset`, as for the Conductor: a build that doesn't know the key would refuse it. It needs the tab panel (`lbterm_tab_panel.enabled`, with the tab bar holding only the window's buttons), since the button sits over the rail.

## What counts as a message

Every `.md` file in one of the folders, each a message waiting. A folder that isn't there has none (InMail makes a project's folder when its first message comes). A message's front matter is the block of `key: value` lines between its opening `---` and the next, as the megaproject's `inmail.ts` (`~\AI`) writes it:

```text
---
from: Terminal
to: LBTerm
sent: 2026-10-23T14:02
subject: "The rail's question light"
---
```

A value in double quotes is a JSON string, one in single quotes has its `''` made `'`, as `inmail.ts`'s `parse` reads them. What the list shows of a message falls back when the file doesn't say: who it's for is its `to`, else the name of the folder above its folder; its subject is its `subject`, else its file name; when it was sent is its `sent`, else the file's time.

The format is InMail's, published as `@Blueprint:inmail-files` (LBTerm's `api.json` uses it, so a change to it comes by InMail). Since 2026-11-08 a message can carry `re`, `replaces`, `answer` and `group` too, which read as any other key and change nothing here, and a conversation that reads a message leaves `<message>.taken` beside it, JSON `{ "session", "at" }`, gaining `released` and `why` when it's handed back. A claim isn't a `.md` file, so the count is the same with or without one. The folders' watch counts any file in them as a change (`Watch::matters`), so a claim written or removed has the thread look again, about 1 ms. `Scan::look` reads each folder once, its claims (`*.taken`) before its messages, a claim read again only when its file's size or time changes, as a message's is, and gives each message the one beside it (`Message::taken`, `inbox::claim`): the session it names, when it was taken, or nothing once it's been handed back (`released`), or when its session isn't a Claude Code id. The file alone says it: whether that conversation is still open is Claude's to say, which took 0.65 to 1.4 s to read, so it isn't asked, and a claim left by a conversation since closed still reads as taken (its link's click resumes it). A claim written or handed back changes what waits, so the windows repaint once and the links and the list follow it.

`lbterm_extras::inbox` holds the reading (`front_matter`, `message`, `Scan`), the order, the count and the button's colours, tested without a window (`cargo test -p lbterm-extras inbox`).

## How it's built

**Nothing is read on the GUI thread.** A thread of its own (`wezterm-gui/src/inbox.rs`) watches the folders (`Watch`: ReadDirectoryChangesW, through notify) and looks in them when something in one changes, the config's folders as they are then, opening only the files that are new or whose size or time changed (`Scan`). When what waits changes, every window repaints. While nothing changes it sleeps: it looked every second until 2026-10-30, so a message showed up to a second after it was written (39 to 1042 ms in `perf/inbox-cost.ps1`, a median of 293 to 505) and the thread woke every second for nothing; it shows in 46 to 89 ms now, as the test sees it in the state file, 25 of them the wait for a message's changes to come together (below). The watch's own thread (notify's) woke ten times a second whatever happened until LBTerm built notify from its own copy (`deps/notify`, perf/at-rest), so the folders cost nothing at rest from then (lbterm/AT-REST.md). Each folder that's there is watched itself, and one that isn't (a project with no `InMail/` yet) from the nearest folder above it that is, which sees it made; a change there that's on no folder's way (another file in the project) is let go without a look (`Watch::matters`). The folders are watched again before each look, so a folder made with another in it already is followed down, and a message written meanwhile is in the look. Changes come several to a message, so a look waits 25 ms after the first and takes them together. A file the look couldn't read (still being written, held by a scanner) is looked for again 250 ms later, since nothing may say when it can be; the watch failing (Windows' buffer of changes running over) is said in the log and answered with a look. A reload of the config wakes it for its folders. Forty-odd folders take a readdir each, a look; on 2026-10-30 Lachlan's config named 47, 44 of them there.

**The button** (`render/inbox.rs`, `lbterm_inbox_button`) is an element of the fancy tab bar's first row, before the strip's words, so it's part of the strip like the restart pill: it fades on hover (`button_hover`, `render/hover_fade.rs`), the state file names it `inbox` among the strip's items, and it doesn't drag the window. Its middle is the rail's (`tab_panel::rail_column`, `Layout::column`), as the context pill's is under it on the second row (lbterm/CONTEXT.md), and the words still start where the panes' text does; a button too wide for the room pushes them on rather than run into them. It's the restart pill's shape, a hairline with fully rounded ends round the glyph, its fill the strip's:

| | Hairline | Glyph | Count |
|---|---|---|---|
| nothing waiting | white 14% | white 45% | none |
| mail waiting | white 35% | white 92% | the waiting orange (`#FF8A3D`), the real count however many (no "99+" since 2026-10-28, Lachlan's ask) |
| under the pointer, or its list open | white 50% | white | the waiting orange |

The orange is the rail's for a tab that needs you, since mail waiting is something that needs Lachlan. The count changing in a window dissolves on `swap`, and more mail brightens the button once with the copy flash's light (`render/strip_swap.rs`, `lbterm_strip_swap_inbox`): a message arriving answers on screen, as everything does (`lbterm/DESIGN.md`, principle 1).

**The list** hangs under the strip from the button, in the tab menu's card and light (z-layers 77 to 79, in the compositor's `top` with the other menus), newest first, as many as fit and the rest a scroll away: each row says when the message was sent (the prompt list's stamps: the time today, the day this week, the date before that), who it's for, its subject, and who sent it when there's room. A message for a repo, its folder in a project `lbterm_projects` lists under another (its `parent`), has the projects card's blue repo mark before who it's for (lbterm/OBJECTIVES.md, "The projects card"; Lachlan's yes, 2026-10-28); without `lbterm_projects` no row has one. A click on a row, or the arrow keys and Enter, opens it; Esc or a click elsewhere closes the list. It follows what waits while it's open: a message archived meanwhile goes from it, and the row picked by the keys stays picked by its file. A message a conversation has taken (its claim beside it, "What counts as a message") says so after its subject, `taken 15:02` (when it was taken, as the stamps say a time), in the rail's working green, since a session is working on it (Lachlan's E1 of 2026-11-08); it keeps its place by cutting the subject short, and who sent it follows when there's room. The card is as wide as its widest row needs, every inset the paint keeps counted and a column to spare (`lbterm_inbox_list_layout`): until 2026-11-08 it counted 24 px of the 28 and no spare column, so the widest row was a column short and never showed who sent it, and with the insets alone its last glyph was cut.

**Opening one** fires `lbterm-inbox-open` with the window, the active pane and the message as a table: `file`, `name`, `folder`, `dir`, `project`, `from`, `subject`, `sent`, and `taken`, the session id of the conversation that has taken it, when one has. Unless a handler returns false, LBTerm then opens a new tab in the folder above the message's, on the active pane's domain (the mux server's, on Lachlan's), running the domain's default program. Lachlan's handler brings a taken message's conversation forward rather than starting a second reader (his E2 of 2026-11-08; Terminal's lbterm.lua, "Lachlan's config" below).

## Links to a message

A link in a pane to `lbterm://inmail/<project>?message=<file name>`, each part percent-encoded, names one message: the one of that file name waiting for that project (its `to`, else the folder above its folder, in any case), as Lachlan's InMail writes it after sending one. Asked for on 2026-10-23, the evening the button came: "when I click the button for an agent to read the inmail, it should link to the specific inmail. Also the button should show if the inmail has since been read by the agent." While the inbox is on, LBTerm draws a link's words in the waiting orange while its message waits in one of the folders, in the rail's working green (`#3DDC84`) while it waits with a conversation's claim on it (his E1 of 2026-11-08), and once it's gone (dealt with, archived) in grey, white 40% over the surface (`#717171`), struck through (his picks, 2026-10-23). Any other link, a project's whole inbox (`lbterm://inmail/<project>`) included, is drawn as it always was, and so are links before the folders' first look. So is a link to a project none of the folders is the InMail of, with no message of its waiting (`lbterm_extras::inbox::looks_in`: the folder above an InMail folder ends with the link's project, in any case, so a code base matches by its own name or its path under the root, `LBTerm` or `Terminal/code/LBTerm`): whether its message waits can't be known. Until 2026-11-03 it was drawn grey, as read, and a project made after the config was read had every link to its mail drawn read while the mail waited. What a click does is the config's `open-uri` handler's.

The colour is chosen where a line is shaped (`render/screen_line.rs`, `lbterm_inbox_link` in `render/inbox.rs`), from what the inbox's thread last found, so nothing more is read for it. The thread counts each change in what waits (`inbox::changes`), and a window that shaped its lines at another count shapes again, on its next paint, only the lines holding a link to a message (`lbterm_inbox_links_refresh`, `lbterm_extras::link_looks`), which the change's repaint brings: a link greys out in the frame the button's count changes in.

## What a change costs

A message arriving or archived anywhere changes the button, so every window paints to show it. Measured in a test window with four panes of coloured text and an InMail folder of its own (`perf/inbox-cost.ps1`), first on 2026-10-29 when the question was why one cost a quarter of a second:

- The thread's look is about 1 ms of its own: a readdir and the one new file read. It looked every second, so the button showed a change up to a second late (a median of 293 to 505 ms in six runs); it watches the folders now and shows one in 46 to 89 ms (above, "How it's built"), and at rest the thread doesn't run at all.
- An arrival painted three frames and an archive two (one of them, in a test window, the state file's frame after DWM's dissolve: lbterm/STATE.md). The third was the brightening's: a light that a paint decides went to the compositor in that very frame and still asked for a frame of its own (`lbterm_light_this_frame` now, render/lights.rs), and a pad's glint did the same.
- Each of those frames drew and presented every visual, 24 in that window, though the strip's are all a change touches: about 20 ms of the GUI thread a frame. Only what changed is drawn now (lbterm/COMPOSITOR.md): two or three visuals, a frame's draw from 5 to 36 ms down to 2 or 3.
- The swap's dissolve made its swapchain again for nearly every change (the button with a count and without are different widths), and that waits for the GPU: 4 to 25 ms. Its swapchain now holds the whole strip, and a clip shows the rows that changed (render/strip_swap.rs).
- In a window whose panes are its own (not on a mux domain), every paint asks each pane its title, which a pane without a title of its own takes from its foreground process, and a list older than 300 ms was walked again on a thread per pane: every process on the PC, four times, 60 to 160 ms of CPU a change. A list taken a couple of seconds after the pane last printed was kept from then (`proc_list_quiet`), and since 2026-10-31 a list is walked again only when the pane's processes start or end in a way it shows (a process starting in a pane titled by its foreground, the foreground ending), which a job of its own says (`mux/src/lbterm_procs.rs`, `mux/src/lbterm_proclist.rs`; lbterm/PERF.md, finding 49).
- The 127 to 164 ms paint the slow log showed is the window's first frame, not a message's.

All together: 125 to 440 ms of GUI CPU a change before, against 23 to 44 ms now (the changes after the first, in four runs on 2026-10-30); on a mux domain, as Lachlan's tabs are, 45 to 117 ms against 27 to 50. What's left is the paint pass building every pane's quads again (about 5 ms there) to learn that they're the same, which every frame pays.

While the list is open it costs a frame nothing it hasn't already done (since 2026-10-31): it laid itself out twice a frame and again for every mouse event in the window, each time asking which project every message's folder is in by making every project's folder key again (70 messages by 47 projects in a window like Lachlan's). Its layout is kept now and made again only when the messages, the projects, the day, the scroll, the fonts or its place change, and its words are laid out once and kept (lbterm/PERF.md, "What the cards cost"). `perf/inbox-mouse.ps1` holds what a move within a row of the open list costs, and the budget runner's `busy-inbox-list` what a frame costs with it open while the tab under it paints.

## Lachlan's config

Terminal's `lbterm.lua` names every project's `InMail` folder: the index (`~\AI`, named `Life/Projects` in InMail) and each repo in `Backup\repos.json`, as InMail's `projects.ts` lists them, read when the config loads. A project added later shows once the config reloads. Each `InMail` folder's watch holds a handle inside its project, which stops Windows renaming the project: a program renaming one asks LBTerm to let go of it first (`lbterm_let_go`, LET-GO.md). Its handler opens the tab the way an InMail link an agent gives does (`lbterm://inmail/<project>`, the same config's `open-uri` handler): through the Conductor's `new` with the project's folder, started with `wezterm.background_child_process`, so the GUI thread isn't held while node starts. The tab opens in the window Lachlan was last in without switching to it (his pick, 2026-10-23, over a tab LBTerm opens and switches to), and Claude is told to read that message and deal with it, words the Conductor puts in through a file. It returns false, so LBTerm opens no tab of its own. It leaves alone a message from a folder that isn't one of its own, so a test window with folders of its own (below) gets the default. A message a conversation has taken (the table's `taken`) isn't given a second reader: the handler runs the Claude project's `ai open` on that session, which brings its tab forward, or resumes it in a new tab when it's closed, as a click on a conversation's link does (`lbterm://session/<id>`); a link to the message does the same, the handler reading the claim beside the file itself (his E2 of 2026-11-08).

The link to one message is what `inmail.ts send` prints for an agent to give him, `[<project>: read "<subject>"](lbterm://inmail/<project>?message=<file>)`. Its `open-uri` handler opens the tab the button opens for that message, while it still waits in that project's folder (found by its `to`); once it's gone a click does nothing (his pick), and the link is already grey and struck through.

## Checking it

- `cargo test -p lbterm-extras inbox` and `cargo test -p config` (`the_inbox_comes_from_lua`), both in `lbterm.ps1 check`.
- `pwsh -File lbterm\perf\inbox.ps1`: three projects' folders of its own (one never made) and a handler that writes down what it's given. One message: the button over the rail says 1 in orange (`one.png`). A second, sent while it runs: it says 2. A click drops the list, newest first (`list.png`). Down and Enter: the handler hears the message whole and lets the default open a tab in its project's folder. A click on the other row: the handler takes it, and no tab opens. Each archived: 1, then none, the button sitting back with no orange (`none.png`), its list saying so (`target\perf\inbox`).
- `pwsh -File lbterm\perf\inbox-cost.ps1 [-Mux]`: what a change costs (above), with four panes of coloured text: none painted at rest and the InMail thread asleep, then a message written and archived three times. It fails when the thread runs at rest, when a change paints more than its frame and the state file's, when that frame draws more than four visuals or any but the strip's, the swap's and the lights' swatch (the state file's `visuals.which`), when the next draws any, when a change after the first starts a thread that runs (a process walk), when the button shows the changes more than 200 ms after them at the median, or when the changes cost more than 60 ms of GUI CPU at the median (50 on a mux domain; `cost.json` has every number).
- `pwsh -File lbterm\perf\inbox-links.ps1`: two projects' folders of its own and a program printing the same words four times, plain, as a link to a message waiting, as a link to one that isn't, and as a link to a message for a third project whose folder isn't looked in. The first link is orange and the second grey and struck through, the third neither (`links.png`); the message archived, neither is orange and both are struck (`archived.png`); a message of the second's name arriving, it turns orange and loses its line (`arrived.png`) (`target\perf\inbox-links`).
