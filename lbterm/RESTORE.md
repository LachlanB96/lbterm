# Crash restore

When LBTerm ends without closing cleanly (a crash, the process killed, Windows restarting for an update), the next LBTerm asks in its first window, once the window has its tabs, which of the old tabs to open again: all of them (Enter, or "Open all"), the ones picked (Space, A, N, a click on a row, then Enter or "Open picked"), or none (Esc, or "Don't open").

A tab comes back as one pane in its folder. A tab that was running Claude Code comes back as `claude --resume <session>` in a pwsh that stays open afterwards, the same command the Claude project's resume runs, so the conversation carries on where it stopped and its hooks (summary pane, status light) start as usual. Splits aren't rebuilt: a tab's other panes (the summary pane under a Claude session) come back on their own or not at all. A tab that was parked (Lachlan's 8a, NEW-TAB.md, "Landing 4") comes back parked: once it's open its flag is set, here for the GUI's own tab, asked of the server for a mux domain's (`park.rs`); a server that can't park (a build from before 8a) leaves it unparked, logged.

`config.lbterm_crash_restore = false` turns it off.

## The note

LBTerm keeps a note of its tabs in `%APPDATA%\lbterm\session-<window class>.json` (its data folder), rewritten a couple of seconds after the tabs change: a tab opens or closes, a pane's folder changes, a Claude session starts or ends in one, a tab is parked or unparked. It's written on a thread of its own, beside the old one and renamed over it, and only when it differs from the last. Each tab is noted from its Claude Code pane if it has one, else from its active pane: title (without Claude's status glyph), folder, session id, and `parked` when it is (left out otherwise, so a note from before 8a reads unparked; a tab still waiting from an earlier offer pairs with one of the note's own parked or not, the note's own saying which). A tab of the GUI's own passing panes isn't noted: a mux domain's connection status ("wezterm: Connecting...") sits in the window as a tab while the domain attaches, and a note written then listed it, with no folder, as a tab to open again.

The session id is the `claude_session` user var that Terminal's `claudehook.exe` sets in the pane: at SessionStart (`claudehook session start`), and with every working or waiting status, emptied at SessionEnd (`claudehook session end`). So a session that ended normally isn't resumed, only reopened as a shell in its folder.

Closing LBTerm normally (its last window, or Quit) marks the note clean, and nothing is offered next time. The note also holds the pid and start time of the LBTerm that wrote it, so a second LBTerm with the same window class running at the same time isn't taken for a crash. One that has ended counts as gone even while something still holds a handle to its process (a process monitor's, a test harness's), which keeps its pid and times readable: it's running only while it has no exit code. Until 2026-10-30 such a handle made the next LBTerm offer nothing and write its own note over the old one.

With panes in a mux server (a unix domain, `lbterm-mux-server`), a GUI crash leaves them running and the next GUI reattaches to them, so they aren't offered again: a noted tab is left out if a pane that outlived the GUI has its Claude session, or (for a tab without one) its folder, each such pane standing for one tab. A pane with a session no noted tab has can stand for a shell tab in its folder too, after the panes without one: Claude Code started in that tab within two seconds of the crash, before the note said so, and offering it would open a second tab there. Nothing is offered when they're all still open. Reattached panes' user vars arrive a moment after the panes, so with any of them the offer waits two seconds. A GUI that had to start its server found nothing running: the server's first tab is new, and never stands for a noted tab in its folder. A Claude session in that server still counts, though: one resumed by hand while the prompt was put aside isn't offered again when the prompt comes back, where Enter would have started a second `claude --resume` on it. Closing the GUI then marks the note clean only if panes no longer live on in such a domain: if the server dies later (a restart), the next start still offers them.

## When it asks

The prompt comes once LBTerm's start-up is done: the window's domain has attached, so the window has its final tabs (`start_up_done`, at the end of `async_run_terminal_gui` in `main.rs`). Before that, a window on a mux domain holds only the domain's connection status, a tab of the GUI's own that goes as soon as the domain attaches. Until 2026-10-30 the first window asked as soon as it was made: on Lachlan's restart that morning (GUI and server both ended, onto a new build) the prompt went up over the connection status, the attach took that tab away about two seconds later with the prompt on it, the server's first tab took its place, and the prompt's thread was left waiting for input that never came. Nothing was opened and nothing was answered. The prompt goes over one of the window's own tabs (the open one, else the first, opened), never a connection status.

It's asked in one window at a time, the first with a tab of its own (not a window of passing tabs alone, as a configuration error's is, which can sort first), and once answered never again: not in a second window, nor after a reconnect or a resync. Only an answer ends it: Enter, Esc, a button or Q. A prompt that goes without one gives the note back, and it's asked again in that first window, over its tabs as they are then: its tab leaves the window, the window moves to another mux window (a workspace switch, which takes every overlay down), something else is opened over it, the window closes, or the answer never gets to its window (Enter, and the window closing straight after).

It never goes over another overlay. The launcher, a close confirmation (Ctrl+Shift+W, the X button when a tab would ask, the quit prompt) or anything else opened over the prompt takes the prompt down, and the prompt waits for it to close: that overlay's pane leaving the mux brings the prompt back over the open tab, and confirmed, the close leaves the note as it is. Until 2026-10-30 that counted as "Don't open" and spent the note; asked again at once over the same tab instead, as this fix first had it, the prompt took the newcomer down in turn, so none of them could be used while the prompt was up.

The new LBTerm notes its own tabs from the start, whether or not the prompt has been answered, and keeps the tabs it offered in the note as `pending` until it is. The next start offers the pending tabs whatever happened (a clean close too), with the note's own tabs as well if that LBTerm didn't close cleanly, each tab once: a Claude session by its id, and the rest paired one for one, so two shell tabs alike (one folder, one title) are both offered (until 2026-11-01 they were one row). So closing LBTerm without answering asks again next time, and an LBTerm whose prompt nobody answered still has its own tabs offered after a crash or shutdown. Until 2026-10-30 it wrote nothing until the prompt was answered: a prompt left in a tab from 01:05 to a shutdown at 03:27 on 2026-10-24 meant none of that run's tabs could be offered, and the prompt orphaned at 11:09 on 2026-10-30 (above) left Lachlan's GUI writing no note for the rest of its run. (The fix was written on 2026-10-24 and only landed on 2026-10-30, on top of the asking above.) Test windows use classes of their own (`com.lachlanb.lbterm.perf…`), so they never see or touch the real note.

The GUI's log says what it did, at INFO under `lbterm_gui::restore`: the tabs it asked about and over which tab of which mux window, an answer and how many it opened, a prompt gone without one, an answer that never got to its window, the open tab having something else over it, every noted tab still open.

## Where it is

- `lbterm-extras/src/restore.rs`: the note, whether to offer it, when and how often (`Asking`), which window and which tab it goes over (`window_to_ask`, `prompt_tab`), which panes stand for noted tabs (`survivors`, `still_closed`), the answer on its way to its window (`Handed`), the command a tab runs, a row's words, the picks (tested).
- `wezterm-gui/src/restore.rs`: start-up, writing the note, the clean exit, offering it and asking again, opening the tabs. `overlay/restore.rs`: the prompt, and its outcome: answered, or cancelled.
- `lbterm\perf\restore.ps1`: the whole thing in test windows. `LBTERM_RESTORE_CLAUDE` names a stub `claude.cmd` that only echoes its arguments, so a test never starts a real Claude Code. `-Mux` does it on a mux domain of the test's own whose new server answers 3 s late, as Lachlan's did: no note written while the first window attaches lists its connection status, the GUI and the server both killed, the prompt over the server's first tab after the attach and still there 3 s on, a hang-up and reconnect leaving the one prompt, the prompt's tab ended and the prompt asked again over the tab left, once. Both ways the launcher (F8) is opened over the prompt and must stay up, with the prompt asked again only once Esc has closed it; a workspace switch (F9) and back (F6) asks again once each, on the mux window the window is on; and the window is closed with the prompt up. All the while the window's own note, written from the start, must have the killed LBTerm's three tabs pending. The next window asks once and is killed with the prompt up, its note, not clean, keeping the three pending; the window after it asks once, and Enter brings every offered tab back (with -Mux in its server), leaving nothing pending; then, with -Mux, only the GUI killed, which must offer nothing and leave nothing pending. The installed build of 2026-10-30 fails it as Lachlan saw it: the prompt went within 3 s, nothing came back, and the note was never taken over.
