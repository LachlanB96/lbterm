# The context pill

A small pill on the window strip's second row, right under the InMail button, saying what the open tab's Claude Code conversation has cost, with the projects pad right of it (lbterm/OBJECTIVES.md, "The projects card"). A click on it does nothing: until 2026-11-08 it dropped a list of the files in that conversation's context (every CLAUDE.md, import, rule and memory index Claude Code loaded, how each came to be loaded and how big it is), which went with Lachlan's 5a of that day, the context bar's pane listing them now (The context bar, below). Asked for on 2026-11-07: "LBTerm should be able to show me what context files this agent has loaded currently. There should also be a $ amount of how much this agents tab has cost. It should go under the inmail button." The open tab panel's rows say each tab's dollars too (his yes to that, the same day).

## Turning it on

```lua
rawset(config, 'lbterm_context', {
  -- transcripts = [[C:\Users\me\.claude\projects]],   -- Claude Code's; this is the default
  -- count_cost = false,      -- LBTerm counts each conversation's cost itself, for the cost pane
})
```

`rawset`, as for the InMail button: a build that doesn't know the key would refuse it. It needs the tab panel (`lbterm_tab_panel.enabled`, with the tab bar holding only the window's buttons) and the strip's second row (`lbterm_prompt_history`), since the pill sits on that row over the rail. The dollars come from the folder `lbterm_summaries` names. `transcripts` is where the context bar reads the conversation (or `lbterm_scroll_strip.transcripts`, which wins, since one reader serves both); the pill itself reads no transcript. The pill shows while the open tab is a Claude Code session (its pane's `claude_session` user var), and not while the Conductor's view stands over the tabs. `count_cost` is the cost pane's (The context bar, "The cost pane" and "Turning it on"), off unless asked for.

## What it says

**The dollars** are the conversation's cost at list price, to the cent: every run of it (a resumed conversation appends to the same transcript) and every subagent's, priced request by request from the transcripts. Claude Code's own `total_cost_usd` (what `/cost` says) isn't it: that counts one process, and since it no longer restores a session's cost on resume, a resumed conversation would start again at $0. Another program writes the number, and LBTerm shows it as written; in Lachlan's setup that's his statusline (below). The pill reads `$0.42` and `$12.34` with cents under $100, `$148` and `$2304` in whole dollars, then `$12.3k` (`lbterm_panel::text::dollars`), never rounded up past the cent spent; `$–` before the file says anything.

**The list** it dropped on a click until 2026-11-08 went with Lachlan's 5a, its code with it (`render/context.rs`'s list, its layout, mouse, keys and paint, the state file's `menu` kind `context`, `conversations::Reader::Context`, `lbterm_extras::context::heading` and `fit_path`): the context bar's pane has every file, its kind, path and tokens, and the heading of what's in use (The pane, below). The pill doesn't light under the pointer (its hover colours are its rest's, and it isn't one of render/hover_fade.rs's fading items), its cursor is the default one, and a press on it reaches mouseevent.rs's tab bar arms, which do nothing for it: it doesn't drag the window either.

A `pulled in` file is a CLAUDE.md that a file read in its folder brought in after the start. One from a folder that isn't the conversation's own or one above it, another project's, is drawn in amber on the context bar and its pane: that's the expensive kind, a whole project's instructions loaded because one of its files was read. The conversation's own folder is where it started, the first `cwd` its transcript records, which neither a `cd` nor a resume changes.

**On the open tab panel** each row's second line ends with its tab's dollars, in the project's grey, the status cut short before it when the line is full. The closed rail doesn't show them.

## Where the files come from

Claude Code records what it puts in a conversation's context in the transcript (`~/.claude/projects/<folder>/<session>.jsonl`), as attachment records:

- `instructions`, when a session starts or resumes and again after every compaction: `files`, each with its `path`, its `type` (`User`, `Project`, `Local`, `Managed`, `AutoMem` for the memory index) and its whole `content`.
- `nested_memory`, for each CLAUDE.md pulled in later: its `path`, and its text under `content.content`.
- A `compact_boundary` system record for each compaction, which drops everything before it, the files pulled in included; the `instructions` record written right after it loads the start's files again.

So what's loaded now is every file recorded since the last compaction, by path, the newest record of a path giving its size. A resume writes another `instructions` record but drops nothing: what was pulled in before is still in the conversation's history. A subagent's records (`isSidechain`) are its own context, not the conversation's. Claude Code's `InstructionsLoaded` hook reports the same loads as they happen (with why: `session_start`, `nested_traversal`, `include`, `path_glob_match`, `compact`), but not the memory index, and it would need a program of its own to keep what it says; the transcript has all of it already, sizes included.

A file's tokens are its content's UTF-16 units over four, rounded, as Claude Code estimates a memory file's size; the heading adds them up. They're the files' share of the context, not the context's whole size.

## How it's built

**Nothing is read on the GUI thread.**

- The files are read by the scroll strip's transcript reader (`lbterm_extras::conversation`, on its `lbterm-conversations` thread): it parses the `instructions` and `nested_memory` attachments as it parses the rest (`WANTED`, the records it reads at all, has both), keeps the files in `lbterm_extras::context::Context`, and shares them with every snapshot it hands out (an `Arc`, copied only when a file changes, the revision moving so a new snapshot is taken). The reader follows the sessions windows say they show (`crate::conversations::shows`), per window and per reader: the scroll strip says its own (`Reader::ScrollStrip`) and the context bar its own (`Reader::Bar`), so neither undoes the other. The pill's list said its session while it was open (`Reader::Context`) until the list went on 2026-11-08; with neither the bar nor the scroll strip on, nothing reads the transcript at all.
- The dollars are read by the summaries' thread (`lbterm_extras::summaries`), from `<session>.usage.json` beside the session's summary: `{ "usd": 12.34, "window": 1000000 }`, the cost and the context window's size in tokens (`null` before it's known). The writer rewrites it as often as a working session's cost moves a cent, so a change to it alone wakes the GUI with `Changed::Usage` and the sessions it was for, and only a window showing one of them repaints: one whose pill shows it, or whose open tab panel has its row (`TermWindow::lbterm_shows_usage`). Any other change to a summary still repaints every window. A usage-only change doesn't move the summaries' `generation` either, which keys what's laid out from them (the question colours, the drafts), none of which shows the dollars.
- The pill (`render/context.rs`, `lbterm_context_pill`) is built into the strip's second row by `render/strip.rs`'s `lbterm_prompt_row`, centred on the rail's column as the InMail button is on the first row, with the strip between it and the prompt; a pill wider than the room pushes the prompt on, a column after it. It's the InMail button's pill (`lbterm_strip_pill`), sitting back (hairline white 14%, words 70%), the same under the pointer (it lit to 50% and white, and faded on hover with the strip's buttons, until its click went). The projects pad comes after it on the row, half a column apart, or in its place without it (lbterm/OBJECTIVES.md, "How the projects card is built"). Each paint, `lbterm_context_refresh` (after the strip's content, whose look at the tab's panes it reuses, `StripState::session`) builds the strip again only when the pill's words or its session change.

## The state file

`strip.context` is the pill's words while it shows (`$12.34`, `$–`), `null` without it, and `strip.items` names it `context` (never in `strip.lit`, since it doesn't light). The `menu` kind `context`, the open list, went with the list on 2026-11-08. Each rail row has `cost`, its open line's dollars, empty until known (lbterm/STATE.md).

### What it is

A strip down the window's right edge, in the objectives strip's room (lbterm/OBJECTIVES.md), right of the scroll strip, standing for the open tab's Claude Code conversation's whole context window, top to bottom. From the top: each file loaded into the context, a section each; then Claude Code's own parts (its system prompt, its tools, its skills list); then the conversation; then free space down to the bottom. So how far down it's filled says how full the context is, and each section's height its share of the window. With the pointer on it, the bar itself widens over the terminal to the closed tab rail's width, each section's tokens written on the section (a section too thin for its number shows it in a pane as wide as the bar, beside it); resting on a section slides a pane out from under it listing every section, with buttons that stop a file loading again and a Compact now that compacts the conversation (which loads the memory index and the CLAUDE.md files again without what was removed, though Claude Code attaches a removed file itself again after the summary while it's among the five files it restores).

### The sections, and where each number comes from

Everything is read off the GUI thread: the transcript by the conversation reader (`lbterm_extras::conversation`, on the `lbterm-conversations` thread, into `lbterm_extras::context::Context`, shared with every snapshot as an `Arc`), the window's size by the summaries' thread from `<session>.usage.json` (`lbterm_extras::summaries::Usage::window`). `lbterm_extras::context_bar::sections` makes the list from those two, a few dozen numbers, on the GUI thread only when the context's `Arc` or the window changes.

| Section | Colour | Its tokens |
|---|---|---|
| A CLAUDE.md, the user's, a project's, a `CLAUDE.local.md`, a managed one, or a file one of them imports (`@path`) | grey, the strip's turn-end grey `#8A8A9E` | its content's characters over four (`context::tokens`), times the conversation's scale (below) |
| The memory index (`MEMORY.md`, `AutoMem`) | yellow, the rail's idle yellow `#F2E86D` | the same |
| A memory file Claude read (a `Read` of a file in the memory index's folder, the index itself excepted) | yellow | its tool result's characters over four, times the scale |
| A CLAUDE.md pulled in later (`nested_memory`) from the conversation's own folder or one above it | grey | the same as a CLAUDE.md |
| A CLAUDE.md pulled in from another folder, another project's (`File::elsewhere`) | amber, `palette::AMBER` `#FFBF00`, as the list drew it | the same |
| Claude Code's system prompt | the rail's outline grey `#5E5E6E` | the system prompt's characters over four (the latest main request's `api-request-shape`), times the scale |
| Claude Code's tools | the same | the tools' definitions as JSON, characters over four, not scaled (below) |
| Claude Code's skills list | the same | the latest `skill_listing` attachment's rendered text, characters over four, times the scale |
| A file Claude Code attached again after a compaction's summary (a `file` attachment between the `compact_boundary` and the next turn's `instructions`; since the second round's stage 3) | grey | what was sent, the record's `rendered` (the Read tool's call and the file with its line numbers), characters over four, times the scale |
| The conversation | the edit mark's blue-grey `#7A9CC6` | what's in use less every section above: everything else, the messages, tool calls and results, and the lists Claude Code adds that /context counts under Messages (agents, deferred tools, the environment) |
| Free | the track, `palette::TRACK` | the window less what's in use |

Lachlan saw these colours in the first round's captures and kept them (his 5a of 2026-11-09).

**What's in use** is the last main-chain assistant record's usage: its `input_tokens`, `cache_read_input_tokens` and `cache_creation_input_tokens` together, the size of the request that record answered. That's exact, and it's what Claude Code's own /context reports as its total (64,602 against 64,602 on one of Lachlan's conversations, 55,331 against 55,339 on another where /context counted the messages since; Measured, below). A subagent's records (`isSidechain`) are its own context and are left out, and so is a record with no usage or none in it (an API error's, `isApiErrorMessage`). A compaction (`compact_boundary`) drops it: the next request is a new size (768,777 before one of Lachlan's compactions, 100,564 at the request after it), so until that request's reply is in, what's in use is an estimate, the sections Claude Code loads again plus the compaction's own `postTokens` as the conversation, and the bar says so (`InUse::Compacted`). A resume changes nothing: its records go on in the same transcript.

**The scale.** A file's characters over four is Claude Code's own rough estimate, and it's well short on Lachlan's files: /context, which asks the API to count them, gave his `~/.claude/CLAUDE.md` 9,816 tokens for 26,118 characters, 2.7 characters a token, and his six files together 34,801 where characters over four gives 22,797. So every prose section is scaled by the conversation's own measure of it: the first main request the transcript records (its `api-request` record, `querySource` `repl_main_thread` or `sdk`; the system prompt and tools of the `api-request-shape` it names; the messages of the `api-request-blob` records its `tail` names) over its characters, set against that request's real size, the usage of the assistant record answering it. Its characters over four was 43,405 and its real size 64,194 (1.479), and 34,625 against 50,182 (1.449) on another conversation. Scaled so, his files came to 33,714 and 20,766 against /context's 34,801 and 21,245 (3% and 2% short), the system prompt to 3,781 and 3,702 against 3,282 and 3,277, and the skills list to 7,952 and 7,672 against 7,123 and 7,012. The tools' JSON packs more characters a token (42,887 characters counted as 8,753 tokens, 4.9 a token), and scaled it came out 81% over, so the tools aren't scaled: characters over four gives 10,722 against 8,753 and 8,864. The pane's words call every section but what's in use and free an estimate (`≈`).

Until the first request's reply is in (there's no scale and nothing in use yet) and until the window's size is known, the bar draws only its track, and the pane, if opened, says which it's waiting for. A Claude Code that records no requests never gets a scale, and the pane says so.

**Small sections.** In a 1M window a 3k-token file is about 5 px of a 1,700 px bar, and Lachlan's `later.md`, 303 tokens, half a pixel. So the bar at rest is laid out in whole pixels by `lbterm_extras::context_bar::runs`, from the track's height:

- The filled part ends at what's in use of the window, to the nearest pixel (`context_bar::filled`): 312k of 1M in 1,700 px is 530 px down. The runs fill exactly that, so the line where the filled part ends is always where what's in use puts it.
- Each section with tokens in it is a run, free space none (it's the track the runs are drawn over), and a section with none (an empty file, a conversation the estimates used up) no run either.
- Each run but the biggest is its share of the filled part to the nearest pixel and at least 3 px tall (`config::lbterm::CONTEXT_SECTION_MIN`, at 96 DPI, scaled with the window's), its last pixel the track's (`CONTEXT_SECTION_GAP`), so neighbours read apart: a 303-token import is 2 px of grey and a pixel's gap. The biggest (the conversation, nearly always) is what's left, so the floors' pixels and the rounding's come off it alone, and every other section is within half a pixel of its share or at the floor. In the unit test of Lachlan's sizes the conversation, 510.4 px by its share, is 507.
- When the floors don't fit in the filled part (a short window, a full one early on: 40k of 1M in a 300 px bar is 12 px for six sections), the smallest run with a neighbour of the same colour joins it, the smaller of two such neighbours, again until they fit or no two neighbours are alike: an import joins the grey file beside it, a memory file its yellow index. The widened bar and the pane still name each section; the state file gives the sections of one run its one rect.
- If they still don't fit, the floor is what the filled part has for each, with no gap, and under a pixel each the runs are their shares and the biggest the rest, so some have none: the fill line still doesn't move.

`runs` is a few dozen sums, made only when the sections or the track change (How it's built). Widened (the second round, 4b), the sections are laid out again for the wider track with a floor of a line's height (`context_bar::runs` on the widened track, the fill line where what's in use puts it), and each section's tokens are written on it (`context_bar::numbers`); a section too thin for its number shows it in the thin pane beside the bar, level with it, pushed down from the one above so none overlap, with a hairline to its section (`context_bar::place`, the first round's `labels`). The first round kept each section's height and wrote every label beside it, in a drawer card (At rest and widened, below).

### At rest and widened

At rest it's `width` wide (10.5 pt, 14 px at 96 DPI), as tall as the closed rail (the panel's `layout.panel(false)`), the objectives strip's ring and look: the panes' colour under it from the scroll strip's room to the window's edge, a hairline ring in the rail's outline grey, and inside it the track, the rail's track colour (`palette::TRACK`), inset as the scroll strip's track is (the hairline and 2 px, 8 px wide at 96 DPI) and clear of the ring's round ends. The sections are drawn over the track from its top, square, each its colour down to its gap; what they don't fill is free space, the track showing through. The pointer arriving lights its ring to the pending light at once (the tab panel's `hover`, `palette::PENDING`); after a rest of `widen_delay_ms` (150) it widens to the left, over the terminal, to the closed tab rail's width (the closed rail's own width, `layout.panel(false).w`: `lbterm_tab_panel.rail_width`, 51 pt, 68 px at 96 DPI in Lachlan's config). As built (stage 3) the widening is a drawer: a card of its own left of the bar, from the rail's width's left edge to the bar's left ring line (55 px at 96 DPI), holding the labels, which slides out from under the bar on `panel_open` (its content's offset from its width to nothing inside a clip ending on the bar's left edge, so its left ring line travels out with it and nothing of it ever lies over the bar), and back on `panel_close`. The bar itself stays as it is at rest, its ring lit. The design said the bar's own clip would widen with the labels fading in on `pane_enter` 60 ms after; a clip widening leaves the card's left edge where it ends until it gets there, and words fading in while the edge is still on its way would show past it, so the labels ride out flat inside the drawer instead (the `lbterm-motion` skill: text moves flat, never scaled). Leaving narrows it after `close_delay_ms`, and while the pane is out it stays out until the pane is back in (The pane). The terminal keeps its size: the drawer is drawn over it, so no pane is resized and Claude Code redraws nothing (Lachlan's 7a).

**The second round: the bar widens, not a drawer** (Lachlan's 4b of 2026-11-09, `q4-drawer.png`, with his rule for panes above): hovering the bar, the bar itself widens to the closed rail's width, each section's tokens written on its own section, in place of the drawer card beside it. The first round chose the drawer because the bar's numbers stuck out past its left edge while it widened; the second round designs that away rather than going back to the card: the numbers laid out at the widened width and clipped to the bar's edge as it moves, or faded in once the width has settled. A section too thin for its number shows it as the drawer did, beside it, in a pane as wide as the bar, never a floating card. The widening is then a new motion, traced into FLOWS.md and measured as its own (What it costs, measured).

As built (the second round's stage 4; `render/context_bar.rs`'s `lay_out_drawer`, `Drawer`, `Thin`, `lbterm_context_draw_drawer` and `lbterm_context_draw_thin`; `lbterm_extras::context_bar::numbers`):

- **The widened bar** is the drawer's visual (`Target::ContextBar(1)`, `DRAWER_Z` 105 to 107) holding the bar itself at the closed rail's width: its rect from the rail's width left of the bar's right edge to that edge, ringed in the bar's own ring colour (lit, `palette::PENDING` over the outline, while the pointer's on it) with the bar's corners, its track inset as the bar's is, and the sections laid out again for it by `context_bar::runs` with a line and the gap as their floor (a line is the objectives font's cell height), so the fill line stays where what's in use puts it, to the pixel, and in the usual case every section has a line's room. Then the colour runs, the removed sections' hatching (`hatches`, the same as at rest), and the numbers.
- **The numbers** (`context_bar::numbers`): a section alone in its run whose colour is at least a line tall gets its tokens on itself, from the track's left plus 4 px, its line centred in the colour, dark (the panes' colour) on the light colours and light on Claude Code's darker grey and the track (`dark_on`, by luminance over 0.45); free space gets its own in the middle of the track below the filled part when that's a line tall. The rest are thin: the sections of a run joined with neighbours of their colour (the floors didn't fit the filled part, `runs`' joining) or of a run under a line, and free space with under a line of room.

- **An import's `@`** (since the second round's stage 2). The first round took an import's whole line out, and refused a line with words round the `@` name, since taking the line would take his words with it. Lachlan, asked (Q2 of 2026-11-09), said refusing or cutting were both wrong: "We have to have a better method". The method: an import is an import only by its `@` (Claude Code imports `@path`, never a bare path or one in a code span), so Remove takes off just the `@` before the path, on any line, the line's words and the path staying as plain text; a line that's only the import goes the same way, its path left as a plain line, so no line is ever deleted or refused. A rule, not a dot on the line: a compaction is a moment in the conversation, not a change in what it cost, and names on the line's own row collided at the plot's top right, where the line ends. `after`, the summary's own size, isn't the context after: the system prompt, the tools and the files Claude Code attaches again come on top of it (this conversation's of 2026-11-13: 12k after, 55k next). Colours: his turns the conversation's blue-grey (`#7A9CC6`), subagents teal (`#4FC9B0`), workflows the rail's idle yellow (`#F2E86D`), compactions the turn-end grey (`#8A8A9E`), the line his turns'.
- **Until it's counted** it says `Counting what this conversation has cost…`, and when there's no transcript for the session in the transcripts folder, or it can't be read, it says that instead.

**What each split means and how it's counted** (`lbterm_extras::cost`, the module doc; the Claude project's count as its contract and its exports show it, probed 2026-11-09, so the two agree):

- **A request** is an `assistant` record with a `message.usage`, in the conversation's transcript or a subagent transcript. Claude Code writes one message as a record a content block, each with the message's usage so far, so a record whose `message.id` is the last assistant record's (other kinds of record between them or not) replaces that one's count; one without an id is a request of its own. A message id seen again after another message's counts again: that's the Claude project's rule, kept so the totals agree (PITFALLS 274).
- **Its dollars**, by the model's family (`opus`, `fable`, `sonnet` or `haiku` anywhere in its name, any case; anything else, `<synthetic>` included, costs nothing) at `cost::PRICES` a million tokens, but for a model that lists apart from its family, which has a row of its own in `cost::MODEL_PRICES` (a name holding the row's, any case, with no digit straight after it: Fable 5.2 at 8, 40 and 0.2, a fifth under its family's, and Sonnet 5.5, whose cache reads are 0.1, half its family's): input and output and cache reads at theirs, cache writes at 1.25 times input for the 5-minute cache and twice it for the hour's, by `usage.cache_creation`'s two counts when the record has them, else all of `cache_creation_input_tokens` at 1.25. The prices are the Claude project's (`PRICES` and `MODEL_PRICES` in `@Claude:tokens`, priced as its `priceOf` does; opus 4, 20 and 0.2 on 2026-11-09, Fable 5.2's row since its InMail of 2026-11-11 and Sonnet 5.5's since the next day's, each from a `claude -p` run's `total_cost_usd`, which `cost::tests` holds the count to), copied, and `.claude/tests/cost-prices.test.ts` (in the check, through `workflows.Tests.ps1`) holds the copy to them, both tables and how a model's row is matched, and the fixture's total to their count, so a change there fails LBTerm's check rather than letting the two drift.
- **Your turns**: every request in the conversation's own transcript, `<sid>.jsonl`, every run of it (a resume appends to the same file).
- **Subagents (N)**: every `.jsonl` in the conversation's folder beside its transcript (`<sid>/`, and up to five folders under it, `cost::AGENT_DEPTH`, the Claude project's walk) that isn't under a `workflows` folder, each one subagent; N the ones that made a request.
- **Workflows (N)**: every `.jsonl` under `<sid>/subagents/workflows/<run>/` but a workflow's `journal.jsonl` (not a transcript, whatever it holds), each run's folder one workflow however many agents it ran; N the runs that made a request.
- **Compactions (N)**: the `compact_boundary` records in the conversation's transcript. Claude Code records no usage for a compaction's own request (its summary comes back as a `user` record, `isCompactSummary`, and no `assistant` record or `api-request` carries what it cost; read in his transcripts of 2026-10-28, four compactions), so neither this count nor the statusline's has it, and the pane says so instead of guessing at it. Each one's sizes (`cost::Compaction`): `before` the record's `compactMetadata.preTokens`, and `next` the input, cache writes and cache reads of the first request after it in the same transcript but a `<synthetic>` one (never sent), the Claude project's `before` and `next` for the same transcript (`cost::tests` holds the fixture's split and its own count to the same).
- **The token types** are the usage's own: `input_tokens`, `cache_creation_input_tokens` (cache writes), `cache_read_input_tokens` (cache reads), `output_tokens`; each with its dollars as above.
- **The graph's time** is each request's record's `timestamp` (one without takes the last one before it in its file, or the conversation's start); a subagent's mark is its first request's, a workflow's its earliest agent's.

**How it's read**, with the count on (with it off, none of this runs: the Claude project's file is read instead, as the bullet above says, and lbterm/FLOWS.md's cost pane has both, step by step). The first count of a conversation reads its transcripts whole (his biggest, 13.7 MB with 69 subagent transcripts beside it, is read once, then only what each gains); only lines holding `"assistant"` or `compact_boundary` are parsed. The pane is laid out (`cost::pane`: up to two fills a pixel column of the graph, for its line, and about fifty words, the ones whose room is only themselves measured as they'll be drawn) only when the count (by its `Arc`), the session or its place changes (`LaidFrom`), and each paint while it shows draws what was laid out: its card, a quad a fill, its words through render/words.rs, whose quads are kept while they're the same.
- **Its state** is the window's `cost` in the state file (lbterm/STATE.md): the pill, `count`, `source`, `open`, the pane's `rect`, `note`, `total`, `rows` (each spender's runs, dollars and tokens, its row's rect), `compactions`, `graph`, `steps`, `marks` and `words`; `pointer.over` `cost.pane`, the wait `cost.close`.
- **Checking it**: `cost::tests` (the fixture's total and split, a fold reading on and a message split across reads counted once, a file written again, the prices and the writes, a workflow's transcripts, the words, the pane's layout beside and under, the clock in another zone, the counting note, the pane without a split, each compaction's rule and sizes and where its name goes; ### Turning it on

```lua
rawset(config, 'lbterm_context_bar', {
  -- width = '10.5pt',        -- at rest, its ring included (14 px at 96 DPI)
  -- pane_width = '300pt',    -- the pane (400 px at 96 DPI), less when the window hasn't the room
  -- widen_delay_ms = 150,    -- the pointer rests on the bar this long before it widens
  -- open_delay_ms = 300,     -- and on a section this long before the pane opens
  -- close_delay_ms = 250,    -- and they close this long after it leaves both
})
rawset(config, 'lbterm_context', {
  -- count_cost = false,      -- LBTerm counts each conversation's cost itself, for the cost pane
})
```

`count_cost` (off unless asked for; Lachlan keeps it off, his 2b of 2026-11-10) has LBTerm count what each conversation has cost from its transcripts, for the cost pane the context pill's press opens: the split by what spent it (his turns, subagents, workflows, compactions), the token types under each and the graph over time ("The cost pane"). Off, nothing of the count runs (no transcript read for it, nothing counted or kept), and the pane shows the Claude project's split, `@Claude:cost`'s `<session>.cost.json` in the `lbterm_summaries` folder, laid out as the count is (since round 4's stage 3; round 3's pane said only the pill's dollars and window, and that the split wasn't published). `rawset`, as for `lbterm_context`. It needs `lbterm_context` (its transcripts folder, and the reader it shares with the scroll strip), `lbterm_summaries` (the window's size) and the tab panel (`lbterm_tab_panel.enabled`), whose closed rail's top and bottom it spans, as the objectives strip does; without any of them it takes no room (`render/context_bar.rs`, `on`). It goes in `lbterm_objectives`' room: with both set, the bar takes the room and the objectives strip isn't drawn, which the log says once as the config loads, so a config that still has the objectives strip loses nothing else. Widened, it takes the closed rail's width from `lbterm_tab_panel.rail_width`.

### How it's built

- **Room.** The objectives strip's: `render/context_bar.rs`'s `strip_width` (the bar's `width` and a gutter to the window's edge) is added to the window's right border in `get_os_border_impl` (`render/borders.rs`) beside the objectives strip's and the scroll strip's, and the fancy tab bar takes it back (`fancy_tab_bar.rs`), so the panes, their scrollbar, every card placed from `lbterm_room` and the mouse leave room for it and the window's buttons stay at the edge. With the bar on, `render/objectives.rs`'s `on` is false (its `strip_width` 0, nothing drawn, its mouse handler takes nothing), and the log says so once (`objectives: lbterm_context_bar takes the objectives strip's room`). The room never changes as the bar widens or the pane opens, so no PTY is resized. Every other place that needs the right edge reads it from the border (`get_os_border`), so these two are the only ones that add it.
- **At rest** (stage 2). `paint_lbterm_context_bar` runs each paint after the tab panel (whose layout it spans) and the objectives strip, before the scroll strip, inside render/sides.rs's frame (`lbterm_sides_begin` to `paint_lbterm_sides`, render/paint.rs). It finds the open tab's session as the strip and the context pill do (`render/prompt.rs`'s `target`: the active pane's `claude_session`, else the first pane's in the tab), none while the Conductor's view is open; says it to the reader (`Reader::Bar`, a lock and a compare, only a change reaching the reading thread); then takes the session's snapshot's context `Arc` and its `usage.json`'s window from memory (`conversations::get`, `summaries::get`). Those, the track in whole pixels and the floor and gap in pixels are what the sections were laid out from (`LaidFrom`, the context compared by pointer): only when one differs are the sections made again (`context_bar::sections`), laid out into runs (`runs`, `filled`) and turned into shapes, and `layouts` counts it. Every paint then hands sides.rs four shapes of its own (the panes' colour under it, the ring, the inside, the track) and the kept runs' shapes, all drawn in z-layer 38. Off, it keeps nothing and tells the reader only if it had said a session.
- **Mouse.** `lbterm_context_bar_mouse` runs where the objectives strip's does (`mouseevent.rs`, after it and before the scroll strip's): the bar and the gutter left of it, from the bar's top to its bottom, take every event (nothing under them gets a click), with the default cursor, unless a drag that began elsewhere is carrying on; the ring lights to `palette::PENDING` while the pointer's there, which repaints but lays nothing out. The drawer and the pane take the pointer too while they're out (Widened and the pane, below).
- **Layers.** At rest the bar is drawn in `over` with the strips (z-layer 38, the sides' list of shapes, render/sides.rs), so it fades with the panes on a tab switch as the strips do. The design gave the pane the objectives' list card's z-layers (39 to 41) and the widened bar the detail card's (42 to 44); as built they have z-layers of their own, since `objectives::card_of` sends 39 to 44 to the objectives' visuals whatever's on: the pane's shadow, card and words 101 to 103 (`PANE_Z`), the riding scroll strip 104 (`RIDE_Z`), the drawer's shadow, card and labels 105 to 107 (`DRAWER_Z`), each the visual `Target::ContextBar(0)`, `(2)` or `(1)` alone with the compositor (`context_bar::target_of`, in composited.rs's `lbterm_ranges` before `over` takes every z-layer above 0). Their visuals are children of the compositor's `objectives` group, made after its cards, so over them and under the tab panel. Bottom to top: the panes, `over` (the bar at rest, the scroll strip at its own place), the pane, the scroll strip while it rides, the drawer. (Stage 3 took 51 to 57, which are the tab panel's, `PANEL_ZINDEX` + 1 to + 7, and the bar's arm in `lbterm_ranges` comes before the tab panel's, so the rail lost its ring, its words, its lights and its spinner to the bar's visuals whether the bar was on or not: perf/conductor.ps1 failed on the missing Conductor pad in stage 6's e2e, and stage 6 moved them, PITFALLS 220.) Without the compositor 101 to 107 are drawn in the window's one surface after everything else, upstream's overlays (100) included, so on a window narrow enough for the open panel to reach the pane, the pane would be over it there; Lachlan's config has the compositor on.
- **Widened and the pane** (stage 3, `paint_lbterm_context_widened`, each paint after the bar at rest). Two `lbterm_panel::Hover`s: `widen` (rest `widen_delay_ms`, grace `close_delay_ms`) and `pane` (rest `open_delay_ms`, grace `close_delay_ms`), their motion times `panel_open`'s and `panel_close`'s durations so a pointer coming back while one slides in opens it again at once. The mouse (`lbterm_context_bar_mouse`) gives `widen` the pointer on the bar, the drawer or the pane, and `pane` the pointer on a section (once it's open, on any of them), and a left press on the bar or the drawer opens both at once (`open_now`). The drawer's and the pane's places and words are laid out (`lay_out_drawer`, `lay_out_pane`) only when what they're made from changes (`CardsFrom`: the sections' layout count, the bar's place, the font's cell, the room to the left, the pane's width, the font and its shape generation) and only while widened, kept in an `Rc` and drawn from it each paint, and the last ones drawn are what a closing one slides back showing. Laying out measures each word as `compute_element` lays it out (`lbterm_context_width`: about forty words and a handful a path), a few milliseconds of the GUI thread once per change of the sections while it's out, none on a frame of its own. Each paint while out draws two cards' quads and their words, whose quads are kept while they're the same (render/words.rs): the lit row's band and a lit button change only quads under the words.
- **Motion, the first round** (compositor.rs, `prepare_context_bar`, `Slid`; since the second round's stage 4 the drawer is the widened bar itself and the thin pane a fourth part, At rest and widened's "As built" has the motion as it is now). Put away, the clip is emptied and the next opening starts from out. The scroll strip: while it rides (render/scroll_strip.rs reads `lbterm_context_bar_ride`: its offset, to the drawer's left edge while only the drawer is out and to the pane's while the pane is, and whether it's in a visual of its own, with the compositor and motion on while the offset isn't 0 or it's still gliding), it's drawn at its ridden place into `RIDE_Z` (the panes' colour under its own place stays in `over`), its surface there, and whenever that place moves the slider glides from where it showed to 0, on `panel_open` going left and `panel_close` coming back; when it's back home and still, it's drawn in `over` again and its visual put away. So the strip rides out with the drawer and on out with the pane, each on its own glide from where it is: started in the same commit as theirs, it keeps to their edge but for a retarget's speed. Without the compositor everything is drawn at its place at once, the strip at its ridden place in `over`. The state file's animations are `context.widen` (the drawer), `context.pane` and `scroll.ride`.
- **Its session.** The bar says its session to the reader always, as the scroll strip does (`conversations::Reader::Bar`; the pill's list's `Reader::Context` went with the list in stage 5), so with the scroll strip on and showing the same session it costs nothing more: both follow it through the one reader (with the strip showing another session or none, What a frame costs, below). The session is the open tab's, `lbterm_active_tab()` and `prompt::target`. perf/hidden-output (not on main on 2026-11-09) has the scroll strip follow the panes actually drawn instead (`frame_wait.rs`' `lbterm_pane_to_paint`: the tab drawn last while a held pane's push hasn't come), so once both are on main, during a held tab switch the bar, which fades with the panes in the sides picture, would show the new tab's sections beside the old tab's picture: whichever of the two lands second takes the bar's session from the panes drawn, as the scroll strip does there.
- **Which thread.** Off the GUI thread: the transcript's records (`lbterm-conversations`), `usage.json` (the summaries' thread), the Remove and Undo edits (`lbterm-context-edits`). On it, all from memory: the sections from the snapshot and the window's size, their pixels and labels, the pane's rows, and Compact now's look at the pane's screen, the lines the window already holds, as a voice draft's send looks.
- **What a frame costs.** An idle bar costs no frame: it starts no timer and asks for no repaint of its own. The window repaints for it only when its session's context moves or its `usage.json` does. The reader wakes for every revision of a session it follows (each text block, tool call and result, lbterm-extras' conversation.rs), and says with each wake whether the snapshot's `context` is another `Arc` than the last one it gave (`Conversation::context_change` makes a new one only for a change: a file, what's in use, the scale, Claude Code's parts, a compaction); `conversations::repaint_showing` repaints a window whose scroll strip shows the session for any wake, and one whose only reader of it is the bar (`Reader::Bar`) only for a wake whose context moved. - **The state file** (lbterm/STATE.md, `context_bar`): `rect` (the bar, ring included), `track` (inside it), `session`, `waiting` (what it waits for, in the pane's words, while it draws only its track: `Reading the conversation…`, or `context_bar::Waiting`'s), `in_use`, `window`, `estimate`, `scale` (real over estimated), `filled` (the filled part's end, in pixels down the track), `layouts` (how many times the sections were laid out), and `sections`, each `{kind, path, tokens, rect, colour, button, removed, note}`, `kind` the section's `What::name` (another project's pulled-in file `elsewhere`, the conversation's own `pulled_in`), `rect` its run's (none for free and empty sections), `button` `remove` or none. `pointer.over` names `context.bar`. ### What stays LBTerm's when a harness takes Claude Code's place

Lachlan asked on 2026-11-14 that each feature be weighed for where it belongs: LBTerm, or the harness meant to take Claude Code's place. In the harness's design the harness owns a conversation and its process, LBTerm draws the conversation in a pane, and a feed on a pipe carries the session's entries to LBTerm. Its "The context bar" section designs the bar's controls for a harness session. For the bar as built:

- **LBTerm's for good**: everything drawn and moved. That's the bar at rest and widened, its runs and numbers, the thin pane, the sections pane, the scroll strip's ride, the pill and the cost pane, their motion, and the buttons as things pressed. A harness has no window.
- **The conversation's owner's**: what's in the context, and what a press does to it. For a Claude Code tab LBTerm works out the parts itself from the transcript (`lbterm_extras::context`, the scale, every `≈`), because Claude Code states none of it. A harness states the context by part on its feed, with measured numbers and each block's state (in the context, cleared, compacted, dropped). The two join inside LBTerm as two producers of the one snapshot the bar draws from (`Context`, then `context_bar::sections`), and the Claude Code producer is deleted when Claude Code tabs retire. So the transcript reading isn't extended: when the bar needs a fact Claude Code doesn't record, it waits for the harness rather than estimating it.
- **Compact now** is LBTerm's button and the owner's action. Today it types `/compact`, and reads the tab's light and the screen to know when it may. On a harness tab it asks the harness to summarise, and the harness says whether it can do that now. The harness's design has four controls there: clear results older than a point, summarise up to a point, leave out, and take out now. The last two are what Lachlan first asked the bar for ("buttons to remove that context from the memory right now"), and a harness can do them for one conversation alone, which Claude Code can't (The buttons, above). Of the four, LBTerm holds "clear results older than here", and "leave out" wherever it ends in a clearing, as drawn and not offered (LBTerm's word of 2026-11-13, after a request was refused straight after a clearing), until the two conditions the harness design gives for lifting that hold are met (ToolBelt's loop/DESIGN.md, "The context bar"), so not all four come to the bar when the harness does.
- **Remove and Undo** are LBTerm's either way. They edit the memory index or the file that imports a file, on disk, which changes what every later session loads, not this conversation's context. A harness tab's marks for one conversation would come beside them.
- **The cost pane's split** is the Claude project's (`cost.json`), which is written for a harness session too. LBTerm's own count (`count_cost`, off) stays for someone without that split (Lachlan's 2b) and isn't made to read a harness session.
- **Compact now dim while Claude compacts** comes from Claude Code's hooks (the light's PreCompact). A harness states compacting as its session's state.
