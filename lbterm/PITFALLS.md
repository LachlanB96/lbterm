# Pitfalls

Traps LBTerm's work has fallen into, written for the next person to change the code. They come from the independent reviews of LBTerm's tracks (from 2026-10-29: eleven reviews, 5 high findings, 22 medium and 60 low). The fixes are in git, on the branches the reviews read. What stays here is the lesson: what to check so the same kind of bug doesn't come back somewhere else.

- **Building:** before changing code, read the sections your change touches and check it against each trap that fits.
- **Reviewing:** check the branch against them. A finding that teaches something not already here is added by the fix-up, in the same commit as the fix: the trap in general, the example, and the branch it came from.

CODEMAP.md says where the code named here lives.

## Repaints and wakes

1. **A change may be showing only because some other repaint carried it.** Removing or skipping a repaint unmasks everything that rode on it, so before cutting one, list what that frame also showed. perf/conductor-inbox stopped repainting for pane output under the Conductor's view. A tab's `claude_status` change had only ever shown through that output repaint: its alert runs `update_title`, which repaints only when the tab bar changes. So the rail stopped following it. The same review found a notice whose end had only been drawn by those repaints. Every change a window shows (a user var, a title, a notice running out) asks for a frame of its own. (high)
2. **A check can pass because an earlier step painted.** title-storm.ps1's background-title check ran straight after a step that changed the open tab's title, and that step's frames painted the rail. On its own, a background tab's new title never reached its row. Each check makes its change alone and waits for the frame that change asks for.
3. **A wake already pending can swallow a later one.** A guard like "a wake is due sooner, skip" loses the later deadline once the sooner one fires, as the Conductor's view did with a second notice. Re-arm from each paint (the paint asks again), or schedule the latest deadline when the timer fires. `lbterm_extras::pace` once kept `armed` after its auto-reset timer had fired, so a wake put back at or before it waited on a timer that would never fire again.
4. **A loop that's told once must never wait while it still owes something.** `lbterm_flow::Pending` rings a connection once until it next waits. dispatch.rs's loop stopped pushing at `OUTBOX_LOW`, the socket took the whole outbox at once, and the loop waited with panes still owed: a hidden tab's last screen, title and `claude_status` never arrived. After every write, go round again while something's owed and there's room. Test with a socket that takes everything at once. (high, perf/mux-server)
5. **Merging and reordering are safe only for messages that describe state.** A push of a pane's changes replaces the one before it, so it can be merged or sent first. A focus change, a clipboard, a pane removed and a bell are events whose order and count matter. lbterm_backlog's first lane took every PDU for the typed pane, `PaneFocused` included, so a quick switch back could end on the wrong tab. `note_alert` keeping only the latest alert of each kind turned two bells into one. Only state-describing items jump the queue or merge.
6. **`#[track_caller]` doesn't pass through `&dyn WindowOps`.** A virtual call is credited to the impl's own line. A frame asked for by `context.invalidate()` in a key, mouse or rail handler shows in the counters as `window.rs`'s `invalidate()`, not as its caller. Call through a helper of your own marked `#[track_caller]`, or read those credits as unnamed.
173. **A poll cut back unmasks what only its answer brought.** Like a repaint (1), a poll carries more than it was kept for. perf/mux-client stopped pushes and input bringing a unix domain pane's poll back to every 20 ms, since its server pushes every change. But the server answers a resize or a zoom with no push, and the poll's answer had been how the window learnt the pane's new size and the sequence number its rewrapped lines carry: without it a quiet pane split or zoomed fetched a line and painted 60 times a second for good (`perf/cli-repaint.ps1 -Mux`). The lag indicator's wait (`is_tardy`) was the poll's interval too, so a key after a quiet spell would have waited 30 s to be called late, not 3. Before cutting a poll, list what reaches the window only through its answer, and what reads its interval. The poll a resize brought back wasn't sure to go either: it goes with the next frame that draws the pane, once 20 ms have passed since the last, so a drag's last size or a tab out of view could go without it, which mattered once the window took the server's word for which rows a resize changed (perf/mux-client's close-pane stage): since then the resize asks for the push itself once the server has answered it, and a resize brings no poll back (167). (perf/mux-client)
45. **Every way a character arrives takes the fix.** perf/key-latency stopped a typed key's own frame holding its echo's a pacing period, but a dead key's or an IME's composition ends with a frame asked for just before Windows sends the composed character, which held that echo the same way. A change to what typing costs goes through each way a character reaches a pane: keys, key assignments that send text (SendString, SendKey), dead keys, IME commits, pastes, the cli's send-text. (perf/key-latency)
79. **A frame asked for waits until the main thread's task queue has drained.** `run_until_message` (`window/src/spawn.rs`) stops draining only for input or a posted message (`os/windows/work.rs`, `message_waiting`: GetQueueStatus with QS_INPUT and QS_POSTMESSAGE, asked every 0.5 ms), never for QS_PAINT, and Windows makes a WM_PAINT only when nothing else waits. So anything that queues a task per push (the backlog's takes, a notice's two hops a window, a poll's answer) holds back the frame that would show it, and on main only `lbterm_backlog`'s `GAP_AFTER` lets a paint in under a backlog. Before adding a task per event on the GUI thread, count what it puts ahead of the frame. (the pane-output flow, FLOWS.md rows 53 and 68)
80. **A task spawned on the GUI thread while it drains wakes the loop for nothing.** Every spawn sets the spawn queue's event, so a task that queues another (a take's notice, the subscription's hop) leaves the event set after the drain, and the loop's next MsgWaitForMultipleObjects returns at once and finds nothing to do. `metrics`' `gui.wakes` counts those turns, so wakes overstate how often anything woke the thread. Worked out from the code, not measured: a count of waits shorter than about 10 µs would say how many (the pane-output flow, FLOWS.md row 53).
81. **`Window::notify` called on the GUI thread is a task hop, not a call.** It goes through `Connection::with_window_inner`: a Promise and its Future made and thrown away, and another spawn, so whatever is put behind it waits its turn in the queue (up to 7.7 ms behind a take in the pane-output flow's run 3), and a mux notice reaches its window in two hops, the second only because subscribers run inside `Mux::notify` and can't reach the TermWindow. Count it as a task when costing a path, and reach the window's code directly where the caller is on the GUI thread already and holds nothing the window takes (the pane-output flow, FLOWS.md rows 64 and 65).
139. **A size the window finds for itself during a drag is the drag's.** The paint checks the client rect against the layout (`TermWindow::lbterm_follow_window_size`) and lays the window out again when they differ. During a drag driven from another thread (a test's SetWindowPos; another program's) Windows changes the rect before WM_WINDOWPOSCHANGED reaches the window, so a paint between them sees the drag's next size first, and it called `resize` as a size outside a drag: every tab took 7 of a drag's 40 sizes, with the tab in view the only one meant to (perf/mux-client's `lbterm::resize` log). Whatever applies a size passes on whether a drag is under way (`Behind::dragging`), and a test of a drag sends Windows' WM_ENTERSIZEMOVE and WM_EXITSIZEMOVE around its sizes (`Send-SizeMove`), or what it drives isn't a drag to the window. (perf/mux-client)
140. **The message loop's drain stops for input and posted messages only.** `run_until_message` asks for QS_INPUT and QS_POSTMESSAGE, so a paint, a timer and a message another thread sends (SendMessage, and a test's SetWindowPos) wait until the task queue runs dry, and a queue that tasks keep feeding keeps the thread from them for as long as they come: Windows calls a window not responding once its thread has taken no message for 5 s, and DWM puts its ghost over it (PERF.md, finding 33, on builds where a take of hidden tabs' pushes held the GUI thread for seconds). A task on the GUI thread is short, or it's a frame or a sent message held behind it; metrics' `gui.longest_drain_ms` and `Start-HangWatch` say how long the thread went (perf/mux-client: 442 ms in one task on main's build with six tabs flooding behind a full-speed writer, 4.4 ms on the branch's). (perf/mux-client)

134. **A file written as often as a cost moves must not wake what every other change wakes.** The summaries' thread repainted every window for any change to a summary asked for, and bumped `generation`, which keys the question colours' and the drafts' layouts. `<session>.usage.json` changes a cent at a time while a session works, so taking it as one more part of a summary would have painted every window and laid out every pane's question colours again for each cent, the tab in view or not. A part that changes that often wakes with what changed (`summaries::Changed::Usage` and its sessions), repaints only the windows showing it (`TermWindow::lbterm_shows_usage`), and leaves `generation` alone; perf/context.ps1 holds that a cost the window doesn't show paints nothing (lbterm/CONTEXT.md, "How it's built").
205. **What reads a part that wakes only the windows showing it must say it shows it.** A change to a session's `usage.json` alone repaints only the windows `TermWindow::lbterm_shows_usage` names (134), which asked for the context pill's session and the open rail's rows. The context bar reads the same file for the window's size, so a bar that wasn't asked for there would say `Waiting for the context window's size` until something else painted, and with the pill on, as in Lachlan's config, its repaint for the same session would carry it (1), so every test with the pill on passes. `lbterm_shows_usage` asks the bar's session too (`lbterm_context_bar_session`, render/context_bar.rs); a new reader of a part woken this way (`Changed::Usage`, a reader's `repaint_showing`) adds itself to the window's answer in the same change.
219. **A slide or a fade coming in needs no frame at its end; wake for one only when something is going.** DWM plays the motion, so the frame that started it already drew everything that shows once it's done; only something going away (a card sliding back, drawn from its last frame until it's in; the scroll strip riding home into its own place) changes what a frame draws when it ends. A paint that happens while an opening still moves reads it from the compositor (`*_showing`'s settle time) and, woken for that, paints the same again. The context bar did: the pane's paint 150 ms into the drawer's slide woke for its end, and that frame for the pane's, two frames of seven a pane's opening (the budget runner's `context-bar-pane-opening`, its requesters naming the bar's wake 4 times a run where the rests need 2; 5 since). The tasks card already had it right (`if !open && fading { settles }`). When a feature asks the compositor what still moves, wake for the time only on the going side, and read the frame requesters of an action that plays motion: a count above the frames that draw something new is one of these.
215. **A strip item whose mouse events a handler takes before the tab bar's own gets no repaint as the pointer comes and goes, unless that handler asks for one.** The box model draws an item's look under the pointer (`hover_colors`) and render/hover_fade.rs starts its slot's fade only at a paint, and the tab bar's own handling (`mouse_event_tab_bar`, `last_ui_item`) is what repaints for an arrival; a handler earlier in mouseevent.rs's chain that takes the event skips it. The projects pad on the strip's second row (render/projects.rs, whose `lbterm_projects_mouse` runs right after the strip's card so a rest on it opens its card) didn't light under the pointer, and its `projects.open` wait wasn't in any state file, until its card opened 1.5 s later and that repaint carried both (pitfall 1). It keeps `ProjectsState::on_pad` and repaints when it changes. A test of such a look reads `strip.lit` in the first frame after the pointer comes (perf/projects.ps1, step 2).
135. **A menu that takes a release must end its press's capture.** Every press that reaches `mouse_event_impl`'s own arms sets `current_mouse_capture` (`capture_mouse`), and the release's arm clears it. A strip button's click opens its list (the InMail list, the agenda's, the prompts', the context pill's) on the press, and the list, first in the chain of menus that take every event while they're open, took the release before that arm ran. Closed with Esc, the window still held the capture: the tab panel, the objectives and the scroll strip take a capture for a drag under way (`busy`), so none of them answered the pointer until the next click anywhere. perf/context.ps1's open panel after the pill's list caught it. The chain's `if` in `mouse_event_impl` now ends the capture for any release one of them takes; a new handler that takes events whole goes in that chain, not before it.
183. **State held until an animation ends has to be let go when there's no animation.** If the only wake that lets a hold go is asked from a fade's end, then with motion off, or anything else that puts the end state in at once, there's no end to wake at, and the hold lasts until some unrelated paint: in an idle window, never. When a hold or a wait keys off "until X fades", give it a release for X gone with no fade: a paint straight after the frame that removed it. feat/new-tab-menus' `Hover::hold` (the rail held still under a menu's card) was let go only by `tab_panel_hold_wake` at `Compositor::menus_fading_until`'s end; with motion off the closing card is settled at 0 with no fade (`Step::Set`), so no wake came, and the review's probe, the pointer resting on the closed rail's pad, saw the rail still closed 4 s after Esc, where with motion on it opened 131 ms after. Since 2026-11-08 `tab_panel_hold_wake` asks for a paint at once when, after the frame, no card shows and none fades; menu-keys.ps1's step 12 holds it with motion off (feat/new-tab-menus).
233. **A second consumer of a reader that wakes on every change gets every one of those wakes, even if it draws only one part of what's read.** Before subscribing a feature that draws a slice (a count, a size) to a reader that wakes per record, have the reader say which slice changed, wake it only for that, and say in the docs which changes paint. The context bar tells the conversation reader its session all the time (`Reader::Bar`), and the reader woke the windows showing a session on every revision (each text block, tool call and result), so a window whose scroll strip wasn't showing that session started painting a frame per record; the bar redraws only when the context's `Arc` changes, while CONTEXT.md said it repainted "once a reply step at most". Now each wake says whether the snapshot's context moved (`Arc::ptr_eq` on the reading thread) and `conversations::repaint_showing` repaints a bar-only window only then (feat/context-bar's review).
249. **A message that moves only when something ends must set the wake for then.** The hub's `conductor.focus` letting go of a session changes nothing shown at once: the session's outline still shows for its least lap (`ACTING_AT_LEAST`, 1.4 s) and its linger (400 ms), so `Focus::set` says unchanged and `conductor_hub::set_focus` repainted nothing. The rail's wake for the hub (`due.1`, from `next_change`) is only asked at a paint, and the last paint was while the session was still named, with no end: none. So the outline stayed until some other paint came, in an idle window for good, and since landing 4 so did the Conductor's pad's spectrum with its hues turning in DWM. perf/conductor.ps1's let-go check had passed because it judged a picture taken 2.5 s on, and something painted the window in that time (not traced: `Get-Shot` posts the test's held pointer when one is held, `Send-HeldPointer`, and the rows' clocks wake the rail); landing 4's wait on the state file for the pad no longer lit timed out at 5 s with the window settled. Since 2026-11-09 `set_focus` compares `next_change` before and after, and when only that moved it sets every rail's wake for it (`TermWindow::tab_panel_hub_wake`) without a paint now. Any message that changes when something goes rather than what shows (an `until`, a let-go, a resend with a later end) does the same, and a test of a let-go waits on the state file, never on a picture, which can paint (2, the same trap from the test's side) (feat/rail-landing-4).
251. **A value kept in a rail row that changes more often than what the row draws repaints the window for nothing.** `lbterm_panel::claude::Row`'s equality is what decides whether a tab's new OSC 7501 record or title moves its row (`programs_move_row`, `titles_move_row`, `moves_row`: `row(a) != row(b)`), and a moved row repaints the whole window. A program's record carries its own time (`Program::updated`), which a finished session's row takes as its `since`, and Claude Code and claudehook's `bg/` records send it again with a newer time while nothing shown changes (the age reads "12m" either way). Stage 4 of feat/rail-landing-4 (2026-11-09) needed that `since` for Shift+Forward's oldest-waiting tab; put in `Row`, every such record would have repainted. So it stays out: `row_since` hands it back beside the row, `waits_on_you` reads it at the press, and `row` drops it. A field added to `Row` is something the row draws (both looks name every field, `look::looks`); a time, a count or anything read only by a choice made elsewhere is worked out where it's needed.

315. **A rail row reads a tab's titles only through `titles_read`.** `lbterm_panel::claude::titles_move_row` answers "no" without making a row when the old and new titles read the same by `titles_read` (the tab's title stripped of glyphs, the active pane's program name, the first Claude glyph of the tab's title then its panes'), so Claude Code's ◐ and ◑ cost three strips and two glyph checks, not a Tab cloned and two to four rows. `row_since` reads the titles through it and nothing else. A row that reads anything more of a title (another pane's words, a second glyph, the title's length) must read it through `titles_read` too, or a title that changes the row is taken for one that doesn't, and its background tab's row keeps the old words until something else paints it (the window's mux subscription drops the alert that would have repainted it: titles.rs). `titles_a_row_reads_the_same_never_make_another_row` checks the shortcut against the full compare (perf/background-titles).

381. **A row's next change is the soonest of everything on it that counts time, never the last one set.** `lbterm_panel::claude::row_since` folds each clock the open row shows into `Changes::age`: its age, the time since Lachlan's last prompt (`text::since`) and a stuck reply's minutes. The stuck arm set `wake.age` by assignment, which was right while it was the only clock a working row had, and once the prompt's time came (feat/rail-last-input, 2026-11-14) it would have dropped that sooner moment, so a stuck row's time could still say "4 min" for most of a minute after it had turned five. Each now takes the minimum with what's there (`a_tabs_row_says_how_long_ago_he_last_prompted_it_once_its_known` holds the stuck case). A new clock on a row goes in the same way, and in `Changes::step` instead when the closed rail shows it.

## The Conductor's view and hidden panes

7. **The Conductor's view covers the panes, but they stay in the layout.** Anything that asks whether a pane is visible, on screen or in the last frame gets "yes" for a pane under the view. Two of the five high findings were this:
   - output under the view (1 above);
   - a tab switch while the view was open: the old tab's panes, never shown, were dissolved from full opacity, so a hidden tab flashed up and faded (feat/tab-switch-fade).

   Ask whether the view drew over them in the last presented frame.
8. **A background tab is in the mux but not on screen.** Its output paints only its rail row, its title has to reach the rail on its own (2), and its last push is the easiest to lose (4). Lachlan runs eight or more Claude sessions, most in background tabs: test with tabs in the background, not only the open one.
229. **"Hidden" names three things, and a session hidden from the Conductor is none of the others.** A pane is hidden when the Conductor's view covers it (7) or its tab is in the background (8, perf/hidden-output's "hidden output"), and since New-tab landing 3 a Claude session is hidden from the Conductor when its button.json's `hidden` names it (`Said::hidden`, `conductor::Hidden`; NEW-TAB.md, section 8). That last says nothing about the screen: such a session's tab is often the open one, its output paints as any pane's, its rail row still turns orange when it waits on him, and its digests, labels, objectives, tab links and questions go on. Code that asks whether a pane is on screen must never read the Conductor's list, and code for the Conductor's list must never skip a pane for being off screen; name the Conductor's in full (`hidden from the Conductor`, `conductor::Hidden`) wherever the other two are near.

236. **A pick another program answers through a state file is answered only by a write made since the pick.** The tab menu's Hide from Conductor waits for the Conductor's button.json to list the tab's sessions (NEW-TAB.md, section 8), and Show for it to list none. Judged by the list alone, a Show picked while the Hide before it waits reads as done at once, from the file as it was before either (hiding nothing, as a show asks): the pad glints, then the row flicks to hidden and back as the Conductor carries out the hide and then the show. So `conductor::hide::Pick` keeps the file's `updatedAt` as it was picked (`then`) and `Picks::settle` takes a pick as done only from a file with another one, which the Conductor writes fresh on every `hide` and `show`, already so or not. A new wait on a file like it (a seat's answer, a links file's) needs the same, or its own answer's id, as the Conductor's `--result` gives its handler. Since the review's fix-up no row is offered while a pick waits (244), so the Show-while-a-Hide-waits case can't be picked any more; the case left is a file that already says what's asked as the pick is made (the menu open while a hide run by hand wrote it), and `then` still keeps that from counting. (feat/conductor-hide, stage 2 of New-tab landing 3)
237. **On the Conductor's view the last place pushed under the pointer wins, so a button inside a row that opens something is pushed after the row.** `seat::layout::Scene::hit` looks through `hits` from the end, and a session's row pushes its own place (`Target::Session`, opening its tab) once its lines are drawn, at the end of its loop. The Hidden group's Show sits on the row's line, so `layout.rs` keeps its rect and draws it (`Builder::button`, which pushes its hit) only after the row's `hit` and card: drawn where it's laid out, as the other buttons are, a press on Show would open the tab instead. A new button on a row (a card's, a session's) goes after the row's own hit the same way; `sessions_hidden_from_the_conductor_fold_into_a_group_at_the_foot_with_show` holds Show to it by hit-testing each button's middle. (feat/conductor-hide, stage 3 of New-tab landing 3)
238. **`Ui::folded` holds the side's sections turned from how they start, not the folded ones.** The Hidden group starts folded (`seat::layout::FOLDED_AT_FIRST`), every other section open, and a press on a heading toggles its name in `Ui::folded` either way, so for the Hidden group a name in the set means open. Ask `Ui::is_folded(key)`, never `ui.folded.contains(key)`: the second reads the Hidden group backwards, open as folded. `Target::Reveal` (the folded side's buttons) removes a name to open its section, which is only right for one that starts open; none of its sections starts folded today, so a section added to `FOLDED_AT_FIRST` that the folded side can reveal needs Reveal to set it open through `is_folded` instead. (feat/conductor-hide, stage 3 of New-tab landing 3)

## Output on a mux domain

What tracing pane output on a mux domain, from the program's write to the frame (FLOWS.md's first traced flow, 2026-11-04), found waiting for the next change to that path.

82. **The parser's coalescing sleep doesn't end when more output arrives.** `Coalesce::wait` (`mux/src/lbterm_wait.rs`) sleeps all the time left on its high-resolution timer and asks the socket after, so a lone echo always waits the whole `mux_output_parser_coalesce_delay_ms` (3 ms, and 0.3 to 0.75 ms of slack, measured). A change that makes it wake on data has to wait on an event (WSAEventSelect or the like) together with the high-resolution timer: WSAPoll's own timeout is whole milliseconds and ends on the 15.6 ms tick (30; PERF.md finding 67). (the pane-output flow, FLOWS.md row 10)
83. **Synchronized output has no bound.** After DECSET 2026, `parse_buffered_data` holds every action until DECRST 2026 or DECSTR, with no time limit and outside the 128 KB cap: a program that dies mid-frame leaves its pane showing nothing new, and a long synchronized stream grows `actions` without limit. Upstream's code too. Claude Code asks DECRQM 2026 and turns synchronized output on when the status is 1, 2 or 3, and LBTerm's terminal answers 2, so whether its frames come through ConPTY wrapped decides how much rides on this (FLOWS.md, "Not traced yet"). Give a hold a deadline and a size before relying on it (the pane-output flow, FLOWS.md row 9).
84. **The coalescing deadline outlives a synchronized frame.** A frame that starts during a coalescing wait is flushed inside the parse's callback without clearing `deadline`, so the next plain batch finds a deadline already past and goes to the terminal with no coalescing at all. Clear every per-batch state on every path that flushes (the pane-output flow, FLOWS.md row 9).
85. **Blocking calls run under a pane's terminal lock.** Two places on the output path do it. The parser answers queries with the lock held: replies to DSR, DA, DECRQM, OSC 7501's query and kitty's notification queries go to the pty's input pipe by a synchronous WriteFile from inside `Terminal::perform_actions`, so a conpty host that stops reading its input would hold the lock, and with it the server's main thread at that pane's next push. And the server's push asks the process list with it held: `LocalPane::get_current_working_dir` is `self.terminal.lock().get_current_dir().cloned().or_else(|| self.divine_current_working_dir(policy))`, one expression, so the guard, a temporary of it, lives through `or_else`, and for a pane with no OSC 7 cwd the job query (QueryInformationJobObject), a ReadCwd's OpenProcess and ReadProcessMemory, or on the pane's first ask a whole process walk run on the main thread while that pane's parser waits. A guard taken in a method chain is held to the end of the expression, whatever follows it: bind what's read in a `let` first (`get_title` does). Don't add a blocking call under a pane's terminal lock; queue the bytes and write them once it's let go (the pane-output flow, FLOWS.md rows 13 and 27). Since perf/mux-client's flood build the server's push no longer does it: it reads the terminal in one go and lets it go before it asks the process list, and takes the cwd as listed, read on the `lbterm-procs` thread (`Pane::lbterm_read_for_push`, `Ask::Listed`); every other caller of `get_current_working_dir` still goes through the one expression.
86. **One terminal lock a getter isn't a snapshot.** `compute_changes` reads the seqno, the changed rows and the lines under separate locks (nine for a push that sends) while the parser goes on, so a line changed in between goes out now and again in the next push, and the cursor can be older than the lines. Under a flood each lock can wait out a whole batch (`dispatch.rs`: 1 to 3 ms a push). Read what a push needs under one lock (the pane-output flow, FLOWS.md rows 27 to 30). Since perf/mux-client's flood build a local pane's push reads its state, the seqno and the changed rows under one lock (`mux/src/lbterm_push_read.rs`), and the lines under a second, so a line changed after the read but before the copy still goes now and again in the next push; a new value read beside the others belongs in `from_terminal`, not in a getter of its own.
87. **A step before the codec can be undone by it.** `lbterm_push::lines_to_send` compresses each line it copies, and `SerializedLines::from` then calls `cells_mut_for_attr_changes_only` on every line, which turns it back into cells (`make_cells`): the compression bought nothing, and the rebuild alone was 4 of the server main thread's 24 busy samples in the trace's run. Anything done to a line for the wire's sake (a compressed form, cached data) has to survive `SerializedLines::from`, or it's wasted (the pane-output flow, FLOWS.md rows 30 and 32).
88. **The server pushes a tab out of view exactly as it pushes the one in view.** Each round takes the pane last typed into first and the rest in the order they were owed, so under load a pane in view that nobody is typing into (a session being watched) waits behind hidden tabs' pushes in a round. The server knows each mux window's active tab (SetFocusedPane) but doesn't use it for pushes (8; the pane-output flow, FLOWS.md row 25).
89. **In the GUI, `Mux::notify(PaneOutput)` runs its subscribers with the client pane locked.** `apply_changes_to_surface` calls it holding `ClientPane.renderable` (a parking_lot Mutex, which isn't reentrant) and its RefCell's `borrow_mut`, so a subscriber that reads that pane there and then (`get_lines`, `get_dimensions`, `apply_hyperlinks`, `get_metadata`, the title) deadlocks or panics. A subscriber may read only the mux's own maps (perf/mux-client's `lbterm_hidden_output` reads `get_pane`, the active tab and `contains_pane`), an atomic the pane keeps for it (`ClientPane::lbterm_rows_changed`, 176) or queue work (the pane-output flow, FLOWS.md row 61).

And a window that said only pushes whose seqno moved would miss a round push of a title alone, which keeps the seqno of the push before it and is waited on again. So each push applied is noted as it's applied, and every path that takes one says it (wezterm-gui's termwindow/panes_drawn.rs, wezterm-client's lbterm_drawn.rs). A new place a pane's push can land without a frame reading it (a new overlay kind, a view drawn over the panes, a paint skipped) says it too.
235. **A leave that lasts until the other side has read something made after an event has to name the first thing made after it, not the latest.** The server's input rule lets a pane typed into go unpaced until a frame has read a push made since the key (`lbterm_flow::Pending::input`). Stage 4 ended the leave at a word for a push at least as new as the last one sent, and under a flood the pushes go on faster than the frames say, so that word never came: one key early in perf/mux-pace.ps1's flood left the pane unpaced to its end (200 to 287 pushes a second against 56 to 59 frames). It keeps the first push's seqno after the input and ends at a word for it or later; a test that only ever names the latest push in its words (as stage 4's did) can't see it.
242. **A compare meant to catch a resize compares the size alone, not `RenderableDimensions` whole.** The struct carries `physical_top`, `scrollback_top` and `scrollback_rows` beside the size, and they move with every line a pane scrolls. The names path of a held pane (`lbterm_out_of_view`, sessionhandler.rs) sends a title or folder change alone with the size as last pushed, unless the pane's size has changed since (a resize answered, its push to come), when it sends a real push; perf/hidden-output's fix-up wrote that test as `dimensions != self.dimensions`, so a pane that scrolled out of view and set its title had a real push for every title, which ended its hold, and its next output a new PaneHeld. Its unit test's pane didn't scroll. mux-flood's floods set a title a block: on the branch's build of 2026-11-09 the window took 3,404 PaneHeld and about 3,500 pushes with lines in its 15 s flood, and each ended hold queued a `hidden_scan` of the pane on the GUI thread (2,898 of them, 6.1 s of the 15, about 2.1 ms each), so the GUI thread spent 525 and 580 ms a second there against main's 193 and 201, and with a flood in view drew 40 to 45 frames a second against main's 59 (FLOWS.md's run 15). No earlier run saw it: mux-load's Claude-like tabs set no title while they print, and mux-flood ran only as a behaviour check, which passed. Fixed in perf/hidden-output's sixth stage (`lbterm_same_size`: columns, rows, pixels and dpi; tests `a_held_panes_titles_go_alone_while_it_scrolls` and `lbterm_same_size_is_the_size_alone`). A test of a held pane's path prints enough to scroll it.
246. **A frame that draws a pane doesn't always read that pane, and WezTerm's two kinds of overlay differ in which.** A tab overlay (`tab_state(tab).overlay`, `assign_overlay`: the launcher, the tab navigator, the prompts and confirmations of a tab or the window) replaces the whole tab with its one pane, so a frame reads none of the tab's. A pane overlay (`pane_state(pane).overlay`, `assign_overlay_for_pane`) takes one pane's place in `get_pos_panes_for_tab`: copy mode, search and quick select report the id of the pane under them and read its lines through their `delegate`, so the frame reads that pane through them; the close-pane confirmation is a pane of its own, with its own id, and the frame reads it instead. So code keyed on "the frame read this pane" (a downcast to `ClientPane` in `paint_pass`) resolves a pane overlay that reads the pane to the pane under it, and code that asks "does this window show and read pane X" tells the three apart: a tab overlay covers it, a pane overlay of its own covers it, copy mode, search and quick select read it. When listing the paths that must say a word the other side waits for with no bound (234), list every way a window can show a pane (the open tab, a zoom, a tab overlay, each kind of pane overlay, the Conductor's view, a minimized window, a switch's kept frames) and run each in a test window. perf/hidden-output's pace (What could go 12) asked only the tab's overlay (`lbterm_pane_shows`) and noted only ClientPanes (`lbterm_frame_read`), so with copy mode or search open over a printing pane in view the server waited for a word that never came: the review's probe on the stage 6 build (2026-11-09) saw 1 push and 0 PanesDrawn in 6.1 s and the window's copy 111 lines behind the program, with the pane's user vars held with it, where main's build took 22.9 pushes a second; MUX.md had listed copy mode and quick select as covered panes. Fixed in perf/hidden-output's fix-up (lbterm-extras' `overlays::shows` and `reads_under`, `panes_drawn.rs`'s `lbterm_under_overlay`); perf/mux-pace-paths.ps1 runs every path. The state file's `overlay` names only an overlay with an id of its own, so it's `null` under copy mode, search and quick select (STATE.md).
250. **State a window mirrors from its server is set only where it's kept: the window asks, and the server's word back sets the window's copy.** Upstream's tab title is the pattern to avoid: a window sets its local tab and its domain's subscriber sends the change on, and the server's push back sets the local tab again, which notifies and sends again; for a title, setting the same words is no change, so it settles. For a flag that flips (a tab's parked flag, Lachlan's 8a), a park and an unpark a moment apart each come back after the window has moved on, set it to the old value, send that, and the two chase each other for good. NEW-TAB.md's design for 8a said "sent by the client domain's subscriber, as for TabTitleChanged"; as built, `ClientDomain::lbterm_park` only asks (codec's TabParked) and the local tab takes its flag from the server's push alone (`lbterm_remote_tab_parked`), as every other window of the server does, and the subscriber does nothing with `LbtermTabParked` (lbterm/MUX.md, "Parked tabs"). A notice that tells a peer what it did itself is an opening for a loop (159); a flag set from two sides needs one owner. (feat/rail-landing-4)
311. **A names push's seqno is the last push's only while the server holds the pane; otherwise it's the server's read of it.** `lbterm_out_of_view` (sessionhandler.rs) sends a pane out of view's title and folder with the cursor, size and flags as last pushed, but when the pane printed nothing a push compares and no hold was said (`held` with `lbterm_held` None and nothing but the seqno moved, as a title alone does: every `advance_bytes` moves the seqno), it moves its own seqno on to the read's and the names push carries that: the client's copy is the pane's as of it. So a tab printing nothing but its title (title-storm's stand-in tabs) sends a newer seqno with each, and one held since its last push sends the hold's base. Code that tells a names push by its seqno being the last applied misses every title of a quiet pane; wezterm-client's `lbterm_names::current` takes a seqno not behind the last applied, and refuses one that would end a hold, whose end only the GUI thread's apply tells hidden_scan of (perf/background-titles).
312. **A PDU the backlog counts as applied may not be applied yet.** `process_unilateral_inner` hands a push that waits on the server (an image's data, a pane to resync) to a task of its own and drops its `Applied` at once, so the client thread reads on for the answer the task waits on: `Backlog::unapplied` says it's applied while its pane still shows what it had. Anything that must keep a pane's PDUs in order across threads asks `Backlog::waits`, which counts a pane's PDUs until they're applied, a task's until it ends (`Applied::goes_on`): a names push applied on the client thread ahead of such a push would have its older title put back by it (wezterm-client's lbterm_names.rs, perf/background-titles).
313. **The client thread takes a pane's renderable lock, so the GUI thread must never wait on the client thread while it holds one.** Since perf/background-titles a names push is applied on the connection's client thread under the pane's `renderable` mutex (`lbterm_names::applied_here`), when nothing of the pane waits in the backlog. A GUI-thread path that holds a pane's renderable lock and then blocks on something only the client thread can bring (an answer: `smol::block_on` of a request, `lbterm_current_now`'s ask, a wait on the backlog's room) deadlocks both if that pane's names push comes meanwhile: the client thread stops reading on the lock, and the answer never comes. None does on 2026-11-10 (`lbterm_current_now` asks before it reads; PaneWriter spawns its write; the paint's lent rows wait on nothing), and the lock is taken only for a pane none of whose PDUs is being applied. Waits on the client thread go before the lock is taken, never under it; and a lock held long on the GUI thread (hidden_scan's read of a pane out of view) holds the client thread, and a key's echo behind it, that long.

314. **A window's mux subscription reads nothing the GUI thread keeps to itself.** Its closure is `Send + Sync` and runs on whatever thread calls `Mux::notify`: the GUI thread for a client pane's alert today (the take applies it), but any thread a notification is ever sent from. Since perf/background-titles it decides a pane's title alert there, before any task (`titles::lbterm_title_alert_dropped`), so everything that decision reads is left where any thread reads it: the window's `TitleWatch` (atomics for the handlers' answers, set at each config load or override by `lbterm_titles_read_update`; the rail's drawn rows as an `Arc`'d map under a mutex, replaced by each paint as it draws, never after), the mux, and the taskbar's retries, which were a `thread_local!` and are now a process-wide `Mutex` (`taskbar.rs`, `FAILED`): a thread-local read from another thread is silently empty, and the retry would never come. A new input to that decision goes there too, never a `RefCell` of the window or a thread-local. `budget::lbterm_hidden_output` still reads the thread-local budget, which holds only while PaneOutput is notified on the GUI thread. And the watch's rows are the rows as drawn, not as the next paint will draw them: a decider that read the window's state ahead of its paint would drop a title whose row the screen still shows old.

317. **Taking one PDU of an event's burst out of the backlog changes how the rest of the burst is batched into takes.** The first PDU a pane's burst hands over queues the take and gives the GUI thread a head start while the rest arrive, so they share it; take that PDU out (applied on the client thread, dropped there) and the next one queues the take instead, which can now run before the burst's last PDU comes, and a second take follows for it. Before calling such a change a saving, count the takes an event brings before and after in one interleaved run (`title-storm.ps1 -Metrics`' sites), not only what a take costs. perf/background-titles' part 1 applied the names push on the client thread: each take cost less (54 to 44 µs), but the client's takes went from 2.21 to 2.49 a title (+0.27 +-0.18 at 99%, FLOWS.md run 19, against main's slot build), which used the saving up, so part 1 alone left the GUI thread about where it was until the alert and the window's title stopped being handed too (perf/background-titles).

318. **A step of a push's apply moved to the client thread makes every atomic it writes shared between two threads.** A pair of atomics written Relaxed by one thread, or a reader that loads a flag and then stores it false where another thread sets it, can lose an update once both threads write: the reader's store lands after the writer's set, and the newer value is never read. Check each atomic the moved step writes for its ordering, clear a flag another thread sets with a swap, publish a value before the flag that says it's there (Release, read with Acquire), and correct any doc that says which thread writes it. `Drawn` (wezterm-client's lbterm_drawn.rs) was written for the GUI thread alone: `RenderableInner::lbterm_names_here` now calls `Drawn::applied` on the client thread while the paint runs `Drawn::take`, which was a load, a store of false and a load of the seqno, all Relaxed, so a push applied between the load and the store went unsaid with the older seqno said. Now `applied` stores the seqno and raises the flag with Release, and `take` keeps its one plain load for a frame with nothing new, then lowers the flag with a swap and reads the seqno with Acquire (perf/background-titles' fix-up).

321. **The client thread's title decision takes the GUI's locks, so none may be held on the GUI thread across a wait for the client thread, and its window lock is never taken twice.** Since perf/background-titles' fix-up wezterm-gui's `TitleDecider` runs on the connection's client thread for each title alert of a pane with nothing waiting (wezterm-client's lbterm_titles.rs), holding `titles.rs`' `WATCHED` while it asks each window: the window's `mux_window_id` mutex (a copy, released at once), the mux's windows `RwLock` for reading (`get_window`, in a scope that ends before anything else is locked), each tab's split tree (`contains_pane`, `get_active_tab`), the watch's drawn rows and the taskbar's retries (each a mutex, briefly), and each pane of the title's tab's renderable lock (`get_title`). parking_lot's `RwLock` lets no reader in while a writer waits, so a thread that holds a read and asks for another deadlocks against a writer on another thread: the decision takes the windows lock once and lets it go before `titles_move_row`, and must stay that way (a nested `get_window`, `get_active_tab_for_window` or `get_tab` inside the scope would hang the client thread as soon as the GUI thread waits to write, and every echo behind it). The GUI thread takes `WATCHED` only when a window subscribes, holding nothing else, and waits on the client thread under none of these (313: `lbterm_current_now` asks with no lock held). And the client thread never sets the mux window's title itself: `Window::set_title` needs the windows lock for writing, which the GUI thread's nested reads would deadlock against, and notifies the GUI's subscribers on the calling thread (part 3 keeps the title instead: 322).

322. **A mux window's title from the server is kept apart until a take sets it, so every reader reads it through `lbterm_window_titles::title`.** Since perf/background-titles' fix-up the client thread keeps the server's newest title for each window in mux's `lbterm_window_titles` and hands nothing while no handler and no connection to the GUI's own socket reads one as it changes (wezterm-client's lbterm_titles.rs); the next take of anything sets it on the window (`set_kept`), and the four readers read the kept one first: Lua's `MuxWindow:get_title`, the `window_title` of the tab information format-tab-title and format-window-title get (`termwindow/mod.rs`), the GUI socket's ListPanes (`sessionhandler.rs`) and the client domain's check before it sends a title back (`domain.rs`). A new reader of a mux window's title calls `lbterm_window_titles::title(&window)`, never `window.get_title()`, which can be a title behind for as long as no take runs (output held at the server for every tab out of view: minutes). A handed title is kept too, and forgotten when its task sets it only if it's still the one kept (`set`), so a newer one kept meanwhile isn't read over by an older set.

## Watching files

9. **A watch that replaces a poll gets no second chance.** A poll found the file again on its next look. When a watched folder is removed or renamed away, Windows ends the watch silently and nothing ever looks again (high, perf/at-rest, for every watch that replaced a poll). `lbterm_extras::watch` follows a folder back now. Anything new that watches goes through it rather than `notify` directly. An overflowing `ReadDirectoryChangesW` buffer completes with 0 bytes: that means look again, not "nothing happened".
60. **A look, then a watch, misses what comes between: look again once the watch holds.** The scroll strip's reading thread looked for a session's transcript not written yet, then watched the projects folder for one of its name. Written after the look and before the watch took hold, the transcript said nothing to the watch and was never looked for again, so the strip didn't show the conversation until Claude Code next wrote to it. On a loaded PC the thread can come to the look late, after a test has written the transcript, and `conversation::tests::a_transcript_not_written_yet_is_read_once_it_is` waited its 5 s for nothing (2026-11-01): run 280 times on the old code under load, beside copies of lbterm-extras' tests in a warden job of 4 CPUs, it failed once that way, and none of 280 on the new (2026-11-02). Whatever a watch is for is looked for again once the watch holds it, whenever the folders it watches or only the targets it's for change (63) (conversation.rs's `follow` does since 2026-11-02; the tasks card and the summaries follow first and read after, as `Watch::follow` asks). A test can put a write in the gap every time: `a_transcript_written_as_its_watch_is_made_is_read` writes it from a hook the reading thread runs just before it follows (`Conversations::start_probed`), and failed 30 of 30 runs on the old code and none of 30 on the new. (perf/connection-light)
63. **Look again whenever what a watch is for changes, not only when the folders it watches do.** A watch whose callback filters changes by the targets it holds drops a change to a target added since, even in a folder already watched, so the gap between a look and a watch (60) opens again each time a target joins a folder that's watched already. perf/connection-light's conversation.rs looked again only when `Watch::follow` said the watched folders changed. A second session without a transcript, shown while the projects folder was already watched with all its folders for the first, changed only the targets: `follow` said nothing changed, and a transcript written between the look and `follow` storing the new targets was dropped by the callback's filter, so the strip waited for Claude Code's next write. `follow`'s loop now looks again whenever the targets or the folders changed, and `a_transcript_written_as_a_second_session_joins_a_watch_that_holds_is_read` writes the second's transcript in that gap every time: it failed on the code before and passes on the fix (2026-11-02). (perf/connection-light)
73. **A watch holds the folders it's in.** Windows won't rename or remove a folder while any handle inside it is open, whatever its share mode, and a watch holds one on the folder it watches and one on that folder's parent (notify's watch of its name). The InMail button's watches sat inside every one of Lachlan's projects, so no project could be renamed while LBTerm ran: two renames failed on 2026-11-03, and a scan of open handles named the GUI (high, found from outside, not by a test). A watch never takes a folder's name from another program: anything new that watches goes through `lbterm_extras::watch`, which steps out of a folder on request (LET-GO.md), and a watch of a folder other programs rename is weighed for this before it's added.
10. **A test window's folders aren't Lachlan's.** at-rest.ps1 gives each window folders of its own, so it couldn't see that his tab links' file shared the machine-state folder, at about 7 changes a second from other programs, until Terminal moved it on 2026-10-31. A watch's cost depends on the neighbours of the file it watches: measure one in a busy folder too.
254. **A file LBTerm puts in RUNTIME_DIR under a name upstream code lists by prefix is taken for upstream's.** `discover_gui_socks` (wezterm-client's discovery.rs) took every entry of `~/.local/share/lbterm` whose name starts `gui-sock-`, tried a unix connect to it, and deleted it when the connect failed and it was over a second old. Every GUI runs that sweep from its `update_checker` thread (wezterm-gui's update.rs), which `start_update_checker` starts even with `check_for_updates` off: 10 s after the GUI starts (no check file is ever written, so the delay is `initial_interval`), then daily (AT-REST.md, its threads). A JSON file never takes a connect, so it always went. feat/rail-landing-4's 8a published a GUI's own parked panes as `gui-sock-<pid>.parked.json` (`<socket>.parked.json` by the contract): the review's probe of 2026-11-09 parked a GUI-local tab and found the file at 4,068 ms and gone at 13,167 ms with the tab still parked, and the publisher never wrote it again, its list unchanged; any GUI starting later (a test window, a try window, a GUI restart) swept every live GUI's file too. Lachlan's daily tabs' `sock.parked.json` was never at risk. park.ps1's step 7 had passed because it read the file within 10 s, and the docs said the file "stays as its gui-sock-<pid> does". Since the fix-up the sweep counts `gui-sock-` followed by digits alone as a socket (`lbterm_is_gui_sock`), and takes a file LBTerm put beside one, `gui-sock-<pid>.<more>`, only once that socket's gone, swept now or before (`lbterm_beside_gui_sock`), so a GUI's file lives as long as the GUI and goes after it (tests `only_gui_sock_and_a_pid_is_a_guis_socket`, `a_file_beside_a_socket_is_named_by_it` and `the_sweep_keeps_a_live_guis_files_and_takes_a_dead_ones_with_its_socket`, the last with a listening socket); park.ps1 reads the file again 13 s after its window started. Before naming a file beside a socket or in RUNTIME_DIR, grep for what lists that folder by prefix (discovery.rs, the harness's `Get-GuiSocket`, log pruning), and test that the file is still there after another GUI has started and 10 s have passed, not only right after it was written. (feat/rail-landing-4)
256. **On Windows an atomic write by rename must retry, and a writer that failed must not count what it failed to write as written.** MoveFileEx over a file a reader holds open without FILE_SHARE_DELETE (.NET's `File.ReadAllText`, PowerShell's `Get-Content`, an antivirus scan of a new file) fails until the reader lets go. lbterm-extras' `state::write_atomic` retries for 250 ms (`RENAME_FOR`, 5 ms apart) for that, but only its doc comment said why, so feat/rail-landing-4's new writer in another crate, mux's `lbterm_parked::write`, did a bare `fs::rename`; and `look` had already set the publisher's `last` to the new list, so a failed write left Terminal's statusline box wrong until the next park, unpark or pane change. Since its fix-up the write retries as `write_atomic` does (mux can't depend on lbterm-extras, so the loop is copied) and a write that still fails sets `last` to `None`, so the next look writes its list whatever it is (test `a_write_waits_out_a_reader_holding_the_file_without_share_delete`). A new writer of a file someone else reads uses `write_atomic` or its loop, and marks a final failure as unwritten. (feat/rail-landing-4)
380. **A bit set one part wider than its word aliases another part in a release build.** `summaries::Parts` was a `u8`, one bit for each of a session's eight files, built as `Parts(1 << part as u8)`. A ninth part (`<sid>.prompt.json`, feat/rail-last-input) shifts a `u8` 1 by 8: a debug build panics, but a release build masks the shift to its low three bits, so the new part's bit is the first part's and a change to the new file reads the session's one-line summary again instead, with no error anywhere. `Parts` is a `u16` since. Before adding a variant to an enum that numbers bits, count the variants against the width, and test that each variant's bit is its own by comparing it with every other variant, or check the width at compile time: "every file has the new part" and "some other part lacks it" both pass on the aliased code. LBTerm's cargo tests run in release (`lbterm.ps1 test` is `cargo test --release`, and `[profile.release]` sets no `overflow-checks`), so an oversized shift doesn't panic there either: it masks to the word's width and lands on the first variant's bit. The branch's first test, `Parts::ALL.has(Part::Prompt) && !Parts::of(Part::Usage).has(Part::Prompt)`, held on the old `u8` too (`1 << (8 & 7)` is 1, `Part::Short`'s bit, which `ALL` has and `Usage`'s `0x80` hasn't), and only the watcher test, reading `.txt` instead of `prompt.json`, would have shown it. Since the branch's review, `each_part_has_a_bit_of_its_own` compares every pair of parts over the tests' `EVERY` list, and `const _: () = assert!((Part::Prompt as u32) < u16::BITS)` beside `Parts` fails the build for a last part past the word (feat/rail-last-input's review).

## Measuring

11. **A check that judged nothing must not pass.** More findings were this than anything else:
    - a lateness check skipped when no frame was held;
    - a key-wait check skipped when nothing waited;
    - a budget with no values counted as within;
    - a locked desktop skipping the pixel checks with a NOTE and still printing "colours still change";
    - triggers.ps1 asserting nothing and passing with no hearts captured;
    - a `-Measure` mode that skipped the judging and still printed the pass line: perf/mux-resize.ps1 said "every pane at the window's size after the drag and each jump" on a run where every part had settled never (an installed window on perf/mux-client's server), and that branch's stage 3 ran it only with -Measure, so it never saw the failure (perf/mux-client).

    When there was nothing to judge, say "unmeasured" and give a result that isn't a pass. A mode that measures without judging says so in place of the pass line (the harness's `PassedLine`), with what would have failed.
12. **Conditions change the numbers.**
    - On a locked PC (LogonUI) DWM holds each paint longer, so pacing measured locked doesn't hold unlocked.
    - A hidden or covered window never presents, so its screen-time stats read zero.
    - Other agents' runs load the PC.

    Say whether the desktop was locked and what else was running, and measure the claim that matters unlocked and visible.
174. **A difference smaller than the runs' spread takes many runs to tell, either way.** A tab switch's first frame on a mux domain varies by tens of milliseconds from run to run (each run's first switch 60 to 260 ms, the rest 20 to 90), and paced frames add up to a refresh more. perf/mux-client measured its switches 2.2 ms slower than the build before in one round each, and single rounds after swung from 26 ms faster to 26 slower; only over 54 and then 84 switches a build did a steady 6 ms show, with a cause in the code (the new tab's screen scanned for links in its first frame, 3 ms of the GUI thread), and with that fixed 42 switches against 108 put it at 2.3 ms, within what the spread can't tell apart. A median of six or twelve settles nothing a few milliseconds wide: pool every run of each build, say how many, give the 90th percentile too, and find the cause in what the code does (the GUI thread a switch, the counters' tasks) before believing the latency. (perf/mux-client)
136. **A test that counts on from where it expected turns one miss into many.** perf/mux-flood.ps1 looked for each key's echo at the column one past where the last should have been, so a single key the window never showed made every key after it on that line wait out its 5 s: "6 of 28 keys' echoes didn't show" read as a window that stopped echoing, and a stage spent a probe build, a bisection and an hour of runs looking for a stall that wasn't there, when the window's own counters (`budget` `key`, `unshown` 1 and every other key shown in 45 ms at most) said one key. Expect each step from what the window shows after a miss, name the miss (when, and what it showed), and read the window's counters before the test's tally. A failure that came in one stretch of the evening, on builds with different code, and not in thirty runs after it is written down as unexplained, with those numbers, not pinned on the code that changed last (nor, by trap 46, on the conditions). (perf/mux-client)
13. **A budget set from a measurement can enshrine the bug.** key-echo's mux-server CPU budget was 1.5 times a measured 19.6 ms a key, when an echo should cost 1 to 2 ms, so the budget passed the problem. Budget what it should cost, and file the gap as a finding.
14. **A rate declared isn't the rate that comes.** The budget declared animation frames at `animation_fps`, but a blinking cursor runs at its own rate: 1.2 a second against the 1 declared with Lachlan's config. So the daily watchdog warned about a blinking cursor, the first thing it had to allow. Declare a tick at the rate the frames really come, and test the watchdog with his config. (high, perf/budgets)
15. **Measuring costs the daily build.** Instrumentation that runs every frame runs in Lachlan's window too:
    - locks;
    - `metrics::histogram!`, which takes its histogram's mutex, allocates with labels and, for a `.rate` key, reads the clock (the recorder's global mutex and SipHash lookup a record are gone since perf/fonts-core, each thread keeping its handles: `lbterm_extras::recorder`, PERF.md finding 87); a count that's only added to is an atomic, as `lfucache::counts` is;
    - a QueryInterface on the swapchain;
    - Vecs made each frame;
    - a list of every animation ever played.

    Use `lbterm_extras::hist`'s fixed atomic buckets and reuse buffers. Anything heavier goes behind a switch the runner or a `metrics` request turns on (perf/budgets).
70. **CPU measured by cycles moves with the clock, and the clock moves with the load.** Cycles count time at the nominal 3.0 GHz, but Windows runs a lightly loaded core at 1.3 to 1.9 GHz and a busy one at the 3.5 GHz cap (2026-11-03), so the same work read up to 2.7 times dearer when the PC was quieter. The budget runner scales its cycles to the nominal clock and says the clock and what else ran (PERF.md, "The PC while it measured"); a script that measures cycles on its own reads the clock over its span too (`Start-PcWatch`, `Stop-PcWatch`, `ConvertTo-PcSpan`) before its numbers are held against another run's.

So against tab_switch's 200 ms ease-out a switch from rest shows its whole fade, only that much late, and a switch while another fades steps by what the fade moves in the difference of two frames' lags, about 1.5 ms, unless the frame makes a tab's surfaces for the first time; Lachlan's 2a of 2026-11-10 asked for these numbers before deciding (perf/commit-lag). The frame flow's trace of the same day (FLOWS.md, "A frame, from the invalidate to DWM's present") adds two things: the Commit isn't where DWM starts them, the first DWM frame that includes it is, up to a refresh later (326); and in its run of tab-by-key the first switch (10.8 ms) made no surface, so a run's first switch is more likely a spare's surface sized again, which nothing counts (331).
354. **What a share moves in a stretch of time doesn't bound how far apart two stacks showing it can be when their curves' lags differ.** A tab in flight shows its share through an opacity that is the share over what the layers above it leave (`Flight::opacity`), no one curve: just after a switch at `slowdown` 5 the tab left's share falls about 0.001 a ms while its opacity falls about 0.03 a ms, because what the tab above it leaves is still growing. Shift every curve of a stack by one time and the stack shows the flight that much sooner or later, moving as the shares move; shift two curves of one stack by different times and the two steep slopes no longer cancel. Lags do the second: only the curves a switch changes are played again (`Switched::redrive`), so a stack holds curves handed over by several frames, each at its own frame's lag, and `prepare` to `prepare_sides` took a different time in each (298). flight.rs allowed the strips and the panes apart by what the panes' share moved within the spread of the lags (`Shot::moves`), which held at a quiet PC's 2 to 6 ms and failed under a check's load: 0.020 apart against 0.018 allowed at 6 ms and 0.045 against 0.038 at 15 ms, two of six checks on 2026-11-12, on branches that changed no Rust; then 5 of 80 runs under two copies of the suite on 4 CPUs, at lags 7 to 63 ms apart. A bound that holds takes each curve on its own (`Shot::reach`): with every opacity anywhere from the moment to the spread of the lags after it, the least and the most each stack can show of a tab (a layer least at its least under the ones above it at their most, and the other way round), and the two stacks' reaches have to meet, because the flight's share at one moment, the one the least lagged curve shows now, is within both. The window goes after the moment, never before it: before a curve's own commit there is nothing of it to read. A looser check has to be shown to still catch a fault: against strips made wrong in the test (read further on than their lags say, or scaled) it failed strips 3 ms or more further on and 2% or more off, at lags 2 to 4 ms apart, and passed 1 and 2 ms and 1%; and 80 of 80 runs passed under the load that failed 5 of 80 before. The switch's check still goes by `moves`, the two frames' together, and failed in none of those runs: the curves a switch leaves alone are the same in both frames and the new ones all carry the new frame's two lags, but a switch back plays again every curve under the tab taken out, which the frame before held at several frames' lags, so nothing proves load can't beat it too. Its reach would have to go both ways from the moment, and a new strip's curve has nothing before its commit. fix/motion-begin begins every curve at its frame's moment, which takes the lags and every allowance for them to 0: merging it, its flight.rs wins whole and `reach` goes (fix/flight-test-allowance).
324. **A frame's curves get their starts from many `Instant::now()` calls, and DWM starts all of them at one commit.** `prepare` takes the frame's moment (`now`, kept in `prepared`), `PanelLayers::sync_rings` inside it takes its own, and so do exactly these prepares after it: `prepare_sides`, `prepare_keyboard`, `prepare_hover`, `prepare_strip_card`, each `prepare_faded` (seven a frame), `prepare_menus` (one for all its slots), `prepare_connection_lamps`, `prepare_hearts`, `prepare_lights`, `prepare_readout` and `prepare_swap`; `prepare_menu_spinner` and `prepare_link_lamps` read none. Decisions take moments of their own inside the draw too: `lbterm_arrival.frame`, and `lbterm_menu_visuals` (`menu_showing(slot, now)`, between `prepare_new_tab` and `prepare_menus`). `drive` stamps each Tween at its own moment, after its caller read the from-value at the caller's; `play` makes no Tween, and its callers stamp prepare's moment (`dim_to`, `play_alpha`, a left outline's `going`), `prepare_keyboard`'s (`light`, `tint`), `prepare_menus`' (a lamp), or, in `FocusOutline::rise`, an `Instant::now()` taken after the play over segments sampled at prepare's `t`. A curve sampled at one moment from a model started at another leads the rest on the screen by the gap (`prepare_sides`, 298; `rise`'s segments against its stamp), and a curve stamped later than the moment its from-value was read is behind its own model by the gap when it's next turned round. The gaps are µs, and any surface made or sized between two moments adds its whole cost, 3.4 to 6.5 ms a surface (331). A fix hands one frame moment to every prepare and to `drive` and works every curve out from it, every stamp listed here and not only prepare's; a new prepare doesn't take a moment of its own (feat/context-bar's `prepare_context_bar` takes one). CODEMAP.md, "A frame", step 6, lists them (docs/frame-motion-commit).
325. **The strip's words and the strips' pictures follow different clock rules.** `prepare_swap` keeps a stack of its own (`SwapStack::flight`), switched at its own `t` and sampled at that same `t`, so from rest the words' fade starts at its beginning and shows with the panes'; `prepare_sides` samples the panes' stack, whose leavings started at prepare's `t`, at its own later `t`, so from rest the strips lead (298). On a turn round both step, each by its own frames' lag difference. Moving either to the other's rule changes what shows, each the opposite way. This answers 298's "`prepare_swap` ... wasn't looked at" (docs/frame-motion-commit).
326. **DWM starts an animation at the first frame that includes its commit, not at the Commit call.** `IDCompositionAnimation::SetAbsoluteBeginTime`'s documentation: "the first frame that includes the commit samples the animation at offset zero", the start varying with the time from making the animation to Commit and on to the engine picking the commit up. The lag trace (`lbterm::compositor::lag`) measures prepare to Commit only, and the stand-in starts every animation at `Call::Commit { at }`, the call's moment (304). The rest, from the Commit to DWM's next frame, is neither measured nor modelled: 0 to a refresh (6.25 ms at 160 Hz, 16.7 at 60) and DWM's pickup, and since LBTerm's paints aren't locked to the vblank it changes from commit to commit and can be more than the 1.5 ms spread of commit lags 304 measured. A retarget's step is the difference of two frames' whole screen lags, so a test that passes against the stand-in can still step on the screen by up to a refresh of motion (docs/frame-motion-commit, from Microsoft's documentation; not measured).
327. **Ends, `done` moments and wakes are on the compositor's clock, early against DWM's by the lag of the frame that started each curve.** Exiting panes' `done` (`Tween::finishes`, drive's moment plus the curve, or `at_clock(leaving.end())`), `SidePicture.done`, `LeftOutline.done`, the swaps' ends, `put_away_faded`'s wake (done + 2 ms), `Compositor::settles`, the state probe's end frame and `present.rs`'s Episode `settles` all are. So `put_away_faded` and `prepare`'s `retire` take a visual out while DWM still has up to that lag of its tail to play (about 1.7 ms after a switch, about 13 after a first switch, and up to a refresh more, 326), and present's walk can stop a frame or two before DWM's last frame of motion. Harmless on `tab_switch`'s ease-out, whose share there is under about 2.5e-4 at a steady switch's lag plus a refresh and under about 1e-3 after a first switch (about 13 ms plus a refresh), below a level of 255 (3.9e-3) either way; a short curve, or one that ends steeply or on something visible, would show the cut (docs/frame-motion-commit, worked out from the curve).
329. **On a mux domain the frame wait splits one tab switch's curves over two frames.** On a switch to a tab whose pane the server holds, the first frame draws the old tab's panes (`lbterm_frame_panes`, CODEMAP.md's "A tab switch", step 4) while everything that reads the open tab starts: the rail's marker and rows (`rail.marker`, `rail.row.swap`), the strip's swap (`Words::Swap`: no panes dissolved yet) and any card's fade (frame_wait.rs's header); the panes' dissolve, the sides' picture and the left outline start at the frame that draws the new tab, a frame period later at least, up to `SWITCH_WAIT`'s 50 ms. The kept frame is drawn, so the pacing holds the next a period after it however soon the push comes: 16.8 to 17.6 ms in FLOWS.md's run 13 (pane-output flow), 17.3 ms on average and 18.7 at most over 12 waits in Lachlan's window on its 60 Hz screen (2026-11-10, `metrics`' `frame_wait`, every wait ended by the push). Don't read the 0.4 to 2.8 ms MUX.md gives for stage 5 of 2026-11-08 as the gap: they were the whole-window build's, which drew nothing while it waited, so its wait ended at the push (0.8 to 3.7 ms in run 13). That's a difference of starts within one switch that no fix to the commit's lag takes away, and none of the routes to starting them together is free: the whole window held for the push holds the rail for the new tab's first paint too (15 to 25 ms for a screen of links in run 13, the rail 16 to 30 ms later; Lachlan's 2b of 2026-11-08 chose against it), and the panes' dissolve given the switch's first frame's moment as its begin would skip its first period (against his 2b of 2026-11-10). His answers of 2026-11-09 kept the strip's words with the rail, as built (FLOWS.md's pane-output flow, "Decided by Lachlan on 2026-11-09", its (Q2)) (docs/frame-motion-commit, from the code and CODEMAP.md; measured on docs/frame-wait-split).
330. **A spinner held where it stops is off by the lag.** `MenuSpinner::hold` sets the arc at `started.elapsed()` over `SPIN_PERIOD`, `started` being `turn`'s own moment, but DWM began the turn at the first frame that included that frame's commit, and the held angle shows at the stopping frame's: just before it DWM showed (the stop's first DWM frame less the turn's) × ω, and `hold` set (the hold's moment less `turn`'s) × ω, so the arc steps by 257° a second (360° over 1.4 s) times the turn frame's screen lag less the stop frame's, forward or back: about 0.4° for the 1.5 ms spread of commit lags, up to about 1.6° for a difference in DWM's frame phase of a refresh (6.25 ms) (docs/frame-motion-commit, worked out).
332. **Presents before the commit make a new visual's first frame and the tree's change likely to show together, not certain to.** `call_draw_composited` presents every drawn visual and then commits, but DWM applies a commit at its next composition whether or not the GPU has finished the presents queued just before, and shows a swapchain's new buffer only once it's rendered; nothing ties the two (no `WaitForCommitCompletion`, no frame statistics read). Whether they ever split isn't known (FLOWS.md's frame flow, "Not traced yet") (docs/frame-motion-commit).
333. **Acquiring a visual holds one of its swapchain's frame-latency slots until its present, so an acquire, its draw and its present stay in one frame.** Only visuals that must be drawn are acquired (COMPOSITOR.md). A change that moves draws or presents to after the commit (those of visuals the commit neither adds nor moves needn't come before it), or splits the commit, keeps each acquire paired with its present in the same frame (docs/frame-motion-commit).
334. **A begin time has to be set before the animation is handed to a property.** The property takes a copy as it's handed over (294), so `IDCompositionAnimation::SetAbsoluteBeginTime` after `animate(&animation)` reaches nothing; it goes in with the segments and the `End`, in each of compositor.rs's seven makers of animations: `drive`, `play`, `lap`, `Spinner::turn`, `new_ring`'s hue rotation, `prepare_connection_lamps`' y animation and `MenuSpinner::turn` (the repeating ones keep no start, so a change that leaves them without one says why). The stand-in would flag a late one as it flags `late` segments (docs/frame-motion-commit, from the documentation; nothing calls it yet).
337. **`Tween::velocity` during a delay says the motion is already moving.** `drive` with a delay holds the start value on a flat segment (`AddCubic(0.0, from, 0, 0, 0)`) and stamps `start` at the delay's end, so before it `elapsed` saturates at 0 and `velocity` gives the curve's starting speed while DWM holds still: a motion turned round in its delay (the panel's words on opening, a rail row's going face) carries a speed DWM never had. feat/context-bar's round 4 makes it 0 before a tween's start (`a_tween_waiting_on_its_delay_is_at_rest`), for the context bar's delayed drives; main has it as written here until that lands (docs/frame-motion-commit).
353. **A drive with a delay holds its from-value, so one turned round while it's still moving stops dead for the delay; and parts that must move as one share one animation, never two curves sampled alike.** `drive`'s delay is a flat segment at `from` (`AddCubic(0.0, from, 0, 0, 0)`), which is right for a part at rest waiting its turn, but a part still on its way, given a delayed drive back, freezes where it is for the whole delay and then goes back from rest: a stop no interruption may make (the lbterm-motion skill's step 5). Since round 4's stage 6 of feat/context-bar the widened bar's slide back waits for the thin numbers' pane's only from out (`slide_wait`'s `bar_moving`): the thin pane comes out in the bar's own slide now, so a pointer leaving mid-slide finds both moving, and both go back at once from where they are. Round 3's wait never met the case, the thin pane not being out until the bar's slide was done. And two parts whose edges must meet through a motion (the thin pane's clip on the bar's moving left ring) get the one `IDCompositionAnimation` (a parent visual whose offset plays the other's, `Slid::follow`, handed the bar's animation in the same `drive`), never a second `Motion` sampled from the same token: `segments` ends a spring where it's within `PIXEL_EPSILON` of its end, so two distances on one spring end apart (about 30 ms for 54 px against 121 on `panel_open`), and a clip and the edge it rides would part by up to the epsilon at the tail. `a_tween_waiting_on_its_delay_is_at_rest` (337) and the context bar's compositor tests (`imp/tests/context_bar.rs`) hold both (feat/context-bar).

## Caches and memory

24. **A cache's key must cover everything its value depends on.**
    - Kept trigger tints were keyed by the line, not the palette, so OSC 4 or 10 left the old colour.
    - A row's look that turns on another row is kept by both. The weights' colour on a Claude pane's row turns on the row above (an option's line Claude Code wrapped onto it), so the triggers' kept copy is made again when the head the row above hands down changes (`Weighed::head`, render/triggers.rs), not only when its own seqno moves; and the head is handed down in the frame's own order of rows, so it's never read from a row's neighbour out of the frame (feat/questions-pane).
    - Rows kept by a pane's seqno went stale on a mux pane, where a completed fetch doesn't move the seqno.

    Name every input, and key by all of them.
25. **Some things only grow.** Each of these grew, or stuck, for as long as the GUI ran, which is days:
    - every session's prompts from Claude Code's history file, kept for the GUI's life;
    - every animation ever played;
    - each pane's kept rows, dropped only when a new pane was copied;
    - an error flag set for good after one transient failure.

    For anything kept, say when it's let go.

    The glyph cache's atlas only grows too, until it's full and made again, every glyph drawn again in that frame. An image put in it through `cached_image` takes a new place for each new hash, so a picture that changes every few seconds (a live tile) filled it every few minutes. Something that changes in place keeps its place and is written over (`render/thumbnails.rs`, `place`), and a test counts the places it took. Then its quads are the same as last frame's, and the compositor draws a visual again only when its quads change: the screen kept the old picture until the quad carried the picture's version (in its alt colour, which mix 0 takes none of). Whatever changes what a quad's texture holds has to change the quad too.
26. **A cache's size is a memory cost a window.** The line caches' size was picked from tab hops alone, but a window whose panes print fills them whatever its tabs. Measure a full cache before Lachlan chooses. He leans to speed, so report the memory rather than trimming it. What an entry holds counts as much as how many: perf/line-quads-by-content made a cached quad its four vertices and its hash, 280 bytes, where a boxed quad was about 130, and measured full (perf/gui-thread.ps1's fill against main's build) a window grew about 1.6 times as much, 63 MB more of varied lines and 127 MB more of full-width colour runs; a change to what an entry keeps is measured full too. And measured soon after a scroll, it looked the other way: `busy-scroll`'s window held 38 MB less, because main's key had filled the cache with a copy of each line for every row it passed and this one hadn't filled yet. Read a cache's memory full, not after a few seconds of one scenario.
27. **Process walks cost the whole PC.** A pane whose working folder came from its processes walked every process on the PC every 300 ms (13 to 18 ms each, about 5% of a core a pane). Walk when output or a change says to, on a thread of its own, never on the GUI thread.
40. **A pane's folder isn't always said by its shell.** The Conductor starts a Claude Code tab as `pwsh -NoProfile -Command "claude ..."`: no prompt runs before claude, so nothing says the pane's folder (OSC 7) until claudehook's first hook does, and till then the folder shown is its foreground process's. A rule written for Claude panes "with OSC 7 from the pwsh prompt before them" walked every process on the PC every 300 ms while such a tab's statusline and hooks came and went, printing nothing; cmd and Git Bash tabs did the same for good. Work out what a pane shows from what it has said (its title, OSC 7), not from what its program usually is, and test a pane that names itself without saying its folder. Only what changes what it shows walks: a process starting in a pane titled by its foreground, or the foreground itself ending, whose pid the job's message carries. (perf/key-latency)
38. **Once GPU writes are skipped by hash, a quad's hash has to cover every byte of its vertices, on every path that writes them** (the setters, `extend_with`, the copies made with their hashes). When the whole buffer was written every time a visual drew, a field written without folding still reached the GPU once anything else changed; now it never does. perf/paint's `WebGpuVertexBuffer::upload` writes only the quads whose hashes differ from what the GPU's copy holds (`lbterm_motion::content::dirty_runs`). quad.rs's `every_write_to_a_quad_changes_its_hash` holds the setters (`lbterm.ps1 test -Package wezterm-gui`, not in the check), and paint-cost.ps1 holds every path end to end: with `LBTERM_CHECK_UPLOADS` the window keeps a shadow of each GPU copy and counts the quads left out that weren't what it held (`visuals.stale`) (perf/paint). Since perf/line-quads-by-content a quad drawn into a `HeapQuadAllocator` (a pane's lines, the Conductor's view's shapes, render/kept_quads.rs's parts, the cards) is written as one mapped from a layer's buffer is, by the same setters in the order they're called, so whatever holds there holds in a heap too: a later `set_fg_color` sets the alt colour to the colour and the mix to 0, and a later `set_position` undoes `set_corners`. Main's `BoxedQuad` kept fields and replayed them in a fixed order as it was copied in, corners and gradient last, with the alt colour 0 when only `set_fg_color` was called; a call site that set the position or a colour after `set_corners` or `set_fg_gradient` drew one way boxed and another mapped. Every heap-drawn call read on 2026-11-04 (card.rs, conductor.rs, connections.rs, link_drag.rs and tab_panel.rs's `set_corners`, followed only by `set_hsv`; screen_line.rs's rainbow `set_fg_gradient`, after `set_fg_color` and `set_alt_color_and_mix_value`, followed by `set_texture`, `set_hsv` and `set_has_color`) draws the same pixels either way: the vertices differ only in an alt colour equal to the colour where the box left 0 (mix 0, so unused) and the rainbow's mix, 0 now where the box kept the glyph's, with its alt colour the gradient's own (so the mix changes nothing). A new call that sets a colour after the corners or the gradient now overwrites them, as it always did in a layer.
39. **A check that a cache isn't made again when nothing changed can't catch a key short of an input: a key that never changes passes it best.** Change each input in turn and require it made again, as well as requiring nothing made at rest. paint-cost.ps1 failed a frame that made a card or panel template again with nothing changed, which a template key without the background or the DPI would have passed, the old template showing; it now adds a tab, makes the window a pixel taller and reloads with another background, and requires the templates made from each made again (perf/paint).
54. **A result kept per object turns on every object's history once the cache is shared.** When a cache moves from one consumer (a font, a pane, a window) to all of them, whatever its answer depended on in one consumer's own history now depends on what every other consumer met first. Before sharing a cache, check that its answer is the same whoever asked and in whatever order, and test the output (pixels, not counts) with and without another consumer having filled it first. perf/fonts-core shared the fallback faces fonts find among every font with the same fallback settings, and gave each new font every face found so far. After a bold line of Hangul, a cleared screen and a zoom, the regular font drew ※ ① ② ≒ 〓 from the Korean face the bold font had found, where main drew them from DirectWrite's own pick, the same with or without the Hangul (718 pixels differed, the same in both rounds); font-setup.ps1 counted searches and passed. A font takes a face only for a character it meets now, and fallback-faces.ps1 compares the pixels (perf/fonts-core).
55. **A cache that some event used to clear relied on that event for every input its key leaves out.** When a change stops clearing it there (to keep work across a reload, a zoom, a tab switch), list every input the old clear covered and add the ones missing to the key or to the condition for keeping it. The shape cache is keyed by style and text, not by direction. Upstream cleared it on every reload, so a change of `bidi_enabled` or `bidi_direction` took effect; perf/fonts-core kept it when `font_key` matched, and `font_key` left the bidi settings out, so a bidi change would have left runs shaped in the old direction. They're in `font_key` now (perf/fonts-core).
103. **A cache keyed by where something is drawn can't keep what only moved.** `LineQuadCacheKey` held `top_pixel_y` and `phys_line_idx` until perf/line-quads-by-content (2026-11-04), so a pane that scrolled laid every visible row out again every frame (about 90 of 92 rows missed a frame in perf/paint-cost.ps1, 3 ms of `render_screen_line` and 1 ms of evictions) and filled the 4,096-entry cache with entries no frame would hit. Key what a thing shows and apply where it goes as it's copied (128, 129). And a change to the line path measured with a ticker or a spinner (busy-one-tab, paint-cost -Spinner: one row changes) says nothing of scrolling output: measure both (the pane-output flow, FLOWS.md rows 85 to 91).
104. **What a frame keeps on a line stays only if the frame was given the line, not a copy.** The renderer keeps a line's shape key on the line itself (`Line::set_appdata`, `render/mod.rs`'s `line_shape_hash`) so the next frame doesn't hash it again. A local pane hands a frame its terminal's own lines; a mux pane's rows reached the frame as copies (`get_lines`), three times a frame (`apply_hyperlinks`' two, `with_lines_mut`'s one), so the key went with each copy and every row of every mux pane in view, every pane Lachlan has, was hashed again on every frame (0 hits of 30,360 in the pane-output flow's run, FLOWS.md rows 79, 81 and 84; perf/mux-client found the same apart from it). perf/mux-client lends the frame the rows where the client holds them (`wezterm-client/src/pane/lbterm_lent.rs`). Before relying on something kept on an object, check that every path to it hands out the object and not a clone, and test that the second look finds it (`lbterm_lent.rs`'s tests mark a lent line and look for the mark where it's held). And whatever changes the object without moving what the kept value is checked by forgets the value: the client's local echo writes its guess into a line without a new sequence number, so it clears the key (`renderable.rs`, `clear_appdata`).
105. **The client's line cache reserves for the whole scrollback when it's made.** lru 0.16's `LruCache::new(scrollback_lines)` sizes its HashMap up front, about 1 MB a mux pane at 50,000 lines (65,536 buckets of 16 B), so only a smaller cache cuts it, not a lazier fill. Worked out from the code (the pane-output flow, FLOWS.md row 60).
128. **A line laid out once and drawn at many rows takes nothing from its row but the offset added as it's copied.** Since perf/line-quads-by-content a pane's line is laid out as if at the window's top (`top_pixel_y` 0) and kept by what it shows, and each frame its vertices are copied in with the row's pixel y added to every one (`lbterm_motion::content::place`); rows that show the same line share the entry. So anything `render_screen_line` draws (or what it calls: `populate_image_quad`, `filled_rectangle`, the cursor's sprite, the lock glyph) that takes the row some other way is drawn at another row's place as soon as the line moves or another row shows it: a y clamped or clipped against the pane's or the window's bounds (worked out at row 0, the window's top), a colour or a pattern by row (stripes, a row's number, a mark from the scroll strip), `stable_line_idx` or the line's index read for anything but finding the cursor's row. Each goes in the key (as the cursor, the selection's columns, the composing text and password input do) or is drawn apart after the rows (as a picture row's thumbnail is, `lbterm_paint_thumbnails`), and the list under FLOWS.md's segment 4 table says which; add a new one there. perf/line-quads.ps1 compares a scrolled screen row by row with the rows before it and with the same text drawn in a window that never scrolled (perf/line-quads-by-content).
129. **A copy that moves vertices moves their hashes, on every path.** The GPU's copy of a layer is written only where a quad's hash differs from what it holds (38), and a line's place in the layer's buffer doesn't change when the line moves if nothing above it in the pane changed how many quads it has: a lone line on an otherwise blank screen, moved up a row, sits in the same quads of the buffer. Copied in with the hashes it was laid out with, the pane's content key and every hash would be what they were, and the screen would keep showing it a row lower. Hits and misses both go in through `HeapQuadAllocator::lbterm_apply_moved`, which folds the row's offset into each hash (`lbterm_motion::content::moved`); a new path for kept lines goes through it too, never `apply_to` (for quads copied in where they were drawn: the Conductor's view's shapes, render/kept_quads.rs's). `lbterm-motion`'s tests hold that a row's offset changes every hash and the same row keeps them, and perf/paint-cost.ps1's LBTERM_CHECK_UPLOADS counts a quad left stale on the GPU; perf/line-quads.ps1's lone mode is the scenario that has it to count (131) (perf/line-quads-by-content).
131. **A stale-upload check catches a hash that leaves something out only where a quad keeps both its place in the buffer and its hash while its vertices change.** LBTERM_CHECK_UPLOADS, `visuals.stale` and captures compare what was drawn with what should have been; in a scenario where every index of the layer's buffer holds other content than the frame before, every hash changes anyway, the upload writes everything and the visual is drawn again, so it passes with the change left out of the hash. 303. **wgpu-hal's D3D12 device has one idle fence and one auto-reset event, which every surface's configure and drop wait on with no timeout, so two threads doing either on one device can wait for ever.** `Surface::configure` and a surface's unconfigure (its drop) call `wait_for_present_queue_idle` (wgpu-hal 25.0.2, `dx12/device.rs` 235, from `dx12/mod.rs` 1179 and 1353): it reads the device's idle fence (`Device::idler`), signals one more on the present queue, gives that value to `SetEventOnCompletion` with the device's one auto-reset event (`Event::create(false, false)`) and waits on it with `WaitForSingleObject(INFINITE)`; the device's own fence waits (`dx12/device.rs` 1995 and 2035) use the same event. Anything that shares one wgpu device across threads (cargo tests, which each run on a thread of their own; a worker thread making surfaces) keeps its surfaces' configure and drop to one thread at a time, or gives each thread a device of its own.
